# 31 · 操作手册——版本更替与发版清单（改哪里、什么顺序、验收什么）

> 目标读者：本人（与 docs/27 同款"照抄就能做对"风格）。定位分工：**docs/27 讲怎么打包、怎么冒烟；本文讲发一个新版本前后要动哪些文件、按什么顺序提交、验收哪些产物**。
> 本清单按 v0.3.3 实际发版过程整理（2026-11-17），以后每次发版照走，发现新的坑就往 §7 里补。
> 终端默认 Git Bash（GB）；打包命令的 PS 写法看 docs/27 §4。

---

## 1. 版本号要改的地方：**只有一处**

| 位置 | 改不改 | 说明 |
|---|---|---|
| `package.json` 的 `"version"` | **改** | electron-builder 产物名（`${version}`）、`dist/latest.yml`、包内 `resources/app/package.json` **全部自动随动**，不要手改它们 |
| `package-lock.json` 的 `"version"` | **改（两处）** | 行 3（顶层）与行 9（`packages[""]`）——手改与 package.json 同值。★行 1405 附近还有依赖 `chromium-pickle-js` 自己的 `"version": "0.2.0"`，**别误伤**。历史备注：v0.3.1–v0.3.3 手改 package.json 时它没跟、npm install 也没同步（一直停在 0.2.0），v0.3.3 发版后一次性校平并纳入本清单 |
| `src/`、`desktop/`、前端 | **不存在** | 源码与 UI **零硬编码版本号**（2026-11-17 grep 实证：src/ desktop/ 无 `0.3.x` 字面量，桌面壳与页面均不显示版本）——以后若加了"关于"页显示版本，记得回来更新本清单 |
| `dist/` | **不入库** | `.gitignore` 第 2 行；产物只留在本地 |

## 2. 发版前提（缺一不发）

1. **本轮改动的编号文档已写好**：docs/NN 设计稿 + 头部实施记录（变更惯例，docs/21 §6）；文内测试数字是**最终复跑值**（不是计划值）
2. **README 已同步**三处：
   - 维护导航「**最新一轮**」轮换——本轮变"最新一轮"，原最新轮降级为"上一轮"（保留到上上轮即可）
   - 受影响的**章节口径**（行为变了但 README 还写旧行为 = 文档撒谎）
   - **文档索引**登记新 docs 条目（docs/28 曾漏登记被补，发版前检查索引止于 NN-1 还是 NN）
3. **过时数字顺手同步**：docs/27 §5 的测试项数与 sa4 项数**每次发版都会过期**（实测：450 项/10-10 → 480 项/11-11 就是这么过期的）——发版前 grep 一眼 docs/27 里的旧数字
4. **预检三件套全绿**（docs/27 §5 第 1 层）：

   ```
   npm run typecheck      三段全过无红字
   npm test               fail 0（项数随测试增长，480+）
   npm run smoke:sa4      11/11 项通过
   ```

## 3. 提交惯例：**两个提交，顺序固定**

```bash
# ① 特性提交（先）：本轮全部 src/ + docs/ + README 改动，不含 package.json
git add src/ README.md docs/NN_*.md docs/27_*.md   # 按实际改动
git commit -m "feat(web): <一句话主题>（docs/NN）" -m "<body：改了什么/为什么/测试数字>"

# ② release 提交（后）：只有版本号（package.json + package-lock.json 两处字段）
# package.json 与 package-lock.json（行 3、行 9）版本 bump 后：
git add package.json package-lock.json
git commit -m "chore(release): v0.3.N——版本号更新重打包（随 docs/NN <主题>）"
```

- 提交信息**中文**、`feat(web)/fix/chore(release)` 前缀、body 写清测试数字——历史翻起来能对上轮次
- release 提交信息里**点名"随 docs/NN"**（v0.3.1→v0.3.3 都是这么写的）
- 个人项目直提 main，无 PR 流程

## 4. 打包（双镜像必带，docs/27 §4 详注）

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/ \
npx electron-builder --win
```

- 2–5 分钟；输出里的三条警告（asar disabled / no code signing / author missed）是**已知取舍不是错误**
- `installing native dependencies / @electron/rebuild` 段出现是正常步骤（koffi 原生依赖装配）
- 成功标志：`dist/ZQQ-harness-Setup-<版>.exe` 与 `dist/ZQQ-harness-<版>-portable.exe` 都出现

## 5. 产物验收清单（照抄，GB）

```bash
# ① 双产物 + latest.yml 文件名都带新版本号
ls -la dist/*.exe dist/latest.yml
#    预期：ZQQ-harness-Setup-0.3.N.exe / ZQQ-harness-0.3.N-portable.exe / latest.yml

# ② latest.yml 的 version 字段 = 新版本（releaseDate 是 UTC，比本地慢 8 小时是正常）
head -3 dist/latest.yml

# ③ 包内 app 版本随动
grep '"version"' dist/win-unpacked/resources/app/package.json

# ④ koffi DLL 在包内 ★查法有讲究★
ls dist/win-unpacked/resources/app/node_modules/@koromix/koffi-win32-x64/win32_x64/koffi.node
#    ★别去 node_modules/koffi/build 里找——koffi 3.x 的原生二进制在 @koromix 平台分包里，
#    主包内 find *.node 一个都没有是正常形态，别误判成"DLL 丢了"

# ⑤ 本轮新代码确实进包：挑一个标志性字符串（新按钮文案/新函数名）grep 包内对应文件
grep -c "自动放行" dist/win-unpacked/resources/app/src/web/public/index.html   # v0.3.3 例：3
```

- **人工项**：双击 `dist\win-unpacked\ZQQ-harness.exe` 快速验收（出窗不白屏 / 功能可用 / 关窗进程清零，docs/27 §4 第 3 步）；要发给别人再按 docs/27 §5 第 3 层清单真装一遍

## 6. 推送 GitHub

```bash
git status --short        # 应干净（dist/ 不会出现）
git log --oneline origin/main..HEAD   # 预览将要推的提交
git push origin main
```

## 7. 常见坑速查（版本更替专属；打包运行时坑看 docs/27 §6）

| 坑 | 说明 |
|---|---|
| 只改了 docs/ 或 README 就重打包 | 白等 5 分钟——**只有 src/、desktop/、public/ 变了才需要重建**（docs/27 §3） |
| lockfile 只改了一处 version（或误改行 1405 的依赖版本） | 项目自己的在**行 3 与行 9 两处**；行 1405 是依赖 `chromium-pickle-js` 的版本，碰了会污染依赖树记录——改完 `git diff package-lock.json` 应只有两行 |
| 在 node_modules/koffi/build 找 DLL 没找到就以为打包丢了 DLL | 原生二进制在 `@koromix/koffi-win32-x64` 分包（§5-④），主包无 `*.node` 是正常形态 |
| README 索引漏登记新 docs 条目 | docs/28 踩过（索引止于 27 没登记 28，后补）；发版前对照 docs 编号检查索引 |
| docs/27 里的测试项数/sa4 项数没更新 | 每次发版必过期（§2-3）；它俩是手册里唯二的"活数字" |
| latest.yml 的 releaseDate 比 local 时间早 8 小时 | UTC 时间戳，正常 |
| 预检没全绿就发版 | v0.3.0 的教训（sa4 10/11 带红出厂）——**三件套全绿才允许 bump 版本号** |
