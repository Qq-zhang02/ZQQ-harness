**最需要立即处理的发现（P0，详见 §2.2）**：

## 1. 架构现状总评

### 1.1 分层与依赖方向（优秀，勿动）

```
src/core/      零依赖内核：Registry、HarnessContext（7 张注册表）、各扩展点 Definition、
               模块装载器、SSE 事件名单、系统提示装配、文件工具共享机制、HTTP 助手
src/modules/   能力模块（18 个）：工具×9、提供方格式×2、MCP 传输、沙箱后端、技能来源、web 路由×4
src/modules.ts 产品 = BUILTIN_MODULES 组合清单（增删能力的唯一登记处）
src/web/       壳：server.ts 瘦壳（≤250 行哨兵）+ session-runtime/-lifecycle/subagents
               + sessions/workspaces + 单文件前端
```

- 依赖铁律"modules/* → core/* 允许，模块间禁止互相 import"由契约测试的 **import 图哨兵**强制；`server.ts` 有 **≤250 行哨兵**；SSE 13 事件名有三端契约测试锁定；系统提示有 golden 测试。这些哨兵是架构不走样的保险，**任何重构不得删除**。
- 扩展点注册制（工具/格式/传输/沙箱/技能源/提示段/路由七张表）+ 用户级 disabledModules + 外部模块目录，使"新增能力不改旧代码"成立且有测试背书。
- **评估**：这套架构在同类项目中是高水准的。可维护性问题不在分层，而在**个别文件过重**（§3.1）与**配置覆盖不全**（§2）。

### 1.2 配置层（机制优秀，覆盖不全）

机制面（`src/config.ts`）设计很好：缺省值集中在 `resolveThresholds`、lenient 解析（缺失=静默缺省/损坏=全缺省+告警/非法=逐项忽略+告警/未知键告警防拼写错误）、生效值经导出常量下发（消费方零改动）、`/api/meta` 同源。

问题三个：

1. **覆盖面**：现有 18 个阈值键只覆盖了压缩/修剪/子代理配额/pwsh 超时等；MCP 超时、审批升级额度、AGENTS.md 截断、采集上限、清理策略等仍写死（§2.3 给出完整清单）。
2. **键名 typo**：`compectionPressure/compectionKeepRatio/compectionManualKeepTokens` 三个键名拼错（§2.2-④）。
3. **导入期单例**：`config.ts` 在**模块导入时**读一次 `~/.ZQQ-harness/harness.json`（`const HARNESS = loadHarnessConfig()`）。副作用：测试进程读到的是真机用户配置（若用户设了极端值，`npm test` 行为随环境漂移）；运行期无法重载（已文档化为"改后需重启"，可接受）；难以按用例注入覆盖值。改进见 §3.3。

### 1.3 web 层（良好，一处过重）

- `server.ts`（248 行）确实是瘦壳：bootstrap + SSE + 静态页 + 查表分发，无业务逻辑。
- `session-runtime.ts`（503 行）/`session-lifecycle.ts`（249 行）分工清楚（装配 vs 生命周期）。
- **`subagents.ts`（1,390 行）**是后端唯一过重点，混装了：worker 装配（一次性/可复用/重启唤醒三态共用）、非阻塞派发与配额、收件箱送达与合并、上下文治理三档、运行计时、归档/打断控制、transcript 落盘与存档注入、SSE 事件、审计记录。拆分方案见 §3.1。

### 1.4 前端单文件（最大维护瓶颈）

结构：`<style>` ~328 行 + HTML 骨架 ~147 行 + **单个顶层作用域 `<script>` ~2,058 行**。亮点是"三表驱动"（SSE_HANDLERS 13 事件表 / COMMANDS 命令表 / meta 下发渲染），事件名与后端契约测试锁定。

风险清单（详细行号见审计原始记录，此处列结论）：

- **渲染**：`el(tag, cls, html)` 的第三参直接 `innerHTML`，全文件靠每个调用点记得 `esc()`（且 `esc()` 只转义 `& < >`，不转义引号——当前所有注入点都在元素内容上下文所以安全，但这是**靠纪律不靠机制**）；整列表"清空重灌"渲染（renderTree/renderDrawerList/renderProvList/renderRecycle），配套三套滚动/展开态保持补丁（rebuildKeepScroll/harvestOpenKeys/refreshRowMetaInPlace）——补丁的存在说明无 diff 的手写 DOM 已达上限；`foldTurns` 直接搬运 DOM 节点，与 CSS 类名强耦合。
- **状态**：单个可变 `state` + 约 20 个模块级可变量（viewId/sessCache/switchingTo/pendingFollow/viewSeqSeen/drawer.renderSeq…），无封装无订阅；`applyState` 一个函数管 12 件事。
- **竞态**：事件缓冲重放按 `ml` 锚点过滤 + `viewSeq` 序号 + 三重手工 cancellation 守卫——这是全文件回归风险最高的 ~300 行，与 DOM 渲染互相缠绕，**不可单测**。
- **协议耦合**：`info` 事件靠消息文案前缀 "📩" 判断排队消息、自动送达摘要靠正则 `/\[子代理 [^\]]* 完成\]/` 从结果文本反推统计——后端改一个字前端统计归零。
- **重复定义**：上下文档位兜底 25/35 与后端 config.ts 重复（meta 未到时用错值）；工具结果显示截断 20000 前端内部写两遍；确认超时 3000/3000/2500/2500 四处两套节拍；图片规则（张数/大小/mime）前端 3 处 + 后端 1 处共 4 份；输入框高度 160 在 JS 与 CSS 双写。
- **XSS 边角**：历史消息回放图片路径 `img.src = "data:" + mime + ...` **mime 不复验**（上传路径有白名单，回放路径没有——存档被篡改可注入任意 data URI，实际危害低但校验不对称）。

改进路线见 §3.2（渐进式，不引框架，与"无构建"约定兼容）。

### 1.5 测试与文档（优秀）

- 369 项测试含：契约测试（SSE 事件三端、系统提示 golden）、哨兵（import 图、server.ts 行数、config.ts 阈值生效值防回退、扩展成本）、Windows 沙箱真实执行测试。测试分层合理。

## 2. 硬编码参数审计（核心章节）

### 2.1 判定标准

- **不算问题**：已走 harness.json 阈值机制的 18 键及其消费点；协议常量（MCP 协议版本、Anthropic API 版本、WinAPI 常量）；纯算法内部参数（BPE 表、修剪器最小预算、正则）；错误文案里的短截断（300/60 字符级）。
- **P0**：参数间矛盾、或同一值多处定义造成漂移风险、或文案与实际生效值可能不一致——**应立即修**。
- **P1**：用户可感知的运行行为参数（超时/配额/预算/清理），值得进 harness.json——**建议配置化**。
- **P2**：不需要用户配置，但应收敛为单一出处常量（当前分散/重复）——**常量化**。
- **P3**：明确保持现状，**防止过度配置化**（§2.5）。

### 2.6 设计约束与取舍

1. **ThresholdOverrides 是 `Record<key, number>`**：对象值配置（如 anthropic 思考预算表）需要把类型放宽为 `number | Record<string, number>` 并改写校验层——**不建议为它扩类型**，收益小、解析复杂度大。确需运营调优时再单独立项。
2. **导入期单例**（§1.2 问题 3）：新增键继续走现有模式（一致性优先）；整体惰性化作为独立改造（§3.3），**不与参数化混在同一阶段做**。
3. **每键三件套**：`EffectiveThresholds` 字段 + 解析 rules 行 + `resolveThresholds` 缺省；导出常量命名沿用现有惯例（如 `ESCALATION_MAX`）。**提示词/mcp-manage 文案中引用这些常量拼文案**，不得复述字面量（§2.2-③ 原则）。
4. **外部模块可见性**：新常量从 config.ts 导出后自动对模块可用（模块可 `import type` + 值 import config.ts——config 不在 modules→core 禁令内，现有模块已这么干）。合法且应保持。

## 3. 结构改进建议（超出参数化的部分）

### 3.1 `subagents.ts` 拆分（后端唯一过重点）

现状 1,390 行、10+ 职责。拆分约束：模块间禁止互相 import 只约束 `src/modules/*`；**web/ 目录内的拆分不受限**（session-runtime/lifecycle 已互相引用，经 SessionShell 显式首参交换）。

建议按已有注释分隔切五块（每块 200–350 行）：

```
web/subagents.ts          保留：SubagentService 门面 + 派发/配额（tryStartWorker）+ 控制入口
```

拆分是纯移动 + 显式传参（沿 SessionShell 模式），不改行为；契约测试与 smoke:sa2/sa3/sa4 是安全网。**可选**：若将来想做成可禁用模块，再按模块化架构迁移进 `modules/subagents/`——当前优先降文件复杂度，不动架构边界。

### 3.2 前端渐进式改造（不引框架、保持无构建单文件）

按投入产出排序，**每步独立可停**：

1. **常量区 + 纯函数抽取**（半天）：script 头部 `CFG` 常量区（§2.4 末行）；把**事件缓冲重放**（route/ml 过滤/turnEnd 清缓冲）与**foldTurns**抽成不碰 DOM 的纯函数（输入状态与事件，输出动作列表），单文件内独立 `<script>` 块或同文件顶部函数区——为将来可单测铺路（无构建下可用 node:test 直接跑同路径抽出的 .ts；若坚持单文件，先抽函数结构）。
2. **XSS 机制化**（1 小时）：`esc()` 补引号转义（`" '` → `&quot; &#39;`）；历史图片回放路径 mime 复验（白名单外拒绝渲染）；审计 `el(…, html)` 全部调用点后，把第三参改名为 `trustedHtml` 并要求调用点显式 `esc()` 拼接（命名即文档）。
3. **协议解耦**（2 小时）：`📩` 前缀判断与 `[子代理 … 完成]` 正则改为 meta 下发的常量前缀匹配（§2.4）；`subagentArchivePct` 下发后三档标记补全。
4. **渲染统一**（长期）：新代码一律 createElement（el 不带 html 参），innerHTML 拼接仅允许在静态模板；整列表重灌处逐个改为 keyed 更新（先从 renderTree 开始——它是重建频率最高的）。**不引入框架/vite**——"无构建单文件"是项目的明确约定（README/架构图多处强调），破坏它的成本大于收益。

### 3.3 config 惰性化与可测性（独立小改造）

`config.ts` 的导入期读取改为**惰性 + 可注入**：`getEffective()` 缓存函数 + 测试用 `__setHarnessConfigForTest()`（或把 HARNESS 移出模块级常量，改为 server.ts bootstrap 显式调用 `initConfig()` 后各消费方经函数取值）。收益：`npm test` 不再受真机 `~/.ZQQ-harness/harness.json` 影响（当前用户配了极端阈值时测试行为漂移——P8 哨兵测试 `EFFECTIVE = resolveThresholds(...)` 锁的是代码结构不是环境值）；代价：全部消费点从常量改函数调用（约 30 处）。**独立阶段做，不与 §2 混**。过渡方案（更便宜）：config.test.ts 等直接测试 `parseHarnessConfig/resolveThresholds` 纯函数（已是如此），另加一条 CI 型断言"HARNESS.thresholds 为空对象或已知键"防环境污染。

2. **fail-closed**：审批决策归一化、沙箱无后端拒绝执行、harness.json 损坏不阻止启动——配置化不得引入"配置错误→静默放行"路径。

4. **同一运行参数单一出处**（新增）：新增字面量前先问"config.ts 有没有"；哨兵测试锁定高风险值（5MB/1M/8787 类）的出处唯一性。
5. **前端契约面 = meta + SSE 事件名**：前端不得写死后端可配置值（兜底显示逻辑除外，但兜底不得复述具体数字——改为"未收到 meta 前不显示档位"）。
6. **无构建单文件前端**（§3.2-5 的远期选项除外）：任何前端改造不得引入 node_modules 构建链。
