# 41 · 交接文档——超时半成品接续与归档复活（一次性转正）

> **用途**：用户提出"超时的子代理自动归档，结果什么都没有，不能轻易直接放弃做了一半的内容——能不能询问它做到哪步、协调者判断后让它继续、归档的可以复活"。本文档是结论与交接依据。惯例同 docs/31/38：typecheck + `npm test` 全绿；结论以源码为准。
> **写作基线**：v0.3.14 发布后（typecheck 干净；`npm test` 531 项全绿）。行号会漂移，**以符号名为准**。
> **来源**：用户原话「一些超时的子代理自动归档，结果什么都没有，不能轻易直接放弃这些做了一半的内容」「通常协调者喜欢用一次性子代理，然后子代理死半路了……能复活一次性的最好」。
> **决策**（用户确认）：归档复活**含一次性子代理**——复活后转正为可复用形态。

## 0. 现状排查结论（为什么"结果什么都没有"）

超时的一次性子代理被强制归档后，协调者收到的失败报告只有一行归因+统计：

```
[子代理 demo 失败] 子代理超时（300000ms）（3 轮 · 用时 5m0s · 输入 12k/输出 2k tokens）[[过程档案#2]]
```

排查确认三件事：

1. **半成品数据一直都在**：transcript.json 失败也落盘（每轮思考/工具调用与结果全量）；结算点 `ws.agent.messages` 活历史完整（最后完成轮的助手文本与工具调用都在；**半截流式消息不入档**——agent.ts 入档顺序保证，进行中那轮零残留）
2. **报告却是空的**：失败路径 `res.text = ""`，死前进展一个字没有；且 `read_archive` 接续指引只写在可复用分支——**一次性失败连"怎么接续"都不说**（agent-task.ts formatWorkerResult 失败分支只有 tail+transcriptTag）
3. **归档是人为终态而非数据终态**：`reviveFollowup`（docs/17 重启唤醒）已实现"从 transcript 重建 worker"全套装配（createWorkerSession + mountWorkerAgent + restore 回读历史 + effort/scope/system 元数据回填），只是入口 `findReusable` 只认 `state:"idle"`——archived 记录被一句话拒绝

## 0.1 定案总表

| 需求 | 定案 |
|---|---|
| 询问做到哪步 | 失败结算自动生成**残局速览**（`progressDigestOf`）塞进 `SubagentResult.progressDigest`：已完成工具调用数 / 写入文件清单 / 最近 3 个动作（write_file·edit_file 取 path、run_pwsh 取 command 截 60 字）/ 最后一条助手文本（截 600 字）；历史无任何完成轮（首轮 LLM 就超时）→ `undefined` 不造假速览。主动深查仍用 `read_archive subId=N`（不变） |
| 失败报告接续指引 | 一次性失败也补 `read_archive subId=N` + 复活指引（修复此前只写可复用分支的缺陷）；上下文超线者注明"复活会被拒收，改用 agent_task 重派" |
| 归档复活 | `findReusable` 放行 `state:"archived"` 且有 transcript 的记录（与 idle 同通道返回 revivable）；`reviveFollowup` 全套装配零改动复用；**一次性转正**——createWorkerSession 本就 `reusable: true`，复活即转正，审计记录经 upsert 翻转 `archived→idle、reusable→true` |
| 协调者判断续做 | 失败报告自带速览（判断依据）+ agent_followup 复活（判断动作）；工具描述改写"超时/打断做了一半的任务优先复活而非重派" |
| 上下文超线例外 | 强制归档（>50%）与 followup 门槛（≥35%）照旧生效：复活会被 `reviveFollowup` 闸门拒收——此场景指引重派新实例 + read_archive（幻觉风险防线不放宽） |
| provider 缓存视角 | 复活原实例 = 同一对话前缀延续，KV 缓存续用；重派 + read_archive 注入 = 全新前缀，缓存全 miss——报告指引里把复活列为优先 |

## 2. 超时半成品三通道（协调者视角速查）

| 子代理形态 | 超时/打断后 | 接续方式 |
|---|---|---|
| 可复用（reusable=true） | 转 idle 待命，**实例与上下文完整保留** | `agent_followup` 直派（无需唤醒） |
| 一次性 / 已归档（有存档） | 归档，transcript 落盘 | `agent_followup`（按 subId）→ 自动**唤醒复活转正**（本轮新增） |
| 任何形态（保底） | — | `agent_task` 重派 + 任务书指示 `read_archive subId=N`（上下文超线者的唯一通道） |

## 3. 不变量与注意

1. **归档复活不放宽幻觉防线**：contextPct ≥35% 的记录复活被 `reviveFollowup` 闸门拒收（`followupContextReject`）——强制归档线语义不变，测试 docs/10 R1 两条仍绿。
2. **`reviveFollowup` 不依赖 state 值**：只读 `rec.*` 与 transcript meta——这是"archived 同通道"零改动复用的前提；未来动它时保持此性质。
3. **残局速览只报已完成轮**：半截流式内容本就不入 history，速览不造假；"无任何完成轮 → undefined"。
4. **golden 快照纪律**：sections.ts 改文案 = contract.test.ts coordinatorBase 显式同步（本轮 5 处逐行同文镜像，两文件用同一脚本字面量改出，保证逐字节一致）。
5. **转正记录的统计延续**：一次性记录的 tasks/usage/elapsedMs/contextPct 在复活时按存档回填（docs/17 原逻辑），转正后跨任务累计照旧。
