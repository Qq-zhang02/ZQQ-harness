## 0. 需求拆解（用户原话）

> 「协调者派发多个子代理后，已完成的子代理不会显示完成，要等所有子代理完成才返回结果。我需要一个完成后马上显示完成，返回其结果给协调者，协调者收到后自行决定做什么（通常也是等待其他子代理完成）。每个子代理给协调者的返回信息（包括暂停，完成，异常等等返回信息）就像用户可随时给协调者发送消息，协调者随时处于接受信息的状态。」

### 0.1 关键技术点（为什么不是改 Promise.all）

docs/15 的模型是「同轮多个 agent_task 阻塞调用 + 工具循环 `Promise.all`」——结果只能等全部完成后统一回填历史。用户要的模型里**协调者根本不该有阻塞等待**：正确的做法不是把 Promise.all 改成逐个返回（轮次还是要等所有调用 settle 才能开下一轮 LLM），而是**派发本身即时返回**，任务结算后的报告走 docs/11 W1 已有的「自动送达」通道（`deliverToCoordinator` → `rt.inbox`，与用户运行中插话同队列：空闲立即开轮、忙碌排队轮末排空）。暂停/完成/异常/归档全部统一为送达消息——正是「像用户消息一样随时到达」。

### 0.3 明确不做（边界）

- 不做「等待其余报告」的阻塞原语（wait 工具）——等待 = 协调者简短收尾结束回合，报告送达自动开新轮，这是用户要的形态。
- 不做送达防抖/攒批（空闲时每份报告立即开轮——「完成后马上显示」优先）；只合并「忙碌期间已积压」的相邻报告。
- 不保留阻塞式派发选项（模型面无 wait 参数；要顺序依赖就在任务书里写清楚、前置报告送达后再派后续）。
- resume 不送达状态通知（最终报告必然到达，resume 通知是噪声；如需可按 pause 的 via 模式加）。

## 3. 已知边界（诚实声明）

1. 协调者对「正在运行」的子代理没有轮询工具——抽屉 UI 有实时过程流，模型侧只靠送达消息（设计如此：无需轮询，报告会来）。
2. 每份报告在协调者空闲时各开一轮（N 份报告 = N 轮 LLM 调用）——这是「协调者每轮自行决定做什么」语义的直接代价；忙碌积压场景已被轮末合并缓解。
3. 派发回执只带 name/subId/指引，不带任务执行进展；收件箱报告丢档风险与 W2-L1 用户排队消息相同（瞬态不入档，重启即失效）。
4. W2-L2 interject 在协调者会话的实际窗口随非阻塞派发变得极窄（只剩控制类工具执行的微秒级窗口）——机制保留（普通长工具场景 + 单测锁定），协调者真机几乎不再触发。
5. `runWorker` 直调（非服务路径）不挂送达——结果由调用方自行 await（单测/冒烟专用出口，正式路径走 dispatch）。
