## 0. 需求与目标

**需求**：新增「基于子代理的大型项目管理」功能，两层架构——

- **前台对话（协调者 coordinator）**：**无任何其他工具，仅能调用子代理**。只做总体把控（任务分解、派发、验收、整合），不直接读写文件、不跑命令。
- **后台工作子代理（worker）**：具有**完整工具**（run_pwsh / 文件三件套 / load_skill，MCP 见 §4 决策点 D3），独立历史、独立上下文。
- **动机**：解决大型任务中**上下文过长**的问题——具体工作的海量工具调用、文件内容全部留在 worker 的独立上下文里，前台只保留任务书、派发记录与结果摘要。
- **硬性要求（用户补充）**：**必须考虑多个子代理之间的冲突**（并发写同一文件、审批竞争、资源挤占、结果矛盾），见 §5 专项设计。

**非目标（明确不做）**：
- 不做子代理嵌套（worker 不能再派 worker，结构性禁止，见 §4 D6）；
- 不做跨机器分布式调度（单机单进程内的并行）；
- 不引入任何新运行时依赖（零依赖底线：openai SDK + koffi + node 内置）；
- 不改前端技术形态（index.html 单文件无构建）。

```
          │  系统提示 = coordinator 版 base 段（职责/任务书规范/冲突预防），无 skills/mcp 段
          │  历史 = 任务分解 + 派发记录 + 各 worker 结果摘要（自动修剪+spill 保护）
          │
          └─ agent_task / agent_tasks（工具调用，阻塞至 worker 完成）
                │  （并行时 Promise.all，受 subagentMaxConcurrent 上限约束）
                ▼
          worker ×N（一次性 Agent 实例，不进 runtimes Map、不占会话档）
          │  独立 history（coordinator 版系统提示 + workspace 安全规则 + 子代理段）
          │  独立 ToolRegistry（audience=worker 的全部系统工具；无 agent_task → 结构性禁嵌套）
          │  独立升级额度（create() 实例级）/ 独立 spill 子目录 / 独立私有临时目录
          │  共享（父会话级）：审批服务（串行队列）、已读台账（hash 乐观锁）、MCP 配置
          │  自己的 compaction（同款 CompactionDeps）→ 超压自动压缩
          │
          └─ 完成回传：最终报告（≤ subagentResultMaxChars）作为工具结果进前台历史
             usage 汇总计入父会话 totals；报告超长走 spill，前台可再派 worker 读
```

**上下文治理的账**：worker 干 30 轮活的全部过程（文件内容、命令输出）只存在于 worker 上下文；前台每任务只增加「任务书 + 摘要报告」两段。前台自身超压仍有压缩兜底（现有机制）。任务清单/进度的跨压缩持久化靠工作区文件（TASKS.md 约定，提示工程，见 §4 D7）。

## 4. 关键设计决策（已定项 + 决策点）

| # | 决策 | 结论/推荐 | 理由 |
|---|---|---|---|
| D1 | 前台「无工具」如何实现 | **注册表分流**：SystemToolDef.audience 字段，createRuntime 按 rt.kind 过滤注册。协调者 registry 只装 coordinator 受众工具（SA3 起 agent_task(s) 两件；docs/7 W2-S 起四件=+pause/resume_subagent，见偏差 24）；普通会话与 worker 装其余全部（现状字节不变） | 结构性保障——协调者就算幻觉想调 run_pwsh 也只会收到「未知工具」错误（现有报错自动教育模型）；不需要运行时拦截 |
| D2 | 调度模型 | **agent_task（单个阻塞）+ agent_tasks（数组并行）并存**，分阶段交付（SA1 先阻塞式） | 阻塞式最不易错、可先行验证 worker 机制；并行式满足大型任务吞吐。轮询/中断介入（spawn+wait 两段式）列为远期，不做 |
| D3 | worker 是否带 MCP 工具 | **SA1-SA3 不带**（worker = 系统工具 only）。Phase SA4 视需求接：共享父会话 McpManager 需先确认 stdio JSON-RPC 并发安全（docs/3 §5 已备案此风险），否则每 worker 独立 McpManager（进程开销） | 先简单正确；worker 的 registry 是新建的，天然不含 mcp__ 工具，零成本实现「不带」 |
| D4 | worker 思考档位缺省 | **继承父会话当前档位**（废弃 v1 缺省 off） | v1 的 off 是「无工具纯问答省成本」语义；worker 要干实事。per-request 仍可覆盖 |
| D5 | worker 轮次上限 | 新阈值 `subagentMaxToolRounds`（缺省 40，可经 harness.json 覆盖）；沿用 Agent 的「达上限收尾总结」机制 | 15 轮对大型子任务偏紧；收尾机制保证 worker 总能交报告 |
| D6 | 嵌套禁止 | worker 的 registry 只装 audience=worker 工具（无 agent_task）→ **结构性禁止**，无需运行时判定 | 最廉价的递归爆炸防御 |
| D7 | 进度/任务清单持久化 | **工作区文件约定**（协调者系统提示要求维护 TASKS.md，由 worker 代写；前台压缩后重读即恢复全局视图）。不做独立的任务板数据结构 | 复用文件工具与压缩摘要；零新机制；对用户可见可改 |
| D8 | worker 全程过程可见性 | **SA1-2**：agent_task 工具块（现有 UI 原样显示调用+结果）。**SA4**：新增 SSE `subagent` 事件（spawned/done/error + 用量），前端在工具块内嵌 worker 时间线；worker 中间过程不穿透到前台历史 | 渐进；先保证功能闭环，可观测性后补 |
| D9 | 协调者 UI 入口 | 侧边栏「＋ 新对话」旁加「＋ 协调者对话」按钮 → `POST /api/sessions/new {kind:"coordinator"}`；kind 按会话存档，切换/恢复跟随；侧边栏条目加 🎯 徽标；state 下发 kind | 与工作区/沙箱的「按会话记录」惯例一致；不做运行中切换 kind（工具集已装配，切换无意义） |
| D10 | 协调者要不要只读工具（read_file 等） | **不给**（严格两层，按用户需求）。worker 报告落盘（spill/工作区文件）后，前台需要细节 → 派一个「读文件并汇报」的轻量 worker | 严格保持前台上下文最小化；避免协调者偷偷自己干活导致上下文重新膨胀 |

## 5. 多子代理冲突治理（专项设计，用户硬性要求）

### 5.1 冲突面总表

| # | 冲突类型 | 场景 | 对策 | 落点 |
|---|---|---|---|---|
| C1 | **文件写覆盖（lost update）** | worker A、B 各自 read 过文件 X，先后写入——后写覆盖先写，先写的修改静默丢失 | **hash 乐观锁**（写前校验，详见 5.3） | core/file-tools.ts + 台账对象化 |
| C2 | **同文件并发编辑** | A 的 edit_file 与 B 的 edit_file 交错 | 同 C1（编辑也走快照校验）；old_string 未命中时现有报错已能自纠 | 同上 |
| C3 | **审批单槽竞争** | 并行 worker 同时触发审批卡——`rt.pendingApproval` 是单槽，第二个请求覆盖第一个，第一个 promise 永挂 | **审批串行队列**（同会话同一时刻至多一张卡在等，后来的排队；详见 5.2） | session-runtime.ts doAsk |
| C4 | **升级额度挤占** | pwsh 升级额度（8 次/会话）被多 worker 共享挤占 | worker 各自 `createPwshTool()` 实例（create() 本就实例级）——**天然 per-worker，零改动**；台账共享但额度独立 | 现状已满足，验证即可 |
| C5 | **任务重叠/重复劳动** | 协调者派发边界模糊的两个 worker 做同一件事 | **单写者原则**：派发权只在协调者；系统提示强制「按目录/模块划分互不重叠的负责范围 + scope 声明」；派发记录天然在前台历史可审计 | coordinator 系统提示 + scope |
| C6 | **结果矛盾** | 两 worker 对同一模块的产出/结论冲突 | 协调者裁决（系统提示明确职责）；必要时派验证型 worker（读两份产出、报告差异） | 提示工程 |
| C7 | **进程/资源挤占** | N 个 worker 并行 pwsh、并发 API 请求打满速率 | 并发上限 `subagentMaxConcurrent`（缺省 3）+ 累计上限 `subagentMaxTotal`（缺省 24/会话）+ 每 worker 轮次上限 D5；超出立即报错回传（不排队——排队会让协调者误以为已受理） | config.ts 阈值 + 工具执行前检查 |
| C8 | **中止传播不全** | 用户 stop 父会话，部分 worker 继续跑 | agent_task 的 ToolContext.signal 透传给 worker 的 `agent.run(text, signal)`；Promise.all 用 allSettled 语义收集被中止的 worker（结果标注「已中止」）；rt.busy 期间 stop 按钮语义不变 | subagents.ts |
| C9 | **会话生命周期竞争** | worker 运行中删除/压缩/改设置父会话 | 现有 busy 409 语义原样覆盖（worker 在工具调用内 → rt.busy=true）；**例外**：手动 /compact 当前也被 409 挡（现状如此，无需改）；删除会话同理被挡 | 现状已满足 |
| C10 | **MCP 连接并发** | （若 SA4 引入）多 worker 共享一条 stdio JSON-RPC 连接 | 见 D3：先不带；引入时要么确认 transport.ts 请求-响应按 id 配对并发安全，要么加请求互斥，要么每 worker 独立连接 | 决策点，SA4 |
| C11 | **TEMP/spill 目录互踩** | 多 worker 私有临时目录与落盘文件同名 | 每 worker 独立子目录：`tmp/<sessionId>/sub-<n>/`、`spill/<sessionId>/sub-<n>/` | subagents.ts 装配 |

### 5.2 审批串行队列（C3 实现要点）

```ts
// session-runtime.ts：requestApprovalFor 内加会话级串行链（并行 worker 下不竞争单槽）
function requestApprovalFor(sh, rt) {
  let chain: Promise<unknown> = Promise.resolve();
  const askOnce = (req: ApprovalRequest) => askWithMode(rt.settings.askMode, req, (r) => doAsk(sh, rt, r));
  return (req) => {
    const p = chain.then(() => askOnce(req), () => askOnce(req));
    chain = p.catch(() => {});          // 链条不断：前一个被拒/取消也继续下一个
    return p;
  };
}
```

- `doAsk` 本体（单槽 pendingApproval + SSE 推卡 + 审计）不动——互斥下同时至多一个在等；
- worker 的请求在 `ApprovalRequest` 上标注来源：command 前缀 `[子代理 <name>] `（**ApprovalRequest 加可选 `subagent?: string` 字段**，前端卡片展示；审计事件自然带标）；
- abort/turn 结束时现有 `rt.pendingApproval("cancelled")` 只会取消「正在等」的那张；**排队中的**后续请求发起后立即检查 signal（askOnce 前置 `if (signal?.aborted) return "cancelled"`）——worker 侧 signal 经工具 ctx 透传，实现时把 signal 也传进审批包装；
- 无人值守（never）模式：askWithMode 直接 unavailable，语义不变（worker 的命令被拒后按现有文案自寻出路）。

### 5.3 已读台账 → hash 乐观锁（C1/C2 实现要点）

现状：`createRuntime` 闭包 `fileReads = new Set<string>()`（仅记路径）。**防不了 lost update**：A、B 都读过 X → 各自可写 → 后写覆盖先写。

改造（落在 core/file-tools.ts，接口变化穿透三个文件工具）：

```ts
/** 会话级已读台账（乐观锁）：记「读取时的内容指纹」。协调者会话与它派出的全部 worker 共享同一实例。 */
export interface FileLedger {
  noteRead(absPath: string, stamp: string): void;      // read_file 成功后记录
  readStamp(absPath: string): string | undefined;      // 写入前校验用
}
// 指纹 = 文件内容 SHA-1（文件三工具本就限制 ≤5MB 文本，成本可控；不用 mtime——外部进程改回同 mtime 会漏检）
```

写入路径（write_file 覆写 / edit_file）在现有「先读后写」检查之后追加：

```
stamp = ledger.readStamp(abs)
if (stamp !== undefined && stamp !== sha1(currentFileBytes)) {
  return "错误：文件在你读取之后已被修改（可能是并行的另一个子代理或外部进程），你的写入被拒绝以免覆盖他人工作。请重新 read_file 后基于最新内容重写。";
}
// ……执行写入……
ledger.noteRead(abs, sha1(newBytes));   // 写后更新，允许本 worker 连续写
```

> **实现口径（SA3 已落地，见实施记录偏差 12/13）**：上述伪代码的 `readStamp` 不能读共享台账的最新值——A 写入更新台账后 B 校验恒过（漏检）。实际实现是 per-reader 快照（`readerLedger`）+ `staleWriteCheck` 统一守卫 + 审批后落盘前终检。

要点：
- **台账实例共享**：createRuntime 建 `FileLedger`，worker 装配时传**父会话同一个实例**——兄弟 worker 的写入会更新指纹，另一个 worker 的旧快照立即失效。SystemToolDeps 的 `noteFileRead/fileWasRead` 签名随之演进（noteFileRead(path, stamp) / 校验逻辑收进 file-tools 共享机制，工具模块不重复实现）；
- **覆盖 run_pwsh 的旁路修改**：worker A 用 pwsh 改文件、B 用 edit_file 写——B 写前重算 hash 同样能发现（A 的修改改变了内容）；反过来 pwsh 写入不受台账约束（OS 沙箱裁决），这是诚实边界：**乐观锁保护台账路径上的写入不被静默覆盖，不阻止 pwsh 侧的写入本身**；
- **串行场景零行为差异**：单 worker/普通会话里没人中途改文件，hash 恒相等；
- 台账是内存态、不存档（现状如此），无兼容问题。

### 5.4 scope 写入分区（C5/C6 的结构性加强，SA3 交付）

- `SubagentRequest.scope?: string[]`（相对工作区根的路径前缀，如 `["src/auth", "docs"]`）；
- **文件三工具 = 硬约束**：ToolContext 增 `writeScope?: string[]`，`adjudicateWrite` 裁决矩阵追加一条——目标路径不在 scope 内直接拒绝（错误文案指明允许范围），不走审批（scope 是协调者的结构性决定，不是用户审批事项）；
- **run_pwsh = 审批理由级**：OS 沙箱只能做到工作区粒度，命令内容无法可靠静态分析——守卫（workspace.ts 启发式）检测到引用 scope 外路径时，把「子代理 scope 越界」加入 reasons 强制弹卡，由用户裁决。**如实标注为诚实边界**（与 README 沙箱诚实边界同一文风）；
- scope 缺省 = 整个工作区（不填时行为与单 worker 一致）。

## 8. 协调者系统提示草案（SA2 落进 sections.ts，实施时可打磨）

```
你是 ZQQ-harness 的任务协调者（coordinator），负责大型项目的总体把控。你自己没有任何直接工具——
读写文件、运行命令、查询资料全部由子代理（worker）完成，你唯一的工具是 agent_task / agent_tasks。

职责与工作方式：
- 先规划再派发：把大任务分解为边界清晰、互不重叠的子任务（按目录/模块/主题划分），说明各自负责范围（scope）。
- 任务书必须自包含：子代理看不到本对话历史。每份任务书写清：目标、背景与约束、涉及的路径、期望产出（文件落点 + 报告结构）。
- 并行纪律：只并行派发互不依赖、写入范围不重叠的任务（agent_tasks + scope）；有依赖的任务等前置完成再派。
- 冲突预防：绝不派两个子代理写同一个文件；发现产出矛盾时自己裁决，或派一个验证型子代理对比后报告。
- 汇总与交付：整合各子代理报告为最终答复；对用户如实呈现（谁做了什么、成败、产出物路径）。
- 进度持久化：维护工作区根的 TASKS.md（由子代理代写）记录任务清单与状态——它在你被压缩后是你恢复全局视图的唯一依据。
```

worker 的 order 5 子代理段（subagents.ts 内置，SA1）：

```
你是被协调者派出的子代理，独立完成一项具体任务。约束：
- 专注任务书目标，不做任务书之外的事；写入尽量限定在任务书指明的范围内。
- 遇到写入被拒（文件已被他人修改/超出范围）时：重新读取最新内容再操作，不要盲目重试。
- 完成后输出报告（这是协调者唯一能看到的内容）：①结论（完成/部分完成/失败及原因）②产出物清单（路径+一句话说明）③关键决定与假设 ④未决问题与建议后续任务。报告精炼，细节写入工作区文件并引用路径。
```

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 协调者越权（试图自己调工具） | 结构性：registry 无该工具 → 「未知工具」报错自动纠偏（D1）；系统提示明确职责 |
| 任务书质量差 → worker 跑偏 | 系统提示强制任务书结构；worker 报告含「未决问题」回流协调者迭代 |
| worker 跑飞/成本失控 | 三重上限（并发/累计/轮次）+ timeoutMs + usage 全程透明计入父会话 |
| 审批疲劳（并行 worker 频繁弹卡） | 任务书约束在区内操作减少弹卡；无人值守模式语义不变；审批卡带来源标注可快速判断 |
| 乐观锁误伤（外部工具改文件后 worker 写被拒） | 拒绝文案引导「重读后重写」，模型可自愈；这是安全侧失败（fail-closed 方向） |
| 前台历史仍被结果摘要撑大 | subagentResultMaxChars 预算 + spill + 前台压缩兜底 + TASKS.md 跨压缩持久 |
| 并行 worker 同时触发压缩摘要调用 | 各 worker compaction 独立异步，无共享可变状态（summarize 无状态），仅 API 并发——受 provider 速率自然约束 |
| 存档兼容 | kind/subagents 全可选字段；旧档载入即 normal（不变量 6） |
| golden 快照与 SSE 契约变化 | normal 快照字节不变（分支隔离）；coordinator 新快照显式新增；subagent 事件三端同步由契约哨兵把关 |
| server.ts 哨兵超行 | 全部新代码进 subagents.ts/模块/前端，server.ts 零改动 |
