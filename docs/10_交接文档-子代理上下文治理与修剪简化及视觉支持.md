## 0. 需求拆解与语义定案（用户原话）

> 1. 「给子代理添加上下文记录（与主对话类似），目的是为了给协调者看子代理的上下文开销，让其判断子代理情况，防止给上下文过多的子代理继续任务（上下文过长容易出现幻觉），我建议 35% 就不要再使用了，子代理任务完成后若上下文超过 50% 则强制归档。」
> 2. 「检查当前的上下文管理，之前貌似有一个过长处理：头部 60%，尾部 40%，中间若超过 2w 则全文记录到文件里面，我需要修改此方法：只保留头部，若超过就保留全文记录。」
> 3. 「检查是否有视觉功能（不同模型有些有视觉功能，有些没有视觉功能），可以的话添加视觉功能，没有视觉功能的模型可用视觉工具（使用视觉模型，可设置使用哪个）。」

**R3 排查结论（现状）**：项目**完全没有视觉能力**——`ChatMessage` 的 user content 是纯 string（`src/llm/provider.ts`），openai/anthropic 两条 provider 路线的消息映射都不处理图片，前端无上传/渲染入口。R3 是从零新增，不是修复。

### 0.1 定案总表

| 需求 | 定案 |
|---|---|
| R1 计量口径 | 与主对话完全同源：worker 的 `Agent.contextEstimate()`（system+工具 schema+技能+消息，下次请求将发送的全部输入）÷ 会话提供方 `contextLength`，取整百分比。只在**任务收尾时点**计算快照（任务进行中不实时跳动） |
| R1 预警线（修订） | 新阈值 `subagentWarnContextPct`（默认 **30**）：任务收尾占用 **>** 该值 → 报告待命提示附「上下文过长」预警（仍可追加——预警≠拒收），前端抽屉行附 ⚠较长 |
| R1 followup 门槛 | 新阈值 `subagentFollowupContextPct`（默认 **35**）：followup 目标 worker 上次任务收尾时上下文 ≥ 该值 → **服务端直接拒绝**（ok:false 明确文案 + 指引归档重派） |
| R1 强制归档线 | 新阈值 `subagentArchiveContextPct`（默认 **50**）：可复用 worker 任务完成时上下文 **>** 该值 → 不转 idle，**强制归档**（finalizeArchive 正常路径），结果文本说明原因与接续办法 |
| R1 呈现 | idle/archived/done/error SSE 事件载荷、SubagentRecord（存档）、currentState.activeSubagents、工具结果文本 stats 行（「上下文 X%」）、前端抽屉行全部带 contextPct；一次性子代理也记录（纯观测） |
| R2 修剪 | 超预算 → **只保留头部** + 省略标记；spill 传入时**触发修剪即全文落盘**（去掉 20,000 字符门槛）；spill 未传（压缩摘要输入防超长）→ 纯头部截断 |
| R2 阈值 | `spillThreshold` **废弃**：config 保留键解析（旧配置不告警、不再被消费），`SPILL_THRESHOLD` 导出与 prune.ts 的消费删除；README 阈值清单改为「15 个活阈值 + 1 个废弃兼容键」口径 |
| R3 消息格式 | `ChatMessage` user 分支增可选 `images?: ChatImage[]`（`{mime: "image/png"|"image/jpeg"|"image/gif"|"image/webp", data: base64}`）；空不写（存档向后兼容，旧档缺省=无图） |
| R3 直看（有视觉模型） | `ProviderConfig` 增 `vision?: boolean`（提供方表单复选框）；当前会话提供方 vision=true 时前端显示 📎 上传按钮，图片随 user 消息直接进历史（两条 provider 路线转多模态 content 数组） |
| R3 视觉工具（无视觉模型） | 新系统工具 `view_image`（audience=worker，普通会话与子代理可用、协调者无）：读本地图片文件 → 经**用户指定的视觉提供方**（providers.json 顶层 `visionProvider` 字段 + 前端「视觉模型」下拉设置）分析 → 返回文字描述；usage 经新接缝计入会话合计（六类守恒） |
| R3 计数 | 图片 token 按固定估算每张 800 计入 messages 分类（tokens.ts 常量 `IMAGE_TOKEN_EST`），与实际 API 计量的差自然归 other——六类合计=实际输入不变量保持 |

### 0.2 明确不做（边界）

- R1 不做「运行中实时上下文百分比」（任务进行中数值跳动，快照口径够用且稳定）；不做按上下文自动压缩 worker（worker 已有 80% 压缩装配，35/50 阈值远在其之前就介入——防幻觉线 ≠ 防溢出线）。
- R2 不改修剪触发预算（toolResultMaxChars/subagentResultMaxChars 不动）；压缩摘要输入的 300k 防超长截断随新语义变为头部截断（可接受——那是兜底不是主路径）。

> **勘误（docs/40 追记，2026-11-19）**：上句对「压缩摘要输入」的判断在阅读密集会话下不成立——压缩后知识由摘要承载，摘要输入就是主路径，而其尾部 = 最接近保留工作集的**近期上下文**（与工具输出的「尾部是日志残余」语义不同，head-only 的依据不适用）。docs/40 阶段二起摘要输入改**头+尾保留**（尾留 10% 预算，`pruneToolResult` 增 `tailChars` 选项，工具输出路径行为不变）；同批还有：修剪预算按工具解析（阅读类 `readToolResultMaxChars` 120k 独立预算，`Tool.resultBudget` 挂钩）、read_file/read_archive 双层截断单层化、`subagentResultMaxChars` 缺省 16k→32k。详见 docs/40。本文档 R2 正文的「只保留头部」结论对**工具输出**仍然成立，不改。
- R3 不做：图片生成、粘贴板粘贴、图片二次压缩、协调者运行中插话带图（interim 纯文本）、worker 任务书带图（协调者自己无图可传；worker 要看图自己调 view_image）、read_file 读图片（view_image 覆盖该场景）。图片不进 mdLite 渲染管线（user 气泡的图片独立 `<img>` 渲染，工具结果仍纯文本）。

## 1. R2：工具结果修剪简化（先做，独立且其他改动依赖它稳定）

### 1.1 现状（`src/tools/prune.ts`）

`pruneToolResult(text, budgetChars, spill?)`：超预算 → 头 60% + `[中间省略约 N 字符]` + 尾 40%；`prunedChars > SPILL_THRESHOLD`（20,000，harness.json 可覆盖）才全文落盘并附 `[完整输出已存盘：<路径>]`。消费点：tools/registry.ts 的 executeWithMeta（所有工具统一修剪）、subagents.ts 报告修剪（SUBAGENT_RESULT_MAX_CHARS）、compaction 摘要输入防超长（300k、不带 spill）。

### 1.2 新语义（定案）

```
text.length <= budget → 原样（不变）
超预算（budget ≥ 64）：
  head = 预算内头部（codePointBoundary 保护不变）
  spill 未传：text.slice(0, head) + "\n[后文已省略约 N 字符]"
  spill 传入：全文写 <dir>/<n>.txt（best-effort，失败退纯头部截断）+
              text.slice(0, head) + "\n[后文已省略约 N 字符；完整输出已存盘：<file>，可用 Get-Content / Select-String 按需读取]"
预算 < 64：整体丢弃说明（现状分支保留）
```

**依据**：尾 40% 对长输出（日志、报告）价值低且把中段信息全部挤掉；头部保留 + 落盘让模型需要时按需检索全文，比「头尾夹中间丢」更可控。去掉 2 万门槛的理由：既然已经触发修剪，全文落盘的成本（磁盘）远小于信息损失。

### 1.3 改动面

1. `prune.ts`：`pruneToolResult` 重写上述分支；删 `SPILL_THRESHOLD` import；`PruneResult` 形状不变（text/prunedChars/spilled）。
2. `config.ts`：`EffectiveThresholds.spillThreshold` 字段与 parseHarnessConfig 规则**保留**（兼容旧配置，不产生未知键告警）但注释标「已废弃（docs/10）：修剪改为头部保留+触发即落盘，不再消费」；`SPILL_THRESHOLD` 导出删除。
3. `prune.test.ts`：用例重写——预算内不动；头部截断+标记；spill 触发即落盘（小文本超预算也落盘——门槛已删）；落盘失败退纯截断；budget<64 分支；codePointBoundary 代理对不劈（保留既有）。
4. README 同步（§上下文管理、阈值清单）。

**红线检查**：SSE/契约零涉及；`PruneResult` 形状不变 → registry.ts 消费点零改动；subagents 报告修剪自动获益（行为变化：尾部不再保留、落盘更积极——预期内）。

## 2. R1：子代理上下文治理

### 2.1 计量与数据流（定案）

```
任务收尾（runOneTask，res 拼装完成后、按类别分流前）：
  pct = round(ws.agent.contextEstimate().total / cfgOf(sh, rt).contextLength * 100)
  ws.contextPct = pct          （WorkerSession 新字段；一次性也写——观测）
  res.contextPct = pct         （SubagentResult 新字段 → 工具层格式化）

可复用分流（idle 路径前插入）：
  pct > SUBAGENT_ARCHIVE_CONTEXT_PCT(50)
    → 不转 idle：res.forceArchived = true + finalizeArchive(...)
      （记录/事件正常带 contextPct；归档语义与手动归档完全一致）
  否则 → 正常 idle；若 pct >= SUBAGENT_FOLLOWUP_CONTEXT_PCT(35)
    → 待命提示附警告「上下文占用已达 X%，不建议再追加任务」

followup（subagentServiceFor，任务上限检查旁）：
  ws.contextPct >= SUBAGENT_FOLLOWUP_CONTEXT_PCT(35) → ok:false 拒绝文案
  （「上下文占用 X% 已达上限 35%（subagentFollowupContextPct）——上下文过长易产生幻觉。
    请用 archive_subagent 归档后 agent_task 重新派发；任务书可让它先读过程存档
    [[过程档案#N]] 接续上下文。」）
```

**为什么门槛是 `>=` 35 而归档线是 `>` 50**：35 是「不要再用了」的硬闸（等于也算）；50 是「超过则强制归档」，等于 50 还允许（处在 35-50 区间本就只能归档重派，followup 已被 35 闸挡住，50 线只是把 idle 展示也终结）。两句用户原话的忠实映射。

### 2.2 呈现面（全部复用现有通道，零新事件名）

| 面 | 改动 |
|---|---|
| `SubagentResult`（core/types.ts） | + `contextPct?: number`、`forceArchived?: boolean` |
| `WorkerSession`（subagents.ts） | + `contextPct?: number`（最近任务收尾快照；驻留内存，重启失效随记录消失） |
| `SubagentRecord`（sessions.ts） | + `contextPct?: number`（空不写；旧档缺省=无记录） |
| SSE idle/archived/done/error 载荷 | + `contextPct`（有值才带；契约只锁事件名） |
| `currentState.activeSubagents` 条目 | + `contextPct`（句柄上挂，session-runtime 映射） |
| `ActiveSubagent`（host.ts） | + `contextPct?: number`（startWorker 置 undefined，收尾回填） |
| 工具结果文本（agent-task.ts formatWorkerResult） | stats 行 + 「上下文 X%」；待命提示带占用；≥35% 加警告；forceArchived 时待命提示整段替换为强制归档说明（含 [[过程档案#N]] 接续指引） |

| 提示词/golden | coordinator golden 快照显式更新（contract.test.ts）；普通会话 golden 零改动 |

### 2.3 阈值（config.ts）

`subagentFollowupContextPct` / `subagentArchiveContextPct`：(0,100] 整数，默认 35 / 50；规则/缺省/导出三处（契约哨兵自动覆盖新键）；交叉校验：followup 线 ≤ 归档线（违反时告警并互换？**不做**——两条线独立告警即可，乱配是用户自己的选择，文档写清默认关系）。README 阈值清单 14 → 15（spillThreshold 废弃不计活阈值，见 R2）+2-1 = 15。

## 3. R3：视觉支持

### 3.1 消息格式与 provider 映射（后端核心）

1. `src/llm/provider.ts`：
   - `export interface ChatImage { mime: "image/png" | "image/jpeg" | "image/gif" | "image/webp"; data: string }`（base64，无 data: 前缀）；
   - `ChatMessage` user 分支：`{ role: "user"; content: string; images?: ChatImage[] }`。其余 role 不支持 images（system/assistant/tool 无图）。
2. openai 路线（`toSdkMessages`）：user 且 images 非空 → `content: [{type:"text",text}, ...images.map(i => ({type:"image_url", image_url:{url: \`data:${i.mime};base64,${i.data}\`}}))]`；无图原样 string（字节不变）。
3. anthropic 路线（`toAnthropicMessages`）：user 且 images 非空 → `content: [{type:"text",text}, ...images.map(i => ({type:"image", source:{type:"base64", media_type:i.mime, data:i.data}}))]`；无图原样。
4. tokens.ts：`export const IMAGE_TOKEN_EST = 800`；`messageTokenCount` user 消息按 images.length × 800 加进计数（自动进 messages 分类，WeakMap 缓存路径同样生效——消息对象不可变）。注释写明：按典型 vision 模型中档分辨率估算，各家 API 实际计量不同，差额由 withOther 归 other（不变量保持）。
5. agent.ts：`run(userInput, signal?, images?)` —— `this.history.push({ role:"user", content: userInput, ...(images?.length ? { images } : {}) })`。interject 不带图（运行中插话纯文本，docs/10 §0.2 边界）。

### 3.2 提供方 vision 声明与视觉模型设置

1. `ProviderConfig` + `vision?: boolean`；`validateProvider` 读取（`v.vision === true` 才置 true，缺省不带——旧文件零迁移）。
2. `ProviderStore` + `visionProvider?: string`（顶层可选；validateStore 读取：字符串且指向存在提供方，否则丢弃）。
3. web-providers 模块：
   - save 载荷透传 `vision`（boolean 可选）；
   - 新路由 `POST /api/providers/vision-provider`（body `{id?: string|null}`：设置/清空 `data.visionProvider` + `saveProviderFile`；返回 `{ok:true}`）。27 条路由。
4. 前端提供方面板：表单加「视觉能力（模型可直看图片）」复选框；面板顶部加「👁 视觉模型」下拉（选项 = vision=true 的提供方 + 「未设置」，选择即 POST vision-provider；view_image 未配置时工具报错文案会指到这里）。

### 3.3 view_image 系统工具（新模块 `src/modules/tools/view-image/`）

```
SystemToolDef { name: "view_image", audience: "worker"（缺省），summary: "用视觉模型分析一张本地图片（截图/照片/图表），返回文字描述" }
schema：{ path: string（必填，相对工作区或绝对路径）, question: string（必填，要它看什么/回答什么——越具体越好） }
execute：
  1. resolvePath（workspace 基准，同文件三工具的解析口——core/file-tools 的路径解析复用）
  2. 读文件（≤8MB；magic bytes 判 mime：PNG/JPEG/GIF/WEBP；不识别 → 报错「不支持的图片格式（支持 PNG/JPEG/GIF/WEBP）」）
  3. 视觉提供方：deps.vision?.() → ProviderConfig | null（接缝见下）；null → 报错指引
     「视觉模型未配置：请在界面『提供方管理』给支持视觉的提供方勾选视觉能力，并在顶部『视觉模型』下拉选一个。」
  4. createProvider(cfg, deps.ctx.providerFormats).chat({
       messages: [{ role:"user", content: `请分析这张图片。问题：${question}`, images: [{mime, data}] }],
       effort: cfg.effort === "off" ? "off" : "default"   // 视觉调用不带会话档位；遵循该提供方自身配置
       signal: AbortSignal.timeout(120_000) })
  5. 成功 → 返回 `${content}\n\n（由视觉模型 ${cfg.name} 分析；输入 X / 输出 Y tokens）`
     usage 经 deps.reportAuxUsage 计入会话合计（breakdown 全归 other——同 reportAggregated 先例）
  6. 失败 → 错误字符串（含 HTTP/网络原因；工具错误一律字符串回传不炸轮次）
```

**接缝（core/types.ts SystemToolDeps +）**：

- `vision?(): ProviderConfig | null`——解析 store.visionProvider（未配置/指向的提供方已被删 → null）。createRuntime 注入（闭包读 sh.providerFile，热生效）。
- `reportAuxUsage?(u: UsageInfo): void`——createRuntime 注入 `reportUsage(sh, rt, u)`；subagents.ts 的 workerDeps 注入「聚合进当前任务盒再 reportAggregated」？**不**——直接 `reportAggregated(sh, rt, u)` 的等价物：worker 侧注入 `(u) => reportUsage(sh, rt, {...u, breakdown:{全 other}})`，与 printUsage 聚合盒并行（视觉调用的成本不属当前任务的 LLM 轮次，直接进父会话合计更诚实；reportAggregated 是收尾时一次性的，这里即时上报）。

### 3.6 已知边界（诚实声明）

- 图片 token 估算是固定值，各 API 实际计量不同（差在 other 里显示）；上下文占比与修剪预算同口径受此影响。

- 视觉提供方故障/无视觉能力误标（用户勾错 vision）→ 请求失败按错误回传，不静默降级。
