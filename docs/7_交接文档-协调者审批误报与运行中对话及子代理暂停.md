## 1. W1：worker 审批卡误报（scope 守卫把正则/源码当路径）

### 1.1 现象与会话档证据

worker `e5-highprec`（协调者派发参数 `scope=['e5_highprec.txt', 'TASKS.md', 'scripts']`）连续两张卡：

**卡 A（scope 误报，worker 特有——普通会话无此卡）**：

```
Select-String -Path scripts/e5_highprec.py -Pattern 'e5_via_mpmath|e5_via_decimal|range\(ndigits\)|if have <= want' | Select-Object LineNumber,Line
reason: 子代理引用了写入范围（scope）外的路径：
  e5_via_mpmath|e5_via_decimal|range\(ndigits\)|if have <= want、range\、ndigits\
```

`scripts/e5_highprec.py` 本身在 scope 内（未命中）；被当成「scope 外路径」的三个 token 全是 **-Pattern 的正则内容**。

**卡 B（两类 reason 叠加）**：

```
$env:PYTHONUTF8="1"; …; & "D:/Programs/Python/Python314/python.exe" -c @" …python 源码… "@
reason1: 子代理引用了写入范围（scope）外的路径：from decimal import Decimal, localcontext\nimport mpmath as mp\n…（python 源码文本）
reason2: 引用了工作区外的路径：D:/Programs/Python/Python314/python.exe
```

reason1 仍是 scope 误报（here-string 里的**源码**被当路径）；reason2 是**既有守卫** `checkCommandAgainstWorkspace` 的「工作区外绝对路径」——普通会话引用解释器绝对路径同样弹这张（不是 worker 特有；普通模式平时不弹是因为模型惯用 PATH 短名 `python`）。

### 1.2 根因（代码证据，`src/workspace.ts` 的 `pathHintsOutsideScope`）

三路 token 提取（`pathHintsOutsideScope`，docs/5 §5.4「命中即强制弹卡，误报是安全方向」）：

1. **引号内字符串路**：`command.matchAll(/"([^"]*)"|'([^']*)'/g)` 取引号段，判定「像路径」的条件是 `/[\\/]/`（含正/反斜杠）。**缺陷**：正则 Pattern（`range\(ndigits\)` 的 `\(`）与 python 源码（注释/除法/换行转义）天然含 `\` 或 `/` → 整段被当路径 → 卡 A 的第一个 token、卡 B 的 reason1 全部来自这条路。
2. **裸 token 路**：`command.split(/[\s"'|<>&,;()]+/)` —— **引号字符本身也是分隔符**，引号内文本被切碎后流入本路；`|` 与 `(` 也是分隔符，`range\(ndigits\)` 被切成 `range\`、`ndigits\` 两个残片，均含 `\` → 再次命中 → 卡 A 的「range\、ndigits\」。
3. **消费点**（`src/modules/tools/pwsh/pwsh.ts`）：`scopeReasons.length > 0 → 强制 askApproval`（`if (ctx.alwaysConfirm || scopeReasons.length > 0)`），与命令是否只读无关——`Select-String` 这类纯读命令同样强制弹卡。scope 的设计语义是**写入**范围（防写绕行），只读命令引用区外路径本不违反；但守卫按「引用即弹」处理。

**推论**：W1 = ①token 提取把「非路径文本」（正则/源码）误判为路径（真 bug）＋②只读命令不豁免 scope reason（设计保守面）＋③解释器绝对路径触发既有「工作区外」守卫（预期行为，普通会话同语义，但配合①②放大了「子代理特别多卡」的观感）。

### 1.3 修复方案

**路线 A（推荐，必做）：token 提取精度修正——利用「Windows 文件名合法字符集」硬规则**

- **引号段判定收紧**：「像路径」从「含 `/[\\/]`」改为「含路径分隔符 **且** 各字符段均在文件名合法字符集内」。Windows 路径段不允许 `| { } ( ) [ ] * ? : " < >` 等——因此：
  - 含 `|` 的段一定不是路径（`e5_via_mpmath|e5_via_decimal|…` 整段豁免）；
  - 含「反斜杠 + 正则元字符」（`\(` `\)` `\d` `\w` `\s` …）的不是路径分隔证据（`range\(ndigits\)` 豁免）；
  - 含换行/缩进的多行文本（here-string 源码）不像单一路径，可加长度/行数上限（如 >2 行或 >260 字符的段跳过——NTFS 路径上限 260 本身就是依据）。
- **裸 token 路去重**：裸 token 提取前先把全部引号段从命令串中移除（引号内容只由引号路负责，不重复流入裸 token 路）——消灭「range\、ndigits\」残片。
- 这两处只影响 scope 守卫的**输入 token 集**，不触碰放行/弹卡逻辑本身（fail-closed 方向不变：不确定的照旧命中）。

**路线 A'（建议同做）：只读命令豁免 scope reason（语义修正——scope 管写不管读）**

- 命令的**每个管道段**的首 token 均在只读 cmdlet 白名单（`Select-String`、`Get-Content`、`Get-ChildItem`、`Get-Item`、`Test-Path`、`Measure-Object`、`Where-Object`、`Sort-Object`、`Compare-Object`、`Format-*`、`Out-Default`、`Out-String`、`Out-Host`…）且命令不含**写形态**（`>`、`>>` 重定向；`Out-File`、`Set-Content`、`Add-Content`、`Tee-Object`、`Export-*`、`New-Item`、`Copy-Item`、`Move-Item`、`Remove-Item`、`Rename-*`、`Set-Item`…）→ 跳过 scope reason。
- **不豁免** `checkCommandAgainstWorkspace` 的「工作区外路径」reason（与普通会话同一安全面：`Select-String ..\..\secret` 照弹）。
- **不可豁免**任意代码执行器（`python`/`node`/`pwsh`/`cmd`/`npx`…）——它们可写，只读性无法静态判定；卡 B 的 reason1 靠路线 A 消灭（源码不再被当路径），python.exe 绝对路径的 reason2 属 B 类（下述）。
- 白名单维护在 workspace.ts（与两个 check 函数同处）；写成常量表 + 单测锁行为。

**B 类（解释器绝对路径 reason2）——两个选项，默认建议 ①**：

1. **不动守卫，引导行为**：提示词/排错文档注明「调用解释器用 PATH 短名（python/node），别写绝对路径」——绝对路径引用工作区外程序是既有守卫的合理提示面（执行任意 exe 属敏感操作），普通会话同语义。
2. 窄白名单：绝对路径指向常见解释器（python.exe/node.exe/pwsh.exe）时豁免「工作区外路径」reason。放松面：路径拼接执行恶意同名 exe 的提示会少一层。若用户明确要 2 再做。

**红线**：审批 fail-closed 不破（路线 A 只修输入精度；A' 缩小的是 scope reason 触发面，写路径仍有文件三工具硬拒 + 沙箱 + 既有工作区外守卫三层把关）；普通会话零变化（`pathHintsOutsideScope` 仅被 `ctx.writeScope` 消费，普通会话无 scope 直接返回空）。

### 1.4 测试与验收

- 单测（workspace.test.ts 新区）：用**本文档 §1.1 的两条实弹命令**做回归用例——卡 A 命中集为空（scripts/e5_highprec.py 在 scope 内）；卡 B 的 scope 命中集不含 python 源码段；同时保留正报用例（`python x.py ..\outside`、`Get-Content ..\x`、重定向 `>` 到区外、`Out-File` 区外、正则外仍引用真区外路径）。
- A' 单测：`Select-String -Path 区外相对路径` 仍弹（工作区外 reason 交给既有守卫）？——注意：`Select-String ..\..\x` 的工作区外路径由 `checkCommandAgainstWorkspace` 弹，scope 豁免不影响它；`Select-String 区内scope外.txt` 豁免后不弹（只读、区内——预期）；`Get-Content 区外.txt > out.txt` 不豁免（含重定向写形态）。
- pwsh.test.ts：scope 强制弹卡的既有用例保持（误报修掉、正报不动）。
- 冒烟/真机：协调者派「计算 e^5」类任务全流程零弹卡；`普通会话` 行为字节不变。

## 2. W2：协调者运行中持续对话 + 子代理暂停/恢复（架构级增强）

### 2.1 需求拆解（用户原话 → 五点）

1. 协调者 busy（worker 运行中）时，用户仍可发消息，**不影响子代理运行**；
2. 消息按时间先后交错处理：「我输入信息后先处理我的，子代理返回信息就处理子代理的」；
3. 用户可让**协调者主动暂停**某个子代理（模型决策）；
4. 用户可**手动暂停**某个子代理（UI 操作）；
5. 子代理**完成或被暂停时，协调者收到相关信息**（通知语义）。

### 2.2 结构事实（现状约束，先读这个）

- **busy 即 409**：`/api/chat`（`src/modules/web-sessions/index.ts`）对 busy 会话回 409「请等待完成或先停止」——docs/4 既有语义（防轮中变更撕裂状态），docs/6 P1 时明确保留。W2 要求至少对 `kind=coordinator` 放开。
- **前端 busy=停止按钮**：`applyState` 里 `sendBtn.textContent = busy ? "⏹ 停止" : "发送"`，`send()` busy 分支直接 POST `/api/stop`。放开后协调者会话的「发送」与「停止」语义需要分离（普通会话保持现状）。
- **单轮机器**：`startTurn`（`src/web/session-lifecycle.ts`）置 busy/abortCtl/turnInfo → `agent.run` → finally 收尾。一轮 = 一次 agent.run。
- **agent_tasks 是阻塞工具**：`Promise.all(reqs.map(svc.run))`（`src/modules/tools/agent-task/agent-task.ts`）——协调者的 LLM 请求悬在工具 await 上，全部 worker 完成才返回合并报告。「运行中让协调者先回应用户」意味着要在 agent.run 挂起期间给它新输入。
- **history 是活引用、每轮重取快照**：`Agent.run` 循环里 `provider.chat({ messages: [...this.history] })`——**在工具执行期间向 `rt.agent` 的 history push 一条 user 消息，下一次 LLM 请求自然携带**（这是 L2 的技术支点）。协议上 assistant(tool_calls) → tool → user 的序列 OpenAI/anthropic 均合法。**但顺序约束**：tool 消息必须紧跟 tool_calls 回填，用户消息只能落在其后——「先处理我的」只能近似为「同一次后续请求内同时可见（工具结果在前、用户消息在后）」，无法把用户消息插到工具结果之前。
- **ml 锚点坑（L2 最大风险点）**：`turnInfo.ml` 与 delta/tool 事件的 `ml` 都是「发出时 history 长度」；前端 `switchSession` 缓冲过滤是 `x.d.ml >= msgs.length`。**中途 push user 消息会推高后续事件 ml**，切走再切回时的重放对齐需要重新设计（候选：注入消息走独立渲染路径、或注入后广播一次 init 快照、或给注入消息打标记让前端单独渲染不入 ml 流）。动手前先定方案。
- **compaction 竞争**：注入发生在 `compact()` 的 await summarize 期间会写进被替换的旧数组而丢失（compact 结束时 `this.history = [sys, summary, ...]` 整体替换）——需要协调（如注入前检查压缩进行中/注入函数持有一个互斥位）。
- **worker 登记面**：`rt.workers: Set<Promise<SubagentResult>>` 只有 Promise，**没有 subId/name → 控制句柄的映射**——暂停/恢复需要新增登记结构（如 `rt.activeSubagents: Map<number, { name, gate }> `，runWorker spawned 时登记、finishSubagent 注销）。
- **前端通知面已存在**：SSE `subagent` 事件（spawned/tool/toolResult/done/error + transcript）与时间线行（docs/6 P3 方案 B）——需求 5 的「用户侧收到信息」已满足；缺的是「协调者模型侧收到」与「暂停态」。
- **协调者 registry「仅两件」断言遍布**：smoke-subagent / smoke-sa2 / smoke-sa3 / smoke-sa4 与 session-runtime 单测都断言 `agent_task,agent_tasks` 两件（docs/5 偏差 18 先例）——若给协调者加 pause/resume 工具，**这些断言要全部同步**。

### 2.3 方案分层（建议按层实施，L1 先行验收后再做 L2；S 可独立并行）

**L1：busy 期消息排队（最小可用，零架构风险）**

- `/api/chat`：`kind=coordinator && busy` → 不再 409，消息 push 进 `rt.inbox: string[]`（新字段，瞬态不入档），广播确认（前端本地已渲染 user 气泡则只需防止重复）。
- `startTurn` finally：轮结束后若 `inbox` 非空 → `shift()` 一条递归 `startTurn`（注意重入安全：先清 busy/turnInfo 再开新轮，或抽 `runNext` 函数；广播顺序别让前端看到 busy 闪烁——可接受短暂状态切换）。
- 前端：协调者会话 busy 时输入框保持可用（placeholder 改「运行中，消息将在当前任务后处理…」），发送按钮不再变停止——**停止入口改为输入框旁独立 ⏹ 按钮或 `/stop` 命令（协调者会话专属 UI；普通会话维持现状）**。
- 语义边界（文档明示给用户）：用户消息在**当前轮（含全部 worker + 协调者总结）完成后**才被处理——不是「先处理我的」。这一层解决「能一直对话、不丢话」。

**L2：消息即时注入（近似「先处理我的」）**

- busy 时（协调者）用户消息即时 push 进 `rt.agent` 的 history（user role），下一次 LLM 请求携带。发送即时性达成；顺序语义为「工具结果在前、用户消息紧随，同一次请求可见」。
- 需先解决 §2.2 的 ml 锚点与 compaction 竞争两个坑（建议：注入走服务端广播 `init` 快照重渲染，或注入消息附特殊 SSE 事件让前端定点渲染——新增事件名需同步 core/events.ts + index.html + contract.test 三端）。
- L1 的 inbox 与 L2 可共存：L2 注入失败/不适用（如恰好压缩中）时落回 inbox。

**S：子代理暂停/恢复（推荐「轮边界挂起」语义）**

- **语义**：暂停 = 该 worker 在**下一个 LLM 轮/工具调用派发前**挂起等待（正在执行的工具跑完——pwsh 进程不中断；正在等的 LLM 请求也跑完）。恢复 = 放行继续。不做进程级挂起（Windows suspend 深水区，不做）。
- **机制**：`AgentDeps` 加可选 `pauseGate?: () => Promise<void>`（或传入一个可外部 resolve 的控制器）；`Agent.run` 循环每轮开始处 `await this.deps.pauseGate?.()`。`runWorker` 为每个 worker 建 gate，登记进 `rt.activeSubagents: Map<subId, { name, paused, gate }> `。暂停中的 worker **仍占并发槽**（subagentMaxConcurrent 语义：在跑=占槽，写进文档口径）；超时 `timeoutMs` 计时不因暂停暂停（挂起也算运行时长——简单且防永久挂起占用；文档明示）。
- **手动入口**：前端时间线行（`.subs-line`）加 ⏸/▶ 按钮 → `POST /api/subagent/control`（body: sessionId/subId/action）——web-sessions 模块新路由（server.ts 零改动）。SSE 新 phase `"paused"`/`"resumed"`（phase 扩值先例：docs/6 P3-B 的 tool/toolResult）。
- **协调者主动入口**：新系统工具 `pause_subagent` / `resume_subagent`（audience=coordinator，按 name 或 subId 匹配 `rt.activeSubagents`；协调者怎么知道 subId——见坑：派发时序号在 svc 内部生成，工具阻塞拿不到；**按 name 匹配**最简单，name 在 agent_tasks 参数里协调者自己指定过）。**注意**：加这两个工具 = 协调者 registry 变四件 → 同步更新 smoke-subagent/sa2/sa3/sa4 与 session-runtime 单测的「仅两件」断言（docs/5 偏差 18 先例）+ docs/5 D1 口径修订。
- **需求 5「协调者收到信息」**：a) 用户侧已有（SSE 事件+时间线）；b) 模型侧候选——正常完成不注入（结果随 agent_tasks 批量返回，避免每 worker 完成都打扰协调者上下文）；**暂停/恢复动作**发生时若 L2 通道存在可注入一条轻量 user 提示（「[系统通知] 子代理 x 已被暂停/恢复」）；只有 L1 时等轮结束自然可见。选型写进实施记录。

**红线（W2）**：普通会话的 /api/chat 409 与「busy=停止按钮」语义不变（只对 coordinator 放开）；SSE 事件名新增走契约三端同步；server.ts ≤250 行；withOther 六类守恒（暂停期间 usage 照常最终聚合）；存档向后兼容（inbox/gate/activeSubagents 均瞬态不入档——重启即失效，worker 本就不跨重启存活，文档口径写明）；系统提示逐字节确定（新工具只进 coordinator registry，普通会话字节不变）；审批/沙箱 fail-closed 不动。

### 2.4 测试与验收

- L1 单测：busy 协调者 POST /api/chat 返回 202 且消息入队不中断当前轮；轮结束自动依次处理队列（多条按序）；普通会话 busy 仍 409。
- L2 单测：注入后下一次 provider.chat 的 messages 含该 user 消息且位于 tool 消息之后；compaction 进行中注入不丢（落回 inbox）；前端 ml 重放方案whatever选定后配契约/浏览器端到端。
- S 单测：pause 后 worker 停在轮边界（LLM 调用计数不再增长）、resume 后继续并正常交报告；暂停中仍占并发槽（第 4 个并发任务仍被拒）；timeoutMs 到点仍收尾 error；pause_subagent 按 name 匹配；协调者 registry 断言更新为四件。
- 冒烟：smoke-sa3/sa4 加「暂停→恢复→完成」场景（进程内桩 LLM，零 token）；真机：协调者跑长任务 → 中途发消息得到回应 → ⏸ 一个 worker → ▶ 恢复 → 完成通知可见。

## 3. 建议实施顺序与总验收

1. **W1 路线 A + A'**（独立、低风险、用户体验立竿见影）——先修先测；
2. **W2-L1**（busy 排队 + 前端发送/停止分离）——验收后再评估 L2 的 ml 重放方案；
3. **W2-S**（暂停/恢复，可与 L1 并行）；
4. **W2-L2**（即时注入，坑最多放最后）；
5. 每步 `npm run typecheck` + `npm test` 全绿 + 冒烟（smoke:subagent / smoke:sa2 / smoke:sa3 / smoke:sa4 全过；动了协调者工具集记得同步四个脚本的「registry 仅 N 件」断言）；真机冒烟用隔离 USERPROFILE + 临时端口 + `scripts/e2e-sa4-stub-llm.mjs` 桩 LLM 零 token 复刻（docs/6 先例）。
6. 总验收清单：①「计算 e^5」类任务全程零弹卡（含 Select-String/正则/python here-string）；②写区外/重定向/删除类照弹（fail-closed 不破）；③协调者运行中可对话且 worker 不受影响；④⏸/▶ 手动与 pause_subagent 工具双入口可用；⑤完成/暂停均有通知；⑥普通会话行为零变化；⑦测试全绿、server.ts 仍 ≤250 行。
