# 交接文档 18：暂停/恢复机制退役（打断即终结）+ 自动送达消息摘要渲染

日期：2026-11-14 ｜ 状态：已实施（全量 368/368 测试过，4 个冒烟脚本全过，typecheck 干净）

## 0. 需求（用户原话拆解）

> 子代理暂停后站着一个空位而不结束，一次性的也无法归档，所以暂停就直接打断归档，不要给恢复机会，就不要搞恢复这个机制了，若是复用的子代理，也是直接打断，后续只能给它发送新提示词继续任务，相关系统提示词等等要一并修改。
> 另外子代理完成任务后返回给协调者，若换个对话再换回来，子代理的返回内容会全输出在对话界面的蓝色对话框里，我不要显示这么多，只要显示简单的哪个子代理是否成功返回或者暂停或者其他情况。

| 项 | 定案 |
|---|---|
| W1 语义 | 暂停/恢复机制**整体退役**（挂起占并发槽、无法归档的反直觉行为删除）。打断（stop）= 立即中止当前任务（请求/工具/排队审批一并取消）→ 任务**随即结算**：一次性子代理归档收尾；可复用子代理**转 idle 待命**（保留全部上下文），继续工作只能经 `agent_followup` 发新任务书——没有「恢复」，被打断的任务不会自动续跑 |
| W1 工具 | `pause_subagent` / `resume_subagent` 两件删除，新增 `stop_subagent` 一件（registry 五件→四件：agent_task / agent_followup / stop_subagent / archive_subagent）；名字必须改——「暂停」概念不复存在，保留旧名会误导模型 |
| W1 送达 | 打断结算的失败报告**不送达**（SubagentResult.stopped 标记；UI 路径有状态通知、工具路径有返回文案，再送失败报告=一次操作两条消息）；审计记录/事件/用量照常 |
| W1 归因 | 独立文案「任务被用户停止（进行中的请求与工具执行已中止；没有恢复机制）」——与「归档中止」共用 ctl.abort 收尾链，靠 ws.stopRequested 标记区分（优先级：归档请求 > 用户停止 > 外部中止 > 超时 > 异常 > 空回复） |
| W1 标记层级 | stopRequested 放 **ws 级**（非 cur 级）——覆盖装配窗口与任务间隙的打断：runOneTask 开始时消费（任务未开始即结算），收尾时归因后重置（不影响后续 followup 任务） |

| W2 渲染 | 自动送达消息（[子代理任务报告/状态 · 自动送达]）在用户气泡里**默认只显示一行摘要**：报告取正文首行（`[子代理 X 完成/失败] stats` 本身就是摘要），状态通知截到首个句读；完成=绿 ✓ / 失败=红 ✗ 着色；点击「展开全文」看报告详情（[[过程档案#N]] 链接展开后可点）。刷新/切回重渲染同路径（renderHistory → userBubble 单一出口） |

## 2. 关键决策与理由

- **打断 = ctl.abort 而非独立打断信号**：docs/7 的 interruptSignal/pauseCtl 存在的目的是「打断但**不结算**（挂闸门等恢复）」；打断即终结后这个目的消失——直接 abort 任务 ctl，与归档中止/外部中止共用一条久经测试的收尾链（审批队列快速排空、请求/工具取消、收尾不悬空），删码量远大于加码量。
- **打断报告不送达**：用户上一轮抱怨的「一个操作两次返回信息」模式不能在新语义里重演。状态通知（UI 路径）与工具返回文案（模型路径）已覆盖同一信息；失败报告的增量价值只有 transcript 链接与用量，不值得协调者多开一轮。归档中止报告**照常送达**（docs/11 W1 语义不变——那是模型自己发起的动作）。
- **stopRequested 放 ws 级**：cur 级标记会漏「派发后、runOneTask 开始前」的打断（装配窗口/任务间隙），用户按了 ⏹ 却照跑任务是最刺眼的违背直觉行为。runOneTask 开始时消费重置，后续 followup 不受污染。
- **工具改名 stop_subagent 而非保留 pause 名**：概念整体退役后名字不能撒谎；改名成本（golden/断言/冒烟）一次性付清。
