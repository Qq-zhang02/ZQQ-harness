# 33 · 开发文档——图片附件内容寻址存储（DSH 对齐）

> 状态：**已实施**（2026-11-17，随 v0.3.7 发布；预检三件套全绿——typecheck 三段过 + npm test **495/495** + smoke:sa4 **11/11**；smoke-subagent/sa2/sa3 全过）。
> 来源：用户提出「图片字节只在本地存一份，对话记录只保存内容寻址引用」（参考 DeepSeek harness/DSH 的做法）——本轮会话档此前把整段 base64 嵌在 `sessions/<id>.json` 里（base64 膨胀 ~37%，会话档随图片数量线性膨胀）。

## §0 设计（DSH 对齐部分）

| 环节 | 做法 |
|---|---|
| 存储位置 | `<userDir>/attachments/v1/objects/<sha256 前2位>/<sha256>`——扇区目录防单目录膨胀（DSH 同款布局） |
| 内容寻址 | 引用 = 文件字节（base64 解码后）的 sha256 hex；不可变（同引用内容恒定） |
| 去重 | `put` 先哈希、`existsSync` 命中即跳过——**相同字节全局只存一份**（跨会话、跨消息、压缩备份都指向同一文件） |
| 清理策略 | **永不自动删除**（DSH 同款）——不随会话删除/回收站清空/cleanSpill 清理 |
| 会话档形态 | user 消息 `images: [{ mime, data(base64) }]` → 落盘档 `[{ mime, ref }]`（`StoredImage`）；压缩前备份（`*.precompact-*.json`）同口径转引用 |
| 读回校验 | 恢复时读文件重算 sha256 与引用比对：不符（被改/截断/损坏）→ 视同丢失 |
| 旧档兼容 | 旧档内联 `data` 原样透传（不做一次性迁移——未重存档的旧会话保持原样，重存档时才转引用） |
| 变换边界 | **内存形态不变**（`ChatMessage.images` 仍 {mime, data}——提供方/前端/用量估算/上下文估算零改动）；引用只存在于两个边界函数：`toStoredMessages`（persistSession / bindWorkspace / newSessionForView 存档 + 压缩备份）与 `restoreStoredMessages`（createRuntime 从磁盘回读） |

实现：`src/web/attachments.ts`（`AttachmentStore` + 两个变换函数，纯 node:crypto/fs 零新增依赖）；接线：`SessionShell.attachments`（server.ts 构造）→ toSessionData 三调用点 + compaction backup + createRuntime 恢复；userdir 布局加 `attachments` 键。

## §1 与 DSH 的偏差（不采部分，理由）

| DSH 行为 | 本仓库取舍 | 原因 |
|---|---|---|
| 准入重编码：EXIF 剥离/去元数据/色彩配置、总像素 2048×2048、长边 ≤8192、≤4 MiB、alpha→WebP 否则 JPEG 85/75/60 质量阶梯 | **不采**——字节原样落库 | Node 标准库解不了 JPEG/PNG，重编码要引 sharp/jimp 原生依赖，破「零原生依赖」边界；准入沿用既有 IMAGE_RULES（≤4 张、单张 ≤5MB、PNG/JPEG/GIF/WEBP，docs/10 R3） |
| 读回校验失败**明确报错** | **降级**：丢图 + 消息尾部 `[附件丢失：N 张图片（sha256=前12位…）——附件库中缺失或校验不符]` 标注 | 恢复路径硬报错会把整个会话变砖（切不开/开轮失败）；标注对模型可见可向用户转述。实现教训：降级分支必须**显式覆盖 `images` 字段**——`{...m}` 展开会把落盘档的引用形态数组带回来（全丢时置 undefined，JSON 序列化即省略） |
| 单消息 20 张/50MiB/200MiB/64MP 像素预算 | **沿用既有 IMAGE_RULES** | 上限是产品取舍不是存储层职责；要放宽走 IMAGE_RULES 单点 |
| DeepSeek Files API：首传拿 file id、后续轮复用 | **不采** | 我们的提供方走 OpenAI 兼容 chat completions（base64 数据块），无 Files API 抽象；内存形态仍是 base64，每轮照旧重放——本仓库只解决「本地一份 + 档不膨胀」 |
| append-only 会话日志（session 事件流） | **不采**——沿用既有「每轮结束整体覆写会话 JSON」 | 存档形态差异是全项目架构级决策，不在本轮范围 |

## §2 实施与测试

- `AttachmentStore.put/resolve`：幂等去重写入 / sha256 校验读出（非法引用形状直接 null，防路径穿越）。
- `toStoredMessages/restoreStoredMessages`：引用往返幂等；旧档 `data` 透传；丢失降级标注。
- 接线回归：`SessionShell.attachments`（server.ts + 4 个冒烟脚本的 shell 字面量各 +1 行）；`makeShell` 测试桩（session-runtime.test / subagents.test）补字段。
- 新测试 `src/web/attachments.test.ts`（4 用例）：往返、同字节去重（同引用 + 盘上单文件 + 落盘为解码后字节）、篡改/缺失/非法引用拒绝、往返/兼容/降级（全丢清空 images + 标注含引用前缀；部分丢失存活保留）。
- 哨兵调整：server.ts 行数 278→**282**（接线 +3 行：import/const/字段；contract.test + smoke-sa4 两处同步）。
- 已知边界：附件库无 GC（磁盘只增，清理 = 手动删 `attachments/`，丢失由降级标注兜底）；read_archive 读主对话档只统计图片张数不解码，引用/内联形态都不受影响。

## §3 真机验收指引

1. 贴图发消息 → `~/.ZQQ-harness/attachments/v1/objects/` 出现 `<前2位>/<sha256>` 文件；`sessions/<id>.json` 里对应消息 `images` 是 `{"mime":"image/png","ref":"<64 hex>"}` 且**不含** base64 长串。
2. 同一张图再发一次（新会话或同会话）→ objects 下文件数不变（去重）。
3. 重启/切走再切回 → 图片正常显示（引用解析）。
4. 手动删掉 objects 下某文件后重启该会话 → 消息显示「附件丢失」标注、会话可用。
