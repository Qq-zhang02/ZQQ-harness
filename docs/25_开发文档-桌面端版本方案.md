## 0. 结论摘要（一页版）

| 问题 | 结论 |
|---|---|
| 桌面版选什么技术 | **Electron 薄壳**（§3 方案 A）：主进程只管"起服务进程 + 开窗口 + 管生命周期"，渲染进程直接 `loadURL("http://127.0.0.1:<动态端口>")`——**前端、core/modules/web 三层业务代码零改动** |
| 为什么不是 Tauri | 小体积的代价是 Rust 工具链 + Node sidecar 双运行时 + SEA/pkg 对 koffi 原生模块的支持困境（Node SEA 不支持原生插件），单人维护成本高于收益（§3 方案 B） |
| 业务层要不要改 | 要，但只有 DT0 三小项（§5）：**默认绑定 127.0.0.1**（当前 `server.listen(PORT)` 绑 0.0.0.0，局域网可达——无论是否桌面化都该收口）、**动态端口 + READY 握手行**、**优雅停机**。浏览器模式同步受益 |
| 分几步走 | DT0 服务端就绪化（半天）→ DT1 壳落地（1 天）→ DT2 打包分发（1 天）→ DT3 可选增强（托盘/自启/通知，按需）。每步独立验收、独立 commit（§6） |
| 怎么保证不伤维护性 | 四条铁律（§8）：壳 ≤2 文件且禁止业务逻辑进主进程；`npm run web` 浏览器双入口永远保留并保持行为零漂移；Electron 升级核对单；壳不进 `npm test`（打包后手工冒烟清单 + 复用零 token 桩 LLM） |
| 现在就要动手吗 | 不必。L0（现状 `start-zqq.bat` + 浏览器）已可用；L1（Edge 应用模式快捷方式，§3 末）花半天可得 80% 桌面观感。L2（Electron）在需要"关窗即退/单实例/安装卸载/托盘通知"时再启动 |

- **① 无 CI**：无 `.github/workflows`。测试与类型检查是纯本机纪律。建议（独立小任务，与桌面版无依赖）：GitHub Actions `windows-latest` 跑 `npm run typecheck && npm test`（koffi/沙箱测试需 Windows runner，恰好匹配）；不想用云端也可本机计划任务每日跑。**收益**：防止"本地忘了跑测试就 commit"。
- **② 服务绑定面**：`server.ts` 的 `server.listen(PORT)` 未指定 host = 绑定 `::`/`0.0.0.0`。桌面版天然要求只听本机；浏览器模式也不该默认对局域网开放（Windows 防火墙可能拦，但私有网络下可能放行）。修法见 §5 DT0-1。
- **③ config.ts 848 行**：rules/schema/解析/校验/常量/重绑同居一文件——这是"单一出处"纪律的合理代价（拆开反而制造多出处风险），暂不动；若后续键数明显增长（如 >50），再评估把 `THRESHOLD_RULES`/`thresholdSchema` 拆为 `config-schema.ts`（纯移动，哨兵同步）。
- **④ agent.ts 708 行**：主循环/interim 旁路/压缩/用量锚定四职责尚内聚，但 interim ~150 行与主循环的时序耦合（toolPending 窗口/合并点/在飞等待）是全项目复杂度最高的局部——**改动前必读 docs/8 §1.4 坑清单**，不建议顺手重构。
- **⑤ 运行态常驻内存**（README 已知限制）：会话运行态不淘汰。桌面版长驻使用（开机自启 + 常开）会放大该特性——会话多时内存可观。桌面版不改此设计（会话存档在每轮落盘，重启无损），但 DT3 托盘常驻默认**关闭**，见 §6。

## 2. 桌面版目标与非目标

**目标**（用户可感知）：

1. 独立窗口应用：无浏览器地址栏/标签页，任务栏与开始菜单有入口，桌面快捷方式。
2. **关闭窗口 = 干净退出**：服务进程、MCP 子进程、沙箱临时目录清理全部跟随（现状 bat 关窗后 node 服务可能残留）。
3. 单实例：二次启动聚焦已有窗口（现状重复 bat 会撞端口退出）。
4. 安装/卸载体验（NSIS 安装器或便携版单目录）。
5. 可选增强（DT3）：系统通知（审批卡到达）、开机自启、托盘常驻。

**非目标**（明确不做，防 scope creep）：

- 不做离线/便携多用户：用户数据仍在 `~/.ZQQ-harness/`（单用户单机假设不变）。
- 不做跨平台：项目本就 Windows-first（pwsh 7、Windows 受限令牌沙箱、koffi FFI）；macOS/Linux 桌面化不在本方案范围。
- 不改前端为 SPA 框架/不引构建链：渲染进程就是现有单文件页面（"无构建单文件"是 docs/21 §5 不变量 6，桌面化不得触碰）。
- 不把桌面壳做成第二个业务层：壳只做进程与窗口生命周期（§8 铁律 1）。

## 3. 技术选型

### 3.1 候选对比

| | A. Electron 薄壳（**推荐**） | B. Tauri v2 + Node sidecar | C. WebView2 极简壳（.NET） | C'. SEA/pkg + Edge 应用模式 |
|---|---|---|---|---|
| 形态 | 主进程（Node）spawn 服务子进程 + BrowserWindow 加载 `http://127.0.0.1:<port>` | Rust 壳 + WebView2 + 打包 node.exe 跑服务 | WinForms/WPF + WebView2 控件 + spawn node | 服务端编译单 exe + `msedge --app=` 开窗 |
| 业务代码改动 | DT0 三小项（§5） | 同 DT0 + sidecar 打包配置 | 同 DT0 + spawn 逻辑 | 大（编译/打包） |
| koffi（N-API 原生模块） | ✅ 子进程 = Electron 自带 Node（N-API ABI 稳定，无需 rebuild；且 koffi 只在服务子进程加载，主进程零原生依赖） | ⚠️ sidecar 必须是真 Node——Node **SEA 不支持原生插件**；pkg 已半废弃 | ✅ spawn 外部 node（用户机需装 Node 或随包分发） | ❌ SEA 不支持 koffi；pkg 对 N-API 支持不稳 |
| TS 直接运行（type-stripping） | ✅ Electron ≥38 内置 Node ≥22.18（免 flag） | ✅ sidecar 是完整 Node | ✅ 外部 Node | ⚠️ 单文件化与源码形态冲突 |
| 体积（安装后/分发） | ~220MB / ~100MB | ~10–20MB / ~15MB（含 node.exe ~80MB 实际更高） | ~1–5MB 壳（self-contained .NET ~70MB） | ~90MB exe |
| 内存 | ~180–280MB（含 Chromium） | ~100–160MB（WebView2 系统.runtime） | 同 Tauri 量级 | ~120MB（Edge 现成） |
| 维护栈 | TS/JS 一种语言；Electron + electron-builder 两个 devDeps | Rust + TS 双语言、双工具链 | C# + TS 双语言 | Node 单文件化黑盒 |
| 关窗即退/单实例/托盘/通知 | 全部内建 API | 全部内建（Rust 侧） | 全部可做（自己写） | ❌ 关窗不知会服务；无单实例 |

### 3.2 结论与理由

**推荐方案 A（Electron 薄壳）**，决定性理由按权重排序：

1. **koffi 与 type-stripping 双约束下唯一"零妥协"路径**：服务子进程用 `ELECTRON_RUN_AS_NODE=1` 直接以 Electron 自带 Node 跑现有 TS 源码——不打包、不编译、不改 import，`npm test`/`npm run web` 与桌面版共享同一份代码。
2. **单人维护语言成本最低**：壳 ~150 行纯 JS（§4），无第二语言；Electron 社区文档量最大，排障检索成本最低。
3. **体积与内存劣势可接受**：这是本地工具，不是分发软件；磁盘 220MB 与常驻 200MB 在目标机器（开发工作站）不构成问题。

**否决记录**：B 否决于"双运行时 + SEA 原生插件死路"（要保 koffi 就必须分发完整 node.exe，体积优势蒸发，还多出 Rust 工具链）；C 否决于双语言维护与 .NET 运行时分发；C' 否决于窗口生命周期不可控（关窗残留服务——恰是桌面版要解决的核心问题），但保留其**精神**作为 L1（见下）。

**分级路线（按投入从零到全）**：

- **L0 = 现状**：`start-zqq.bat` + 系统默认浏览器。零投入，已在用。
- **L1 = Edge 应用模式**（半天，可先行）：bat/快捷方式改开 `msedge --app=http://localhost:8787 --window-size=1400,900`——独立窗口无地址栏，观感≈桌面应用。**局限**：关窗不退服务、无单实例。适合作为 DT2 完成前的过渡，不取代 L2。
- **L2 = Electron 薄壳**（本文档主体，DT0–DT3）。

## 4. 目标架构（方案 A）

### 4.1 进程模型

```
┌─ Electron 主进程 desktop/main.mjs（~150 行，纯 JS，零业务）───────────┐
│  app.whenReady()                                                      │
│  ├─ 单实例锁 app.requestSingleInstanceLock()（失败→聚焦已有窗口并退出）│
│  ├─ spawn(electronExe, ["src/web/server.ts"], {                      │
│  │     env: { ...process.env, ELECTRON_RUN_AS_NODE: "1",              │
│  │             PORT: "0", ZQQ_NO_BROWSER: "1", ZQQ_HOST: "127.0.0.1"},│
│  │     stdio: ["pipe","pipe","pipe"] })                               │
│  │   └─ 逐行读 stdout，解析 READY 握手行 "ZQQ-READY {port}"（§5 DT0-2）│
│  ├─ new BrowserWindow() → loadURL(`http://127.0.0.1:${port}`)         │
│  │   （contextIsolation 默认开 / nodeIntegration 默认关；页面即现有    │
│  │    index.html，fetch/SSE 全同源，零改动）                           │
│  ├─ window-all-closed → 优雅停机（§5 DT0-3）→ app.quit()              │
│  └─ before-quit → 兜底 child.kill()（防服务未响应）                    │
└───────────────────────────────────────────────────────────────────────┘
        │ pipe（stdin/stdout 握手 + 父进程死亡感知）
┌─ 服务子进程（= 现有 src/web/server.ts 原样，ELECTRON_RUN_AS_NODE 下
│  就是纯 Node 22.18+ 运行时：initConfig → 装配 19 模块 → listen 127.0.0.1 随机端口）
│    ├─ Agent 循环 / 工具 / 审批 / 子代理（不变）
│    ├─ MCP 子进程们（stdio）——退出时 mcp.stop() 清理（已有）
│    └─ pwsh 沙箱执行（koffi N-API，在此进程加载；主进程无原生依赖）
└─ 渲染进程 = BrowserWindow 里的现有前端（不变，同一份 index.html）
```

**为什么子进程而非主进程内嵌 import**：崩溃隔离（服务异常不连带窗口进程死掉，可报错重启）、server.ts 保持"直接可跑"形态（`npm run web` 零重构）、stdio 握手是最少代码的端口协商。代价是多一层 IPC——但内容只有一行 READY 与 stdin 关闭信号，无协议设计成本。

**主进程刻意不做的事**：不 parse 会话数据、不碰 providers.json、不实现任何 /api——需要桌面行为（通知/自启）时走 DT3 的受控通道（§6），而不是在壳里另起业务。

### 4.2 关键决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 壳语言 | 纯 JS（desktop/main.mjs），不用 TS | 壳小且稳定；规避"Electron 主入口 .ts 加载"这一未经本项目验证的路径（Node type-stripping 对**子进程**模块加载是成立的，对 Electron 主入口则依赖其 ESM 加载细节——没必要赌） |
| 端口 | `PORT=0` 随机分配 + stdout 握手 | 消灭端口冲突（8787 被占是真实发生过的问题，server.ts 有专门报错）；同机多份也不打架 |
| 绑定 | 默认 `127.0.0.1`（新 env `ZQQ_HOST` 可覆盖回 `0.0.0.0`） | 安全收口（§1.2-②）；保留显式逃逸口给"局域网访问"旧用法并在 README 注明 |
| asar | **v1 直接 `asar: false`** | Electron 的 asar 虚拟文件系统对 `ELECTRON_RUN_AS_NODE` 子进程的 `.ts` 模块加载与 koffi DLL 定位均属"能跑但要验证"的灰色地带；本地工具无代码保密需求，plain files 最稳。后续要紧凑再开 asar + `asarUnpack` 并回归冒烟 |
| 通知 | 渲染进程 `Notification` API（Chromium） | `http://127.0.0.1` 是 secure context，通知可用——**零壳代码**；审批卡到达时前端自行弹（DT3 在 index.html 加 ~10 行，属前端演进不属壳） |
| 开机自启 | `app.setLoginItemSettings`（DT3） | Electron 内建，无注册表手写 |

## 5. DT0：服务端就绪化（业务层唯一改动，半天）

三项都是 `src/web/server.ts` 内的小改，**浏览器模式同步受益**，且各自独立可验收：

1. **DT0-1 默认绑定 127.0.0.1**：`server.listen(PORT, process.env.ZQQ_HOST ?? "127.0.0.1")`。README「快速开始」补一句"默认只监听本机；需局域网访问设 `ZQQ_HOST=0.0.0.0`（自担风险）"。**行为变化要在 commit message 里显著声明**。
2. **DT0-2 动态端口 + READY 握手**：支持 `PORT=0`；`server.listen` 回调里 `const actual = server.address().port`，向 stdout 打一行机器可读握手 `console.log("ZQQ-READY " + actual)`（再打印人类可读启动横幅）。壳按行解析该前缀；浏览器模式忽略此行无害。
3. **DT0-3 优雅停机**：新增 `shutdown()`：`server.close()` + 遍历 `shell.runtimes` 调既有持久化/`rt.mcp.stop()` + `process.exit(0)`。触发源两个：`SIGINT/SIGTERM`（`process.on` 注册；Windows 下 `child.kill()` 默认就是硬终止——所以主通道是下一条）与 **stdin 关闭**（`process.stdin.on("end", shutdown)`——父进程死亡/主动关闭管道时子进程收到 EOF，这是 spawn 模式标准的父死亡感知法）。硬杀兜底已天然存在：会话每轮结束自动落盘，最坏丢当前在飞轮。

验收：`PORT=0 ZQQ_NO_BROWSER=1 node src/web/server.ts` 输出 READY 行且随机端口可访问；`netstat` 确认只听 127.0.0.1；关掉父 shell（stdin EOF）后进程与 MCP 子进程在 ~1s 内消失（`tasklist` 查 node 无残留）。**注意**：server.ts 有 ≤250 行双哨兵（contract.test.ts），三小项预计 +15 行内，若触线则把"启动横幅打印"瘦身为函数或调整哨兵常量（哨兵意图是"防业务逻辑回流"，不是死数字——调整需在 commit 说明并保持双哨兵语义）。

## 7. 打包与分发要点（DT2 细则备忘）

- **koffi 无需 rebuild**：它是 N-API 插件（ABI 稳定），且只被服务**子进程**（纯 Node 语义）加载——不进 Electron 主进程，绕开一切 Electron 原生模块 ABI 话题。打包后在目标机首次启动冒烟必须包含一次 run_pwsh（验证 DLL 定位）。
- **node_modules 完整性**：koffi 平台包是 optionalDependencies 形态分发时，`electron-builder` 的 `npm rebuild`/install 步骤可能漏 optional——用 `--dir` 模式本地试打先验证；不行就锁死 win32 平台包为硬依赖。
- **TS 免编译的前提**：目标 Electron 的内置 Node ≥22.18（unflagged type-stripping）。**若未来 Electron 版本核查失败**（§8-3），唯一退路是打包期 `tsc --outDir dist` 预编译（仅打包产物走编译，开发态仍免构建——这是可接受的逃生门，不算破坏"无构建"约定）。
- **杀软误报**：未签名 NSIS + spawn 子进程模式可能被 SmartScreen/杀软盯上。缓解：portable 版先自用；个人使用量级不值得买代码签名证书（记录为已知取舍）。

## 8. 维护纪律与不变量（桌面版新增，任何改动不得破坏）

1. **壳不进业务**：`desktop/` 目录上限 2 个文件（main.mjs + 图标）、主进程不 import `src/**` 任何模块、不读写 `~/.ZQQ-harness/` 业务文件（desktop.json 除外）。建议哨兵：contract.test.ts 增"desktop/main.mjs 不含字符串 `../src/` import 与 `/api/`"（沿 P8 锁法，打包后可跑的静态断言）。
2. **双入口零漂移**：`npm run web`（浏览器）与桌面壳跑的是**同一份 server.ts**，DT0 改动对浏览器模式的行为变化只有"默认只听 127.0.0.1"一条（README 声明）。任何"只给桌面"的行为分支先问：能否做成服务端能力让两端共享？
3. **Electron 升级核对单**（升级 major 前逐项过）：①目标版本内置 Node ≥22.18（type-stripping，查 Electron releases）；②打包产物在干净机器冒烟（含 run_pwsh 沙箱、MCP stdio、图片上传）；③`electron-builder` 配套版本兼容。核对结果记进本文档头部实施记录。
4. **壳不进 `npm test`**：GUI 壳用打包后手工冒烟清单（§6 DT2）+ 复用 `scripts/e2e-*-stub.mjs` 桩（零 token）。DT0 的服务端改动照常进 `npm test`（READY 行/绑定 host 可单测）。
5. **docs 惯例延续**：每阶段实施在本文档头部补记录块；commit 一特性一条。

## 9. 风险清单与已知取舍

| 风险 | 评估 | 缓解 |
|---|---|---|
| Electron 内置 Node 版本不满足 type-stripping | 低（≥38 即满足；升级核对单 §8-3 拦截） | 逃生门：打包期 tsc 预编译（§7） |
