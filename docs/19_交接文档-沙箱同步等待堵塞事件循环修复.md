# 交接文档 19：沙箱执行器同步等待堵塞事件循环（子代理长命令全局卡死）修复

日期：2026-11-14 ｜ 状态：已实施（全量 368/368 测试过、typecheck 干净、专项冒烟修复前后对照通过；行为契约不变，测试零改动全过）

## 0. 需求（用户原话拆解）

> 派子代理后，点进去查看详情，很久不出内容（包括任务提示词），点击暂停也很容易反应很慢，很多其他操作反应（例如发新消息，点击进入新对话）都很慢，很久都没反应。我测试用的是让它派子代理进行 sleep 20s 的指令，这个很慢，但是一些其他指令例如写一个贪吃蛇小游戏，这个就一般不会这样。看看是什么情况，解决一下。

（注：用户口中的「暂停」即 docs/18 的 ⏹ 打断按钮——暂停/恢复机制已退役，本文一律称打断。）

| 项 | 定案 |
|---|---|
| 根因 | `windows-acl.ts` `run()` 的进程等待循环是 **async 函数里的纯同步 `for(;;)`**：`WaitForSingleObject(hProcess, 200)` 是同步 FFI 调用（每次堵住主线程 200ms），循环体内无任何 `await`——命令运行期间**整个服务进程的事件循环被堵死**。worker 与 Web 服务同进程（subagents.ts 直接 `new Agent`），所以全部会话的 HTTP/SSE、SSE 广播、打断用的 abort 定时器统统排不上队 |
| 症状分型 | 长命令（Start-Sleep 20s，沙箱默认 workspace-write 模式必走此路径）= 连续堵 20s，详情页/⏹/发消息/切会话全部无反应；短命令（贪吃蛇类任务几十条各几百 ms）只偶发顿挫不易察觉——注释谎称「异步轮询等待（不阻塞事件循环）」，实际从未异步 |
| 修复一：等待异步化 | `WaitForSingleObject(hProcess, 0)` 非阻塞探测 + 探测之间 `await setTimeout(200)` 让出事件循环；超时杀进程后的 5s 死等同步段同样改**有界异步轮询**（≤5s，超界放弃——finally 关 job 句柄仍有 KILL_ON_JOB_CLOSE 杀树兜底）。abort 检查照旧在每次探测前（打断生效延迟 ≤ 探测间隔 200ms） |
| 修复二：采集句柄泄漏 | 服务端自己的 `hOut`/`hErr`（输出采集文件句柄）从不关闭——既泄漏句柄，又一直占着 `out-*/err-*` 文件使 `rmSync(force 静默吞错)` 实际删不掉，沙箱 tmp 目录持续膨胀。现在 finally 里**先关句柄再删文件**（`INVALID_HANDLE` 常量收敛 CreateFileW 失败分支判断） |
| 附带效应 | 多子代理并行跑沙箱命令此前实际被堵死的事件循环**串行化（伪并行）**，现在真并行——与 docs/15 并行派发的语义对齐；`TMP/TEMP` 改→spawn→还原窗口仍为同步 FFI 段（无 await），并发安全论证不变 |
| 行为不变面 | timeoutMs 语义、Job Object 杀树、fail-closed、输出采集文件机制、SandboxRunner 接口签名均不变；非沙箱路径（danger-full-access 走 `runPwsh`，node spawn 事件驱动）本就不堵 |

## 1. 根因定位（机制链，供后来者复用）

1. 复现分型先行：同一入口「sleep 20s 卡死 / 贪吃蛇不卡」→ 差异只在**单条命令时长**，指向执行器内部的等待方式而非派发/送达/前端轮询链路。
2. `run_pwsh` 默认沙箱模式（workspace-write）→ `runSandboxed` → `WindowsAclRunner.run()`；read-only 同路径，仅 danger-full-access 绕过。
3. `async` 关键字只让函数**返回** Promise，函数体在首个 `await` 前仍是同步执行——该循环恰恰一个 `await` 都没有，`WaitForSingleObject(200)` 连续同步调用 = 事件循环 100% 占用。
4. 同进程放大：worker 的 Agent 实例、HTTP 服务、SSE 全在一个 Node 进程；事件循环一堵，**包括打断按钮在内的所有请求都无法被接受**——这就是「⏹ 点了没反应」的机制（对照实测：`setTimeout(600ms)` 触发的 abort 事件全程无法执行，子进程跑满 10s 自然结束、`interrupted=false`）。

## 2. 改动清单

1. **src/modules/sandbox/windows-acl/windows-acl.ts**（唯一代码改动文件）：
   - `run()` 等待循环重写：`pause(ms)` Promise 助手 + `WaitForSingleObject(hProcess, 0)` 探测 + 间隔让出；超时终止核改有界异步轮询（50ms 粒度）；注释如实重写并留档曾错的机制；

2. **README**：
   - 沙箱节补执行等待异步轮询与打断/超时 ≤200ms 生效、out/err 采集文件运行结束即删（§ 用户数据 tmp 描述同步）；

## 4. 遗留与建议

- 探测间隔 200ms/终结核 50ms 是就地常量，未进 harness.json 阈值表——打断/超时生效延迟 ≤200ms，如需更跟手可调小（代价是空转 FFI 次数增多）；现状够用，不注册。
- `src/sandbox/win.test.ts`（沙箱真实执行测试）未覆盖「事件循环不堵塞」维度；若要回归锁定，可按本篇 §3 的对照脚本思路补一例（运行中定时器漂移 <500ms + abort 快速生效），脚本可从表格复原。
- `readFileSync` 读采集文件（输出上限 1MB）与 grantWrite/GetNamedSecurityInfoW 等 FFI 仍是同步短操作（毫秒级），不构成卡顿源，维持现状；`spawnSync(where.exe)` 仅 findPwsh 首次调用（结果缓存），非热路径。
