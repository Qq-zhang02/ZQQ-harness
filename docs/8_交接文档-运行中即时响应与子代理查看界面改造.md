### 一、需求二排查结论（当前 HEAD 真机复现，2026-11-13）

复现手段：`scripts/e2e-dbg-switch-stub.mjs`（e2e-sa4 桩 + worker 应答延迟，新增的复现工具，保留在库）+ 隔离 USERPROFILE + 浏览器实操（协调者会话派 alpha/beta 两 worker → 运行中切走再切回 → 等完成 → DOM 级检查 + 存档检查）。

1. **症状 3（切回后运行中 worker 实时情况不可见）= 候选 3a 成立，且是确定性 bug（无需竞争条件）**：
   - 根因链：`switchSession` → `renderHistory` 末尾 `finishSegments()` 把 `curTool=null` 且 `toolBlocks.clear()`（index.html）→ 缓冲重放的 subagent 事件（**不带 ml，全量重放**）被 `onSubagent` 首行 `if (!curTool) return` 全部吞掉；切回后新到的实时 subagent 事件同样被吞（curTool 要到下一次 `addTool` 即协调者下一轮新工具调用才会再有，而正在跑的 agent_tasks 块已渲染过不会再设）。
   - 复现实证：切回后「▶ alpha / ▀beta」状态行 + ⏸ 按钮全部消失，工具块只剩「运行中⋯」+参数；worker 完成后的 done 事件也不可见；agent_tasks 结果以散文本渲染（toolBlocks 已清，`addToolRes` 找不到块）——但随即被轮末重渲染覆盖（见 2）。
   - **修法：并入需求三**（抽屉把 subagent 事件路由到独立容器，不依赖 curTool 挂载），**不打补丁**。
2. **症状 2「换一个对话再返回又可以了」= turnEnd 的 needsRefresh 快照机制**：`switchSession` 设 `c.needsRefresh = !!state.busy`，轮末 turnEnd handler 触发 `refreshSnapshot()` 全量重渲染（服务端历史），把丢的内容补齐。**运行中的轮不触发 turnEnd**，所以运行中切回必丢实时——这就是用户看到的差异。
3. **症状 1（完成后无法回看 + 输出格式不对劲）= 候选 1 成立（纯 UI 层级，数据未丢）**：回看入口在两层折叠之下（「🔧 执行过程」折叠组 → agent_tasks 工具块 collapsed → 内含 subs-line 时间线与结果 pre 里的「📄 过程」链接 ×2）；实时与快照两套呈现不一致（实时版有时间线/过程盒、快照版只有工具块）。复现实测：两层展开后内容完好（subs-line 在实时流里、📄 链接与 transcript 文件都在）。

## 1. 需求一（P0）：协调者运行中**即时响应**（W2-L2 正式版）

### 1.1 用户原话与语义定案

> 「我需要的不是新请求排队，而是及时响应，在子代理工作时，新请求直接带上历史上下文（子代理还没处理完，这部分不带）发给模型。」

语义拆解（对照 docs/7 §2.1 五点需求的第 2 点，用户现已定案）：

1. 协调者 busy 且 worker 运行中时，用户消息**立即**发给模型（带上当前全部历史上下文）并**立即得到回应**——不是等当前轮结束（W2-L1 的排队被用户明确否决为「不是我想要的」）；
2. 「子代理还没处理完，这部分不带」：请求里不包含未完成的子代理**结果**（本来也还没有）；
3. 回应及时可见（流式）；协调者后续轮次能「记得」这段运行中对话（进历史，不丢）；
4. W2-L1 的 inbox 不删除——降级为**兜底**（interim 路径不适用/失败时排队，轮末照旧排空）；
5. W2-S（暂停/恢复）与「完成/暂停通知」保持不变。

### 1.2 结构事实与协议约束（为什么不能直接 push user 消息）

先读 docs/7 §2.2（结构事实清单仍然全部有效），以下是 L2 专属的推导：

- **阻塞点**：`Agent.run`（src/agent.ts）的工具循环里 `await registry.executeWithMeta(call.name, ...)` —— agent_tasks 阻塞在这里（`Promise.all` 在模块内）。此时 history 尾部 = `assistant(tool_calls: [agent_tasks…])`，**没有对应的 tool 消息**。
- **协议硬约束**：OpenAI 与 Anthropic 都要求 tool 消息**紧跟** tool_calls 回填——`assistant(tool_calls) → user → tool` 是**非法序列**（API 400）。所以：**不能**把 user 消息直接 push 进 history（会插在未回填的 tool_calls 后面）；「立即发给模型」只能走**旁路请求**（请求里拼装、history 保持合法形状），回应**先缓冲、后合并**。
- **合并窗口的唯一安全点**：工具 for 循环结束后、`if (signal?.aborted)` 检查前（agent.ts 工具循环的紧后处）。理由：①此时本轮全部 tool 消息已 push（`registry.executeWithMeta` 内部捕获工具异常、中止也返回错误文本，tool 消息**必然**被 push——这是既有行为，合并依赖它）；②此后下一轮 `provider.chat({ messages: [...this.history] })` 自然携带；③中止路径也走到这里（merge 后才 return null），缓冲不丢。**注意**：合并必须等本轮**全部** tool 消息 push 完（一轮可能有多个并行 toolCalls，逐个 await）——不能在单个 tool push 后就插 user/assistant（会把 tool 消息隔断，非法）。
- **压缩（compaction）竞争已被结构排除**：compact 只在三处发生——startTurn 的 pressure 检查（run 之前）、run 内 overflow 重试（轮与轮之间，此时本轮工具已回填+合并完毕）、手动 /api/compact（busy 409 拒绝）。只要 interim 只在「工具等待窗口」接受（见 toolPending 标志），就与 compact 无交集。**这是设计不变量，别破坏**。
- **前端 ml 锚点**：实时事件带 `ml = rt.agent.messages.length`（makeUi）。interim 回应**未合并前不在 history**，流式期间 ml 恒为 H_len；合并后 history 一次性 +（1+2k）条。切走再切回的过滤 `x.d.ml >= msgs.length`（index.html switchSession）在「合并前切回」与「合并后切回」两个时点都自洽（docs/7 §2.2 的坑可以用「合并后广播 init 快照」一并消除，见方案）。
- **既有先例可复用**：收尾轮（maxToolRounds 耗尽后的最终请求）就是「不带 tools 的一次 chat」——interim 请求同款形态；usage 走 `printUsage + withOther` 同款；`requestApprovalFor` 的 `rt.approvalChain` 是会话级串行链的先例（interim 串行可照抄模式）。

### 1.3 方案：旁路即时应答（interject）+ 轮末合并回写 + init 快照重渲染

**核心思想**：运行中消息 → 立即发起一次**旁路 LLM 调用**（带全历史 + 未完成任务的状态占位 + 新消息，不带 tools，纯文本回应并流式给 UI）→ 回应缓冲在 Agent 内 → 本轮工具结果 push 完后**合并回写** history → 广播一次 `init` 快照重渲染（复用现有事件名，契约零改动）。

#### 1.3.1 后端：`Agent.interject`（agent.ts 新方法）

```
Agent 新私有状态：
  private toolPending = false;          // 工具循环执行中置 true（唯一接受 interim 的窗口）
  private interimQueue: ChatMessage[] = [];  // 待合并的 [user, assistant] 对（按时间序）
  private interimBusy = false;          // 一次只跑一个 interim 调用（串行）
  private runSignal?: AbortSignal;      // run() 入口捕获，interject 的 chat 挂同一信号

async interject(text: string): Promise<"ok" | "busy" | "not-pending" | "failed">：
  1. 守卫：!this.toolPending → "not-pending"；this.interimBusy → "busy"（由调用方决定排队或稍后）。
  2. 拼装请求（**不改 this.history**）：
     messages = [...this.history,
       …为「尾部 assistant(tool_calls) 里每个尚未回填的 callId」合成 tool 状态消息
         （只有尾部一轮可能悬空——更早轮次的 tool 消息必然已回填，见 §1.2）：
         {role:"tool", toolCallId:id, content:"[子代理任务仍在执行中，结果尚未返回——
          这是运行期间的状态注入，不是最终结果；请勿重复派发同样的任务]"},
       …this.interimQueue,               // 本窗口内先前已回应的运行中对话（保持连贯）
       {role:"user", content: text}]
     不带 tools（收尾轮先例）；effort=settings.effort；signal=this.runSignal；
     onTextDelta/onReasoningDelta 直通 ui（流式给前端）。
  3. chat 成功且 content 非空 → interimQueue.push({role:"user",content:text},
     {role:"assistant", content, toolCalls:[], …thinking 存档同收尾轮口径})；return "ok"。
     失败/中止/空回复 → "failed"（调用方落 inbox 兜底；UI 已流出的半截文本由 init 重渲染自然纠正——见 1.3.3）。
```

**合成 tool 状态消息 vs 截断**：用户原话「子代理还没处理完，这部分不带」字面是截断（请求里去掉尾部 assistant(tool_calls)）。**推荐合成状态占位而非截断**：模型能看到「自己已派发、任务在跑」，不会重复派发同样任务；截断版模型失忆有重派风险。两者都已满足「不带未完成结果」的本意。若真机发现合成版干扰，降级截断只是 messages 拼装改一行。

#### 1.3.2 合并点：`Agent.run` 工具循环后

```
      for (const call of result.toolCalls) { …push tool 消息… }
      // ↓↓↓ W2-L2 合并点（在 if (signal?.aborted) 之前）↓↓↓
      this.toolPending = false;                    // 关窗：drain 期间新消息走 inbox（有界，防无限穿插）
      while (this.interimBusy) await 等待在飞 interim 完成;
      if (this.interimQueue.length > 0) {
        this.history.push(...this.interimQueue);   // [tool 结果们] → [user,assistant]×k —— 协议合法
        this.interimQueue = [];
        this.deps.ui.onInterimMerged?.();          // 新增可选 AgentUi 钩子（见 1.3.3）
      }
      if (signal?.aborted) { …原样… }
```

要点：①`toolPending=false` 放在 drain **之前**——合并期间到达的新消息落 inbox（轮末排空），窗口有界；②等在飞的 interim 调用完成再合并（否则那对消息会错过本轮、且若下一轮是最终回答就永远合并不进去）；③中止路径也经过这里（工具错误文本已 push），缓冲不丢。

#### 1.3.3 UI 钩子与服务端

- `AgentUi` 加可选钩子 `onInterimMerged?(): void`（agent.ts 接口 + makeUi 实现）。**不新增 SSE 事件名**：makeUi 的实现 = 广播 `SSE_EVENTS.init`（`{sessionId, messages: rt.agent.messages, state: currentState(sh, rt)}`——照抄 onCompaction 的两步：init 重渲染在前）。作用：①主聊天列把「interim 回应块」与后续轮次正确分段（否则下一轮 content delta 会接排在 interim 文本后面——onContentDelta 复用 curAnswer）；②ml 锚点一次性对齐（合并后所有缓冲/快照自然一致，docs/7 §2.2 的坑直接消除）；③后台会话的 init 进 sessCache.buf，切回时重放同路径 ✓。
- `/api/chat`（web-sessions）协调者 busy 分支改造：

```
if (rt.busy && rt.kind === "coordinator") {
  const r = await rt.agent.interject(text);   // Agent 挂在 rt 上，模块经 host 拿 rt
  if (r === "ok") { r.json(202, { ok: true, mode: "interim" }); return; }
  // "busy"：interim 在飞——串行链排一条再试（approvalChain 模式）；简化版：直接落 inbox
  // "not-pending" / "failed"：落 inbox（现有 L1 语义：📩 行 + 轮末排空）
  (rt.inbox ??= []).push(text); broadcast(info 📩 …); r.json(202, { ok:true, mode:"queued" });
}
```

  注意：`"busy"` 时最简单的正确做法是落 inbox（模型回应会晚到轮末）——若要保即时性可做会话级 interim 串行链（`rt.interimChain?: Promise`，approvalChain 先例），非必须，**选型写进实施记录**。
- 多条消息时间先后：每条各一次 interject、各自流式回应（串行）；最终 history 顺序 = tool 结果 → [user,assistant]×k（按到达序）——UI 实时流的时间先后是真实的，history 内序与到达序一致（k 内部），只有「相对 tool 结果」一律在后（协议所迫，docs/7 §2.2 已论证无法做到「插到工具结果前」）。文档口径向用户明示。

#### 1.3.4 前端（index.html）

- `send()` 协调者 busy 分支：改为**本地渲染 user 气泡**（interim 回应是流式 delta，需要气泡提供上下文）+ POST /api/chat。mode=interim：什么都不用再做（delta 事件流进来，onContentDelta 自然成块）；mode=queued：维持现状（无本地气泡、📩 行确认）——**两模式气泡策略不同**：interim 画气泡（消息会进 history，合并 init 重渲染时会用 history 版覆盖本地版，无重复）；queued 不画（docs/7 W2-L1 口径）。
- 切走再切回的边角：interim 回应未合并前不在 history——切走再切回，气泡与半截回应消失，合并 init 到达后整体重现。窗口短（一次文本回应的时间），接受为诚实边界（或 queued 模式同款：切回后靠 needsRefresh 拉快照补齐——init 广播已覆盖，无需额外处理）。
- 占位符与按钮语义不变（协调者 busy 发送/停止分离是 W2-L1 已有）。

#### 1.3.5 明确不做（边界）

- interim 调用**不带 tools**：运行中回应是纯文本（用户要的是「回应」；要动手——暂停子代理等——等下一轮，模型在合成状态里能看到任务在跑）。若真机反馈强烈需要，后续再评估带工具的旁路执行（复杂度大得多，涉及嵌套工具执行与并发写 history，明确不在本期）。
- 普通会话不开 interject（busy 仍 409）；worker 内不 interject。
- 不改系统提示（annotation 是运行时消息不是 prompt；普通会话 golden 零改动）。

### 1.4 坑清单（动手前再读一遍）

1. **不要**在单个 tool push 后合并——必须等本轮 for 循环全部 push 完（多 toolCalls 时隔断 tool 消息 = 非法序列）。
2. **不要**在 interject 里写 `this.history`——只读快照 + interimQueue 缓冲；history 的写点只有 run 循环与合并点。
3. `toolPending` 的置位/复位必须对称（try/finally 或工具循环前后成对），否则窗口泄漏：永不关窗 → 轮结束后消息仍走 interim 且**永远不会被合并**（run 已返回）——丢失。
4. interject 的 usage 必须走 `printUsage({ ...u, breakdown: withOther(u, breakdown) })`（breakdown 用 interim 请求的 estimateBreakdown）——六类守恒。
5. thinking 存档口径同收尾轮（有 reasoning 就存，无 toolCalls 不参与回放）。
6. abort 竞争：interim chat 挂 runSignal——中止时 chat 抛错 → "failed" → 落 inbox → 轮末 finally 排空（现有链路）。已流出的半截回应由合并 init / 轮末状态自然收敛，无需特判。
7. 契约测试锁的是**事件名**不是载荷——复用 init/info/delta 零改动；若新增事件名（不推荐）必须三端同步。
8. 冒烟/单测的桩 LLM（ScriptProvider 等）按调用序吐结果——加 interject 后**调用序会插进工具等待窗口**，相关脚本要按新时序重排（smoke-sa3 的 makeScriptedLlm 按 task 路由，interim 请求的 messages[1] 不是任务书——路由要按「含合成状态消息」识别，见 §1.5 测试建议）。

### 1.5 测试与验收

- **agent.test.ts**（核心，直测 Agent）：①interject 请求形状——messages = 全历史 + 合成 tool 状态（每个未回填 callId 一条）+ 先前 interim 对 + 新 user，且**不带 tools**；②回应流式（onTextDelta 收到）+ interimQueue 缓冲 + history 未动；③合并：工具循环完成后 history 追加 [user,assistant]，且发生在 abort return 之前（中止场景缓冲也合并）；④一轮多 toolCalls 时合并在全部 tool 消息之后（history 里 user 不隔断 tool 消息）；⑤窗口守卫：非 tool-pending 返回 not-pending；interim 在飞返回 busy；⑥usage 走 printUsage（六类守恒断言可抄现有用例）；⑦toolPending 泄漏哨兵：正常完成/抛错/中止三条路径后 toolPending 均 false。
- **web-sessions.test.ts**：busy 协调者 → interject ok 走 interim（202 mode=interim、不进 inbox）；not-pending/failed → inbox + 📩（现有断言改mode）。
- **session-runtime.test.ts / subagents.test.ts**：既有用例不回归（协调者工具四件、暂停/恢复与 interim 正交）。
- **冒烟**：smoke-sa3 加场景 9——agent_tasks 挂起（addGate）期间 interject 一条消息：断言桩收到第二次 chat（请求含合成 tool 状态 + user 消息、无 tools）→ 放行 → agent_tasks 返回 → 下一轮请求 messages 含 [tool, user, assistant(interim)] 序列 → 最终报告完成。
- **真机**：协调者派长任务 → 中途发「现在进度如何」→ 秒级流式回应（不是 📩 排队）→ 任务完成后协调者总结时能引用运行中对话内容；普通会话 busy 仍 409。
- 红线自查：contract（事件名/golden）、withOther、存档（merged 消息随 persistSession 落盘 ✓）、server.ts 行数。

## 2. 需求二：子代理完成后无法回看 / 输出格式异常 / 切回后实时情况丢失（bug 排查）

### 2.1 症状（用户原话拆解）

> 「另一个子代理完成后出现无法回看记录，输出格式也不对劲，但是换一个对话再返回又可以了，但是正在进行的子代理的情况却又看不到了。」

1. 某个 worker **完成后**：无法回看其记录（「📄 过程」/过程区），且（该 worker 或工具块的）**输出格式不对劲**；
2. **切到别的对话再切回**：上述两者都恢复正常（→ 实时增量渲染路径的 bug，快照重渲染路径 renderHistory 是好的）；
3. 切回后**正在运行的** worker 实时情况不可见（→ 缓冲重放链路 suspect）。

**先在新构建上复现**：用户反馈可能来自 docs/6 时期或 docs/7 之后的构建——W2-S 已重构过 `onSubagent`（subs-line 改为 `_txt` span + 控制按钮结构），症状可能已变化。第一步固定在当前 HEAD 复现，结论写进实施记录。

### 2.2 结构事实与候选根因（按怀疑度排序）

实时渲染链（index.html）：`onSubagent`（挂在 **curTool**——当前运行中的 agent_task(s) 工具块内）→ `.subs-line` 状态行（`_txt` span + ⏸/▶ 按钮）→ `.sub-proc` 过程盒（`subProcBox`，line 的**兄弟节点**）→ 工具行 + 结果 pre。持久链：done/error 带 transcript → 「📄 过程」→ `/api/subagent-transcript` → `#subModal` 的 `renderTranscript`。

- **候选 1（最可疑，解释症状 1+2）**：`addToolRes`（agent_tasks 的工具结果到达时）把**整个工具块** `classList.add("collapsed")` 并在轮末 `foldTurns()` 再收进「🔧 执行过程」——时间线/过程区都在工具块体内，完成后要**两层展开**才能回看；且折叠时机与 done 事件竞争时，展开态渲染可能中途被打断（部分 DOM 移动中的 innerHTML 替换），表现为「格式不对劲」。切走切回 = renderHistory 全量重建 → 正常。**验证法**：完成后手动逐层展开，看内容是否完好只是藏得深——若完好，这就是 UI 层级问题（并入需求三修），不是数据 bug。
- **候选 2（解释症状 1 的「无法回看记录」变体）**：`dumpTranscript` best-effort 写失败（路径被占/权限）→ transcript=undefined → done 事件不带「📄 过程」入口（`r.transcript` 为空时 subLinkEl 不生成）——表现为「这条没有回看入口」。切走切回也不会出现（记录里确实没有）。**验证法**：查会话档 JSON 的 `subagents[].transcript` 字段与 spill 目录文件是否在；单测已有「写失败不影响结果」用例，但真机失败原因（杀毒/长路径/并发）要留档。
- **候选 3（解释症状 3）**：切回时的缓冲重放 `switchSession` → `renderHistory`（重建 pending 工具块设 `curTool`）→ `dispatchBuffered` 重放 subagent 事件 → `onSubagent` 依赖 `curTool`。任一环断掉实时流就丢：a) `renderHistory` 的 pending 判定要求 `state.busy === true && i === lastAsst && unanswered`（index.html）——若快照 state.busy 为 false（时序竞争：恰逢轮末）或该 toolCall 不在最后一条 assistant（历史里后续已有消息），curTool 为 null → 重放全部被 `if (!curTool) return;` 吞掉；b) `route()` 对 `turnEnd` 清 buf——若切换期间恰好有一轮结束又开新一轮（W2-L1 排空），旧缓冲被清、新事件继续进 buf，但**重放只发生在 switchSession 时点**，切回后正在跑的 worker 新事件会实时到（这个方向应该没问题）——重点查 a)。**验证法**：复现时在 console 里查 `state.busy`、`curTool`（可在 window 上临时暴露）与重放的 subagent 事件条数。
- **候选 4（解释「输出格式不对劲」的另一变体）**：`addToolRes` 对超 20000 字符截断显示 + `linkifyTranscriptTags` 的 `[[过程档案#N]]` 替换 + 工具结果是纯 `<pre>`（不走 mdLite）——worker 报告里的 markdown 在工具块里**原样显示**（协调者最终回答走 mdLite 是渲染过的）。若用户指「报告里的 markdown 是生的」，这是设计现状不是 bug（改渲染要防 XSS——mdLite 已有 esc，可评估对 .tres 套 mdLite，属需求三范畴）。

### 2.3 排查步骤建议（给执行对话）

1. 当前 HEAD 启动（`ZQQ_NO_BROWSER=1 npm run web` + 临时 USERPROFILE），协调者会话派 2-3 个长任务 worker（可用 `scripts/e2e-sa4-stub-llm.mjs` 桩或真模型）；
2. 逐项验证候选 1-4（上面各「验证法」）；结论（哪条成立/全不成立+新发现）写进实施记录；
3. 无论根因为何，症状 3 的结构性弱点（实时流依赖 curTool 挂载 + 瞬态不跨刷新）在需求三的抽屉方案里一并消除——**如果排查结论是候选 1/3，优先直接做需求三而不是打补丁**；只有候选 2（transcript 丢失）是必须独立修的数据 bug（修法：失败原因分类 + done 事件带 `transcriptFailed` 提示行；或重试一次）。

### 2.4 验收

复现路径全部走通：完成后回看入口可用（或明确失败提示）；切走切回运行中 worker 实时流可见（或经需求三抽屉可见）；输出格式与切回后的静态渲染一致。

## 3. 需求三：界面清爽化——子代理内容侧栏抽屉 + 协调者视图降噪

### 3.1 痛点（用户原话：「展开后在同一个界面一层套一层」）

现状嵌套深度（完成后回看的真实路径）：轮折叠组「🔧 执行过程」→ 工具块（agent_tasks）→ 折叠体 → subs-line 状态行 → sub-proc 过程盒（又是折叠）→ sub-tool 工具行 → 结果 `<pre>`——**5 层**，且全挤在主聊天列里，与协调者的思考/正文抢空间；实时与回看两套 UI（过程盒 vs transcript 模态）体验不一致。

### 3.2 方案 A（推荐）：子代理侧栏抽屉（drawer）

**布局**：`#main` 改双栏——`[主聊天列 flex:1] + [#subDrawer 宽 ~420px 可收起]`（有 subagent 事件的会话才显示抽屉开关；普通会话零变化）。抽屉常驻（不遮挡对话），移动/窄窗降级为覆盖式滑出（CSS media query）。

**抽屉两层视图**：

1. **列表页**：本会话全部 worker 一行一个（数据源 `state.subagents` 审计记录 + 活动登记——**currentState 需增发 `activeSubagents: [{subId,name,paused}]`**（瞬态，服务端 session-runtime.ts currentState 一行））：状态图标（▶ 运行/⏸ 暂停/✓/✗）+ name + description + 轮数/用量 + 「⏸/▶」控制按钮（W2-S 的 POST /api/subagent/control 原样复用，从时间线行迁到抽屉行）。运行中的置顶并带 live 指示。
2. **详情页**（点击行进入，← 返回）：单个 worker 的过程时间线——**复用现有 `renderTranscript` 的消息渲染**（user 气泡/assistant 思考折叠+正文/工具块+结果回填，它已是扁平单层结构）。数据源两态：完成后走 `/api/subagent-transcript`（现成）；**运行中**由 subagent SSE 事件流增量维护一份 per-worker 消息形状的缓存（前端把 `tool`/`toolResult` 事件转成与 transcript 同构的行即可——比现在的 sub-proc 盒更简单，没有嵌套），顶部标注「实时（完成后的完整存档以 📄 为准）」。

**主聊天列瘦身**（降噪的关键）：agent_task(s) 工具块**不再内嵌**时间线/过程盒——块内只保留一行摘要：「🤖 3 个子代理：✓2 ⏳1 → 在抽屉中查看」（点击打开抽屉；工具块原有的完整合并报告文本保留在块内折叠体里，那是给用户看的最终产物）。`onSubagent` 的挂载依赖 `curTool` 的结构弱点随之消失（事件路由到抽屉，不依赖工具块存活）——**需求二的症状 3 在此结构性消除**。subs-line/sub-proc 相关代码（subProcBox/subProcTool/subProcResult）删除或降级为抽屉内实现，`#subModal` 模态可删（抽屉取代）或保留给「从历史报告的 [[过程档案#N]] 链接直接开详情」——建议保留函数、入口统一进抽屉。

**协调者视图降噪**：worker 内容移出后，主列只剩 思考块/文本/工具块 三种元素；`foldTurns` 保持现状即可（层级感骤降）。可选打磨：工具块头部加「📄 子代理详情」快捷入口。

### 3.3 备选方案（不推荐但列出）

- **B 模态全屏化**：把现有 #subModal 升级为全屏/大尺寸 + 列表导航。改动最小，但遮挡对话、「同时看协调者输出与 worker 过程」做不到——与「清爽查看」诉求冲突。
- **C 标签页**：主列顶部切「对话 / 子代理」两个 tab。实现简单，但看 worker 时完全看不到协调者，且 tab 状态与 SSE 流的挂载切换要重做，得不偿失。

### 3.4 实施要点

- 全部改动落在 index.html + session-runtime.ts 的 currentState（增 activeSubagents 字段，照 subagents 字段先例，瞬态不落档）+ 若删模态则同步 web-sessions 无需动（/api/subagent-transcript 路由保留）；**SSE 事件名零新增**（subagent 事件原样复用）。
- 抽屉状态（开合/激活的 subId）是纯前端态；切换会话时清空并按 `state.subagents`/activeSubagents 重建列表。
- 刷新后：完成 worker 详情从 transcript API 拉（现成）；运行中 worker 详情从零开始积累（SSE buf 不跨刷新——诚实边界，详情页顶标注「刷新前的实时过程不可回看，完成后可看全程存档」）。
- XSS：renderTranscript 已走 esc/mdLite 白名单路径，新增列表行注意同款转义。
- 契约：`SSE_HANDLERS` 表键与事件名的契约测试不受影响（subagent 处理器内部改道到抽屉）。

### 3.5 验收

单屏内：协调者正文与 ≥1 个 worker 过程**同时可见**、各自独立滚动；回看任何已完成 worker ≤2 次点击（列表行 → 详情）；⏸/▶ 在抽屉列表行可用；普通会话界面字节级无感知（无抽屉元素）。
