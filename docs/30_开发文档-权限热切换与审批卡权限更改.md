# 30 · 开发文档——权限热切换与审批卡「权限更改」（运行中改权限即时生效 / auto 自动放行 / 解除沙箱并放行）

> 状态：**已实施**（2026-11-17，随 v0.3.3 发布；预检三件套全绿——typecheck 三段过 + npm test 480/480 + smoke:sa4 11/11）。
> 来源：用户需求——「对话中途更改权限后是否生效？能否下次请求就用新权限；审批卡上加权限更改选项，后续不再审批」。

## §1 背景与设计决策

现状两处死板：① 会话 busy 时 `/api/settings` 整体 409（含审批策略/沙箱模式），前端同步禁用两下拉——运行中（含审批卡等待时）根本改不了权限；② 审批卡只有「允许一次/拒绝」，无"后续不审批"出口（决策词汇封闭且原设计明文"不做会话级放行"）。

经确认的设计决策（用户选定）：

| 决策点 | 结论 |
|---|---|
| 审批卡新按钮 | **两个都加**：「允许并不再询问」+「解除沙箱并放行」 |
| auto 与提权的关系 | **提权卡保留人工**——auto 只吞普通拦截卡，justification 提权卡照常弹（防模型自我升权，+1/-1 升级额度门不拆，docs/1 §2.4 语义不变） |
| busy 时改权限 | 权限三键（askMode/alwaysConfirm/sandboxMode）放行，effort 等维持 409 |

「auto vs 全开放」的语义边界（对用户解释口径）：

- **auto 改的是"问不问"（同意层）**：拦截卡自动批准——文件工具区外写静默成功（文件工具走 Node 进程不经 OS 沙箱）、worker scope 卡自动批；但 run_pwsh 的命令仍被 OS 沙箱按当前模式关着，区外写入照样物理失败。
- **全开放改的是"能不能"（能力层）**：沙箱墙拆掉，命令无约束执行；区外命令本来就不弹卡；升级额度链休眠（无拒绝即无额度）。

## §2 实施

### 2.1 审批词汇（`src/approval/types.ts`）

- `AskMode` 加 `"auto"`；`normalizeAskMode` 接受显式 auto；`askWithMode` 仍只管 never→unavailable（auto 的不弹卡短路放运行时层——审计要记事件，词汇层拿不到审计数组）。
- `AuditEvent` 加可选 `auto?: boolean`；`auditDecided` 加 `opts?: { auto?: boolean }`。auto 放行**照写 asked+decided 对**（形状与人工一致，`auditStats` 计数语义不变），靠 auto 标注区分。

### 2.2 运行时（`src/web/session-runtime.ts` + `session-lifecycle.ts`）

- `requestApprovalFor.askOnce`：`askMode==="auto" && !req.justification` → 不弹卡直接 `allowed-once`，写审计对（auto:true）；带 justification 照常走 `doAsk`。`rt.settings.askMode` 本就 live 读（每次 ask 现取），策略切换即时生效，worker 排队卡同链受益。
- 新增导出 **`applyPermissionPatch(host, rt, patch)`**（`session-lifecycle.ts`，模块经既有 import 先例 `web-sessions/index.ts:14` 引用）：权限三键白名单 + 值逐键归一化（野值忽略该键，不整包拒绝）→ 改 `rt.settings` → 沙箱键随 `rt.agent.setSandboxMode` 热更 → **busy 跳过落盘**（轮末自动存档兜底，避免存档捕到悬空 tool_calls 半截历史），空闲立即 `persistSession` → 广播 state（下拉/按钮显隐同步）。收 `SessionHost`（模块可见的唯一宿主接缝），非 SessionShell。

### 2.3 端点

- `/api/settings`（`web-sessions/index.ts`）：busy 且 body 只含权限三键 → 放行走 `applyPermissionPatch`；busy 含 effort（或混发）→ 维持 409（fail-closed 整体拒绝）；空闲路径行为不变（权限键现在也立即落盘）。原三段内联应用逻辑（alwaysConfirm/askMode/sandboxMode 各自 persist）收敛进补丁函数，`normalizeAskMode`/`normalizeSandboxMode` import 随之移除。
- `/api/approval`（`web-approval/index.ts`）：body 加可选 `apply` 补丁——**先应用再 settle**：排队的并行 worker 后卡立即见新模式，杜绝"批了一张又弹一张"竞态；busy 是必然（有卡必在轮中），不落盘。

### 2.4 工具 live 读权限（`deps` 会话闭包）

- `createPwshTool(deps?: SystemToolDeps)`（`modules/tools/pwsh/pwsh.ts` + `index.ts` 传 deps）：沙箱模式经 `modeOf()` 在**每个裁决点各读一次**（逐条确认卡批准后重读——卡上切全开放，本条即无约束执行；全开放分支、SANDBOX_UNAVAILABLE 文案、runSandboxed policy 同口径）；逐条确认经 `deps.alwaysConfirm()` live 读。无 deps 测试桩回退 ctx 快照（存量测试不感知）。
- `write_file` / `edit_file`（`adjudicateWrite` 入参）：`ctx.sandboxMode/alwaysConfirm` 快照改 `deps.sandboxMode()/alwaysConfirm()` live 读——运行中改模式，本次写裁决即用新值。
- Agent 逐轮 ctx 快照字段（`agent.ts:574-583`）保留不动（其他消费者/interim 窗口仍用）。

### 2.5 前端

- `index.html`：confirmSelect 加 `<option value="auto">🛡 自动放行</option>` + title 更新；审批卡按钮行加 `aFull`「🔓 解除沙箱并放行」（默认 hidden）与 `aAlways`「允许并不再询问」（默认 hidden），475 行 < 500 哨兵。
- `main.js`：`answerApproval(decision, apply?)` → POST 带 apply；aFull/aAlways 接线（aFull apply `{sandboxMode:"danger-full-access"}`、aAlways apply `{askMode:"auto", alwaysConfirm:false}`）；`showApprovalCard` 按 `C.state.sandboxMode==="danger-full-access"` / `C.state.askMode==="auto"` 控制两按钮显隐；confirmSelect handler 加 auto 映射与 prev 计算；`/status` 审批段加"自动放行"标签。无新增顶层裸 let（哨兵 ≤3）。
- `chat.js` `applyState`：csel 值映射加 auto 分支；**去掉 csel/ssel 的 busy 禁用**（effortSelect 保持）——服务端 409 兜底仍在前端 change handler 的回滚逻辑里（仅 effort 会触发）。

## §3 语义速查（实施后）

| 场景 | ask | auto | never | 全开放（配合任意策略） |
|---|---|---|---|---|
| 文件工具写区外 | 弹卡 | 自动批→成功 | 不弹→拒绝 | 不弹→成功 |
| pwsh 区外写入 | 弹卡（escalation 链）后仍 OS 拒 | 自动批但仍 OS 拒→走提权链 | 不弹→拒绝 | **无约束执行成功** |
| justification 提权卡 | 弹人工 | **弹人工（不吞）** | 不弹→unavailable | （链路已休眠） |
| worker scope 强制卡 | 弹人工 | 自动批 | 不弹→拒绝 | 弹人工（scope 卡任何模式都弹，含 auto 之外的自动路径仅 auto 吞） |

运行中改权限：生效时点 = pwsh/文件工具**下一命令**（deps live 读，同轮内也算）；审批策略**下一次 ask** 即生效（本就 live 读）。

## §5 真机回归补（同日）——升级额度拒绝检测漏检 exit 0 的非终止性错误（已修复）

用户按本特性真机实测「工作区外写入→提权→删除」链路，现象：**写入阶段提权成功**（auto 模式下
普通卡被自动放行放掉了两次、Set-Content 提权卡正常弹出并批准、无约束写入成功），**删除阶段
三通全败且换四种删法（.NET Delete / cmd del / Rename-Item / Clear-Content）结果一样**，全程
无一张卡。审计存档（会话 `events`）证实：删除阶段 **0 条审批事件**——「提权后」从未发生。

**根因**：`runSandboxed` 的拒绝识别旧口径为 `code !== 0 && stderr 命中`。Remove-Item 的
Access denied 是 **非终止性错误**——测试脚本在删除失败后继续 `Test-Path`/`Write-Output`，
pwsh 整体 **exit 0** → 检测漏检：不打 `[sandbox:]` 标、不攒升级额度 → 模型带 justification
重试被静默忽略 → 永远出不了卡。写入阶段能走通纯属脚本尾部差异（Set-Content 拒绝是末语句，
exit 1 被识别）。副作用：exit 0 + 无前缀的输出看起来像"命令成功但文件还在"，模型也被误导。

**修复**（`pwsh.ts` runSandboxed + execute 收尾）：

1. 拒绝识别**只看 stderr 正则**（`is denied|拒绝访问|访问被拒`，真机存档的 CLIXML 编码
   stderr 实测可命中），去掉 exit-code 门槛。误攒成本可控：额度只在模型随后真带
   justification 时消费（每次 -1），且有 8 点/会话上限。
2. justification 带了但入口额度为 0 → **不再静默忽略**，结果末尾追加一句明示：刚被拒
   （攒出 1 点）→ 指引立即带 justification 重试即可弹卡；未被拒 → 说明无需提权。

**无约束删除可行性验证**：诊断中以无约束 shell 对同一文件（`论文工作区\提权测试2.txt`）直接
删除成功（其 DACL 含 `Authenticated Users:(M)`）——证实失败全部来自"实际跑在沙箱里"，非 OS
删除边界；docs/1 §"批准后无约束执行，实测可行"的结论维持成立。测试残留（提权测试2.txt）已顺手清除。

**新增 3 测**（`pwsh.test.ts`，fake runner 桩 `setSandboxRunner` + finally 还原）：exit 0
拒绝打标攒额度 / 真机完整链路（拒绝攒额度 → justification 弹卡 → 批准后无约束真跑）/
零额度 justification 明示反馈。全量 **480/480** 全绿。
