### 4. write_file 第一次调用总忘 path → schema/文案/错误三处强化

- 现状：schema 里 path 本就在 `required`，模型（尤其组织长 content 时）仍会漏——漏参时
  `resolveTarget("")` 只报「path 不能为空」，指引性弱。
- 三处强化（read_file / write_file / edit_file 同款）：
  ① 工具 description 首句点名「每次调用必须同时提供 path（与 content 等）」；
  ② path 参数 description 改「必填……每次调用都不能省略」；
  ③ execute 入口前置判空，缺参返回指引性错误（指名漏的参数、要求带上重试）——模型见到即补参重调。
- 文件：`modules/tools/write-file/index.ts`、`modules/tools/edit-file/index.ts`、`modules/tools/read-file/read-file.ts`。

### 5. 系统工具 token 被算进 MCP 工具类 → 复查不复现，关闭

- 探针实测（估算 breakdown 的真实分类路径 + 前端渲染映射）：`estimateBreakdown` 按
  `mcp__` 前缀分流转发正确（write_file→systemTools、mcp__demo__add→mcp），前端 token 面板
  （chat.js tokRow）与 /status（main.js）映射一致。用户确认此前现象不再复现，未改代码。
- 顺带核实过的小口径问题（未动，留观察）：MCP instructions 在 system 消息内但未从
  systemPrompt 扣除（与 skills 不同），理论上 mcp 分类与其双算——影响小，改动会牵动 golden，暂不动。

### 6. 协调者子代理报告送达时蓝色方框不即时出现 → 前端补即时渲染路径

- 根因：送达报告/状态通知由服务端作为 user 消息开轮（`deliverToCoordinator` → `startTurn` →
  `agent.run` 入历史），浏览器从未发送它——前端 user 消息的实时渲染只有「用户自己乐观渲染」
  与「切走切回快照重放」两条路，送达气泡两条都不走，要切回才出现。
- 修复（纯前端，服务端零改动）：startTurn 广播的 state 事件本来就带 turn 锚点
  `{ml, userText}`（先于消息入历史到达）——`chat.js` 新增导出 `maybeRenderAutoTurn(turn)`：
  判别 userText 是送达消息（splitAutoText 前缀匹配，用户插话已由 send() 本地渲染、天然排除）
  即就地 `userBubble` 渲染（与 renderHistory 的 🤖 送达气泡同款）；按 `autoTurnMl`（cacheOf
  会话缓存）幂等，同轮重复 state 不重画。`main.js` state handler 接线。
- 后台协调者会话（不在视图）不乐观渲染，切回仍走快照路径，行为不变。

## 追加：write_file 参数重排（content → path）缓解首调漏 path（同轮真机反馈）

- 复发：问题 4 的 description/错误指引强化后，模型首次调 write_file 仍极大概率漏 path。
- 第一手（已回退）：按"模型按生成序补参、path 在后顺势补齐"的假设重排为 content → path →
  description——真机观察无改善，用户拍板回退。
- 第二手（现行）：**恢复 path → content → description（required ["path","content"]），
  工具 description 首句内嵌调用示例**：
  `调用示例：{"path": "docs/notes.md", "content": "完整的文件内容"}——path 与 content 是必填参数…`。
  few-shot 示例对参数完整性通常比顺序/文案强调更有效（模型照着示例形状生成）。
- write-file.test 不受影响（execute 传参与 properties 顺序无关）；typecheck + npm test 469/469 全绿。

## 追加：合并送达消息拆回多张独立卡片（同轮真机反馈）

- 现状：docs/16 轮末排空把连续送达报告合并为一条 user 消息开一轮（省轮次，服务端语义正确），
  但界面把合并文本渲染成**一个**气泡——一行摘要只见第一份报告，其余报告藏进展开全文里。
- 拆卡逻辑单一出处：`autoreport.js` 新增纯函数 `splitAutoTextSegments(text, p)`——以「行首的
  送达前缀」为切段锚点（报告/状态前缀任一；正文不含行首前缀、行中出现的字样不拆，不误分），
  段尾的合并分隔线（U+2015 横线行）与空白清理；单条/非送达/前缀缺失返回 null（行为不变）。
  不依赖分隔符字面量，前端照旧不写死送达前缀（meta 下发的 AutoPrefixes 参数化）。
- 消费点：`chat.js userBubble` 开头拆段，多段时每份渲染为独立 `.msg.user` 气泡（renderAutoReportBubble
  同款，摘要各归各的报告）。实时路径（maybeRenderAutoTurn）与历史快照重放（renderHistory）都走
  userBubble，拆卡行为一致；服务端零改动（历史里仍是一条消息，存储/传输形态不变）。
- 单测：autoreport.test.js 补 3 例（混排拆段+分隔线清理 / 单条与非送达 null / 行中前缀不误拆）；
  typecheck 三段过 + `npm test` 469/469（fail 0）。

## 追加：工具调用失败整块标红（同轮真机反馈）

- 现状：只有 pwsh 的 `✗ exit N`（`.tstat.bad`）有红色状态小字，其余工具失败（「错误：…」回传）
  折叠头一律绿色 ✓，失败调用淹没在折叠过程里。
- 判定单一出处：`toolinfo.js` 新增纯函数 `isToolResultError(text)`——「错误：」前缀（全部系统
  工具/MCP 控制面错误回传的统一形态）或 pwsh `exit code: 非零数字`（负数含在内；unknown 不判）。
- 消费点三处（渲染与历史/重放同路径）：
  ① `chat.js addToolRes`——失败时状态字 `✗`（不再误显 ✓）+ `blk.classList.add("err")`；
  ② 中断块（renderHistory 与 main.js turnEnd 清扫的「无返回结果」）同款 `err`；
  ③ `drawer.js` 时间线 `appendToolResult`（抽屉详情页，与主对话同款）。
- CSS（index.html）：`.tblock.err` 红边框 + 红工具名 + 摘要暗红——折叠态一眼识别，展开体不变。
- 单测：toolinfo.test.js 补 `isToolResultError` 七形态断言；`npm test` 466/466（fail 0）。
