# ZQQ-harness 开发文档：沙箱 · 审核 · 上下文管理

> **⭐ 实施记录（2026-11-16，桌面端真机回归：console-less 宿主下受限 pwsh 全崩 0xC0000142）**：
> **症状**：桌面端（v0.2.0 打包版）run_pwsh 每次都 `exit code: 3221225794`（=0xC0000142，DLL 初始化失败）、stdout/stderr 全空；浏览器/dev 模式一切正常。（顺带：会话里模型把它换算成 0xC0000409 是错的，取证以会话存档的十进制码为准。）
> **根因**：受限令牌下的 pwsh 只有「**共享宿主控制台**」一条活路，此前所有测试都跑在有控制台的宿主（终端里的 node）上——该前提被无意满足而从未被显式保障。桌面端 server 是 `ELECTRON_RUN_AS_NODE=1` 的 Electron（GUI 子系统，**无控制台**），pwsh 启动时无宿主控制台可继承。
> **实验矩阵（Electron 宿主实测，一次定案）**：①CREATE_NO_WINDOW / CREATE_NEW_CONSOLE（=新建控制台）→ 受限令牌下 conhost 建不起来，0xC0000142（与下方 M5 记录一致）；②DETACHED_PROCESS（=完全无控制台）→ **进程活、exit 0，但 ConsoleHost 静默不执行命令**（Start-Sleep 3 实测 ~350ms 即回、Set-Content 落盘不存在——假成功比崩溃更危险）；③共享宿主控制台（现有 flag）→ 宿主有控制台时唯一可行。
> **修复（windows-acl.ts）**：`ensureHostConsole()`——宿主无控制台时 `AllocConsole()` + 立即 `ShowWindow(SW_HIDE)`，进程生命周期内复用（不 FreeConsole：反复 Alloc/Free 每条命令闪一次窗）；有控制台的宿主（浏览器/dev）行为零变化。koffi 踩坑：**void* 空指针解码为 JS `null` 而非 `0n`**，判空必须两者都查（首版只查 `!== 0n`，`null !== 0n` 恒真导致补偿被静默跳过、修复一度"无效"）。
> **验证**：Electron-as-node 宿主——Start-Sleep 3 真实耗时 3.8s、Set-Content 真落盘、stdout 采集正常；Git Bash 宿主回归不变；npm test 全绿。附带修复（同日另一真机问题）：默认端口 8787 被 WinNAT 排除段（Hyper-V 动态保留）圈住 → `listen EACCES`，server.ts 对「用户未显式指定 PORT」的 EACCES 自动回退随机端口（桌面端 PORT=0 与显式 PORT 脚本不受影响），详见 docs/27 坑表。

> **文档用途**：作为新对话的实施参考。目标是在本仓库实现三个功能：命令审核（approval）、上下文管理（度量/修剪/落盘/压缩）、沙箱（OS 级进程约束）。
> **设计基准**：DeepSeek 官方开源的 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（下称 DSH，MIT，developer preview）的已实现设计，经裁剪适配到本项目。DSH 参考文件路径见附录 A。
> **写作日期**：2026-09-22。若代码与本文冲突，以代码为准并回改本文。

- **2026-09-23 实测反馈后的两处修正**（用户实测发现"带审批重试仍被拒"与"区外→区内 Move 不拦截"）：
  1. **升级重试从"逐字节复现同一命令"放宽为额度制**：原实现 `escalationArmed: Set<exact-command>` 要求重试命令与被拒命令逐字节一致才弹审批，实测模型换一种写法（复制+删除替代移动）重试就永远走不到审批卡。现改为"每次沙箱拒绝记一次额度（上限 8），下一次带 justification 的调用（无论命令是否相同）即转人工审批，额度无论批准与否都被消费"。审批卡照常展示完整命令+理由，人工把关不变；§2.4 的"每条命令最多一次/无 justification 直接拒绝"按此口径理解。
  2. **删除边界的精确实测（探针 2–7，真机受限令牌，修正本记录早先"裸 DELETE 不受限"的过宽结论——那是在用户配置文件内测的）**：
     - 工作区内：三种删除方式都成功（设计使然，文件继承 wsSid 写 ACE）。
     - **用户配置文件（C:\Users\home 及其子目录，含纯组 ACE 的文件）：裸 DELETE（`[IO.File]::Delete`/`cmd del`/跨卷 Move 的源删除）不被拦**；但 `Remove-Item`/`Rename-Item` 因额外申请写类访问仍被拦。
     - **其余位置（F:\ 数据盘、C:\Users\Public 等仅组授权目录）：裸 DELETE 也被拦**（Win32 错误 5 ACCESS_DENIED），**即使文件 DACL 显式授予当前用户 FA**；全令牌删除同一文件成功（证明非文件锁定）。唯一例外：DACL 含 **Everyone（S-1-1-0）写 ACE** 时裸删除放行（受限列表含 Everyone，DACL 命中即过双重检查）。
     - 机制归纳：受限 SID 双重检查对"写类"访问生效；裸 DELETE 是否通过取决于 NTFS 删除授权路径与目标 DACL 是否命中受限列表 [logon SID, Everyone, wsSid, tempSid]——用户配置文件路径的行为与其他位置不同，边界不整齐，照实写进 README，不试图"修整齐"。删除区外文件的正规通道是审批升级（批准后无约束执行，实测可行）。
     - 探针遗留坑：`icacls /grant` 在 Git Bash 下会被路径转换撕裂（`/grant`→`F:/Program Files/Git/grant`），须用 pwsh 包一层；`.NET File.Delete` 对不存在的文件静默成功，探针必须校验文件真实存在性。

## 1. 全局设计原则（从 DSH 提炼，三功能共同遵守）

1. **Capability seam（能力接缝）**：新能力做成挂在 ctx / deps 上的可选服务（`ctx.sandbox`、`ctx.approval`、`ctx.compaction`、`tokenMeter`），**不进 agent 循环主干**，可整体替换或降级。
2. **Fail-closed**：约束选了但后端不可用 → 明确结构化错误（`SANDBOX_UNAVAILABLE`），**绝不静默降级为无约束执行**。审批应答野值/缺失/异常一律归一化为拒绝。
3. **拒绝即事实**：拦截/拒绝的结果以字符串回传模型（沿用 registry 惯例），让模型自我修正；沙箱拒绝时把命令自己的 stderr 原样带回。
4. **日志不入模型上下文**：审计事件、压缩记录只进会话存档的独立字段，绝不混进 `messages`（messages 就是发给模型的 surface）。
5. **执行器不协商权限**：pwsh/MCP 工具只声明"我需要批准/我被拒绝"，何时问人、怎么问是审批服务的事。
6. **诚实边界**：所有安全声明照实写进 UI/文档（参考 DSH SAFETY.md 的措辞风格），启发式就是启发式，不夸大为隔离。

```ts
  command: string;            // 展示用原文
  description?: string;       // 模型自带的摘要（见 2.2）
  reasons: string[];          // 守卫/沙箱给出的拦截原因（人类可读）
  justification?: string;     // 沙箱升级重试时模型附带的一句话理由（见 2.4）
}

export function normalizeDecision(raw: unknown): ApprovalDecision {
  return raw === "allowed-once" || raw === "rejected" || raw === "cancelled"
    ? raw
    : "unavailable";          // fail-closed：野值/缺失/异常都当拒绝
}
```

- 只有 `allowed-once` 放行，且**仅限当次**（下次同命令重新走审批；不做会话级放行，避免"批准过一次就永久放行"的口子）。
- `cancelled`：用户点了停止/新开对话导致等待中的审批作废。server 端在 abort 时 resolve 掉挂起的审批 Promise。

### 2.2 description：模型自带命令摘要

`run_pwsh` schema 增加必填参数（registry.schemas() 自动下发给模型）：

```ts
description: {
  type: "string",
  description: "用主动语态、5–10 个词概括这条命令要做什么（如：删除 build 目录下的临时文件）",
},
// required: ["command", "description"]
```

- execute 里校验非空：空/缺 → 返回 `"错误：description 不能为空，请用一句话概括这条命令的目的"`（模型会补）。
- **说明从哪来**：不本地分析命令。摘要由模型在调用时自己写好——schema 逼着它交代，审批人先读摘要再读命令。
- MCP 工具不动（参数 schema 由外部服务器定，不可强加）。

### 2.3 ToolContext 与 server 端改造

```ts
// registry.ts
export interface ToolContext {
  workspace: Workspace;
  requestApproval: (req: ApprovalRequest) => Promise<ApprovalDecision>;  // 签名升级
  alwaysConfirm?: boolean;
  sandboxMode?: SandboxMode;        // 功能三引入，这里先留位
  signal?: AbortSignal;
}
```

- pwsh.ts 的调用点同步改：审批被拒时回传文案不变（"用户拒绝执行该命令…"），但 reasons 里追加 description 展示。
- server.ts：`broadcast("approval", { ...req })`；POST /api/approval 接收 decision 字符串 → `normalizeDecision` → resolve。
- **会话策略**：新增 `askMode: "ask" | "never"`（SessionData 字段，UI 开关 + `/confirm never` 子档）。`never`（无人值守/CI）在 server 内部直接返回 `unavailable`，**连审批卡都不弹**。现有 `/confirm on|off`（alwaysConfirm）保留，两者正交。

### 2.4 升级重试（escalation，依赖功能三的沙箱；接口先定）

沙箱拒绝后，模型可以**重试一次**同一命令：带 `justification`（一句话说明为什么需要更宽权限）申请走人工审批。规则：

- 每条命令最多一次升级重试（在工具执行的闭包内记状态即可）；
- 无 justification 的升级重试直接拒绝；
- 审批卡在 justification 存在时显著展示（"模型申请提权：…"）。

### 2.5 审计事件（log-only，不进模型）

SessionData 增加独立字段：

```ts
export interface AuditEvent {
  seq: number;               // 会话内单调递增
  at: string;                // ISO 时间
  type: "approval/asked" | "approval/decided";
  command: string;
  description?: string;
  reasons: string[];
  decision?: ApprovalDecision;   // decided 才有
}
// SessionData 增加 events?: AuditEvent[]
```

- `approval/asked` 在弹卡时写、`approval/decided` 在决议时写，随现有 persistSession 落盘。
- **绝不 push 进 messages**。/status 可显示"本会话审批 N 次（批准 M 次）"。

### 2.6 验收

- 单测：normalizeDecision 全分支；description 缺失被拒；never 模式不弹卡直接拒；审计事件成对出现且不入 messages。
- 手动：Web 弹卡显示 description + 命令 + 原因三段；拒绝后模型收到原文案并改用相对路径。

## 3. 功能二：上下文管理

四个子模块按依赖顺序：度量 → 修剪 → 落盘 → 压缩。**不照搬 DSH 的事件溯源**（那是为可重建投影服务的，本项目会话已是 JSON 存档，引入事件日志属于过度工程）；采用"messages = surface，SessionData = 真相"的轻量映射，代价与缓解见 3.4。

### 3.1 度量：tokenMeter 落地

现状 `contextEstimate()` 每轮全量重算（真分词，准但浪费）。改造（`src/tokens.ts` + agent.ts）：

- agent 内维护 `msgTokens: WeakMap<ChatMessage, number>`（消息对象不可变，push-only，天然可缓存）；`contextEstimate()` 只对新增消息分词，其余取缓存。system 消息在 setWorkspace/setSkills 时重建，自然失效重算。
- 新增 `contextPressure(): number` = `contextEstimate().total / providerConfig.contextLength`，夹到 [0,1]。contextLength 是 ProviderConfig 的**按提供方字段**（providers.json + 提供方表单"上下文长度"可改，默认 1M；`DEEPSEEK_CONTEXT_LENGTH` 环境变量只在旧配置自动迁移时作兜底读一次）。
- 阈值常量进 config.ts：`COMPACTION_PRESSURE = 0.8`（UI 已有占用百分比显示，可顺带加 ≥80% 预警高亮）。

### 3.2 修剪：注册表层统一 toolResultPruner

把截断从 pwsh.ts 上收到 `registry.execute()`，**对 run_pwsh 和所有 mcp__ 工具统一生效**：

```ts
// src/tools/prune.ts
export interface PruneResult { text: string; prunedChars: number; spilled?: string; }
export function pruneToolResult(text: string, budgetChars: number): PruneResult
```

- 三段式：头 60% + 中间省略标记 + 尾 40%（标记注明被剪字符数）；按 UTF-16 码元切即可，但**不得把代理对劈成孤立代理项**（切点回退到最近完整码点）。
- pwsh.ts 保留自己的采集上限（SOFT_CAPTURE_LIMIT，防内存爆）和 maxOutputChars 作为**工具级预算**；registry 级预算（覆盖 MCP）默认 `DEFAULTS.toolResultMaxChars`（新常量，建议 24_000）。
- 修剪事件不进模型：在返回给 UI 的元数据里带 prunedChars（工具块可显示"已修剪 N 字符"）。

### 3.3 落盘：spill（超长全文保底）

修剪会丢信息；当被剪掉的量级太大时改为"全文存盘 + 引用"：

- 阈值：`prunedChars > SPILL_THRESHOLD`（建议 20_000 字符）时触发，`pruneToolResult` 返回 `spilled` 路径。
- 存储位置：`~/.ZQQ-harness/spill/<sessionId>/<n>.txt`（跟会话生命周期走；**会话彻底删除（purge）时连带删目录**——在 sessions.ts 的 purge 里挂钩）。目录/文件权限尽力收缩（Windows 下不做 DACL 细化，注明）。
- 入 history 的文本 = 头尾预览 + `\n[完整输出已存盘：<路径>，可用 Get-Content / Select-String 按需读取]`。模型有 pwsh，自己能读——这就是 DSH 检索提示的本项目版。
- **best-effort**：写盘失败 → 退回纯修剪结果，不报错（成功的工具调用不能因为存档失败变成错误）。
- UI 不受影响：agent 的 printToolResult 本来就传完整输出给前端展示（spill 只影响**入模型 history** 的内容，注意两处别搞混）。

### 3.4 压缩：compaction

#### 触发（三入口）

1. **pressure 自动**：每轮 `startTurn` 开头（请求派生前），`contextPressure() >= COMPACTION_PRESSURE` → 先压缩再跑轮。
2. **手动**：`/compact` 斜杠命令（Web 输入框已有斜杠命令管道）。
3. **overflow 兼顾**：provider 抛"上下文超限"类错误（openai 400 message 含 context length / maximum context；anthropic 同理）→ 捕获后自动压缩并**重试该轮一次**。这与现有 finishReason=length 警告不同：那是输出截断，这是输入放不下。

#### 算法

```
compact(history) →
  1. 锁：agent 正在跑轮则拒绝（busy 复用现有状态）；压缩期间禁新输入（现有 running 拦截）
  2. 选区间：保留 history[0]（system）+ 保留最近 PAST_KEEP_TOKENS（建议 30% 预算）的尾部完整轮次；
     切点 i 必须是"轮边界"——history[i] 为 user 消息，或其前一条为 tool 消息
     （保证 toolCall 与 tool 结果不被拆开，等价于 DSH 的配对平衡）
  3. 总结：用当前 provider 发一次**不带工具**的 chat，专用提示词：
     "把以下 agent 工作历史压缩为工作状态摘要，必须保留：用户目标、已做决定、
      涉及的文件路径与命令、当前进行到哪、未完成事项。输出中文。"
     （该调用**强制 `effort: "off"` 关思考**——辅助调用不付思考成本，DSH 的压缩/起标题调用同款做法，
      详见《开发文档-思考内容管理.md》§2.4）
  4. 替换：history = [system, {role:"user", content:"[历史摘要（系统压缩生成）]\n" + summary}, ...history.slice(i)]
     摘要消息永远不可能是"空消息"（防御性兜底文案，避开已知的空回复 400 坑）
  5. 落盘：SessionData.messages 同步替换 + 新增 compactions 记录：
     {at, cutIndex, summary, tokensBefore, tokensAfter}
  6. 解锁，UI 广播 compaction 事件（卡片：已压缩 N 条消息，上下文 X→Y tokens）
```

#### 失败处理（fail-safe，与 fail-closed 相反方向——宁可压不了不可压坏）

总结调用失败/超时/返回空 → **放弃压缩，history 原样保留**，UI 提示"压缩失败，会话未改动"。任何中间错误都不得破坏会话（会话中毒是本项目踩过的坑，压缩是新的中毒途径，必须防御）。

#### 不可逆性的缓解

DSH 靠事件日志可重建；本项目压缩是物理替换，不可撤销。缓解：压缩前把原 messages 写一份 `~/.ZQQ-harness/sessions/<id>.precompact-<n>.json` 备份（重启后手动可救），不做 UI 入口。注明这是与 DSH 的刻意取舍。

#### 与已知风险项的联动

记忆中的待核查项：V4.1 文档称带 tools 请求须回传全部 reasoning_content 否则 400（实测不回传也没事）。压缩恰好把老轮次物理移除，使"回传全部 reasoning_content"在压缩后**原则上不可能**——若未来真的出现 400，压缩后的会话是第一个现场，排查时先想到这层。**（2026-09-23 更新：思考回传已落地——openai 路线有 `REASONING_PASSBACK` 开关可随时置 on 合规，anthropic 路线 thinking 块自动回放；见《开发文档-思考内容管理.md》实施记录）**

### 3.5 验收

- 单测：msgTokens 缓存命中（用注入的假 tokenizer 计数次数断言）；pruneToolResult 三段/代理对/零预算边界；spill 往返（超阈值产生文件、内容可读、purge 清理）；压缩切点配对平衡（构造 toolCall 跨切点的 history 断言切点被推后）；压缩后 contextEstimate 下降且 system 保留；overflow 识别与一次重试；压缩失败不破坏 history。
- 手动：长会话跑 /compact，Web 出压缩卡片，后续对话模型仍记得早期目标（摘要生效）；purge 会话后 spill 目录消失。

## 4. 功能三：沙箱

### 4.1 模式（三档，存于会话）

```ts
export type SandboxMode = "read-only" | "workspace-write" | "danger-full-access";
```

- 默认 `workspace-write`（工作区 + 私有临时目录可写）——与用户当前使用习惯一致；`read-only` 供"只让模型查资料"场景；`danger-full-access` = 完全不约束（也不走审批，用户明示）。
- SessionData 加 `sandboxMode?: SandboxMode`（随会话存档/恢复，与 providerId/effort 同模式）；顶栏下拉 + `/sandbox read-only|workspace-write|full` 命令。

### 4.2 接缝（Phase A：零原生依赖，先立骨架）

新增 `src/sandbox/`：

```ts
// types.ts
export interface SandboxPolicy {
  mode: SandboxMode;
  workspaceRoot: string;
  privateTempDir?: string;      // workspace-write 时生成 ~/.ZQQ-harness/tmp/<sessionId>/
}
export class SandboxUnavailableError extends Error {}   // fail-closed 专用

// runner.ts
export interface SandboxRunner {
  available(): boolean;
  spawn(command: string, policy: SandboxPolicy, opts): ChildProcess;  // 包装 spawn
}
```

**Phase A 诚实话**：Node 原生 API 造不出受限令牌，所以 Phase A 没有 OS 级后端。Phase A 交付的是：

1. 模式状态机 + UI/命令 + SessionData 持久化；
2. **fail-closed 语义**：选择 `read-only` / `workspace-write` 而后端 `available() === false` 时，运行命令直接返回结构化错误：

   ```
   SANDBOX_UNAVAILABLE：当前平台没有可用的沙箱后端，无法保证 read-only/workspace-write 约束。已拒绝执行。
   可选：切换到 danger-full-access（无约束），或在设置中启用沙箱后端。
   ```

   绝不静默放行——这是与现状最大的语义反转（现状是守卫失败即放行）。
3. 过渡期标签：在 `danger-full-access`（以及未启用沙箱时的默认运行）下，UI 明示当前是"守卫+审批（启发式，非隔离）"。**在 Phase B 落地前，实际执行层仍是现有守卫+审批，守卫照常工作**——Phase A 不删守卫，只是把"守卫是什么"说清楚。

### 4.3 真隔离后端（Phase B：Windows 受限令牌，参考 DSH sandbox-windows-acl）

DSH 在 Windows 的方案（评估过 AppContainer 后放弃，选了更轻的 ACL 受限令牌），五段链照搬：

1. **受限令牌**：`CreateRestrictedToken`，对 `Everyone`/`Users` 的写权限位（FILE_WRITE_DATA/FILE_APPEND_DATA/FILE_WRITE_ATTRIBUTES/DELETE…）打 `DENY_ONLY`；
2. **Job Object**：`CreateJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（句柄关闭即杀整棵进程树）等限制，顺带解决"超时只杀 pwsh、孙进程残留"的已知问题；
3. **ACL 放行**：对工作区根 + 私有临时目录把写权限授给受限 SID（deny-then-grant：默认全禁写，再精确放行）；
4. **环境重定向**：`TMP`/`TEMP` 指到私有临时目录；
5. **执行**：`CreateProcessAsUser` 启动 pwsh 执行命令。

**实现载体选型（本项目约束：零构建、尽量纯 JS）**：

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **koffi（FFI，npm 预编译二进制）** | 无需编译器，纯 JS 引入；直接调 advapi32/kernel32 | FFI 样板代码多；依赖一个有原生二进制的包 | **首选** |
| 自带 helper.exe（C/Rust 预编译产物进 assets/） | 逻辑独立、可控 | 需要交叉编译与签名维护；用户无法自行重建 | 备选 |
| WSL2 整机隔离 | 内核级最强 | 改变部署形态，工作区要跨文件系统 | 作为文档级建议，不做集成 |
| AppContainer | 微软官方沙箱 | 配置重、profile 管理复杂（DSH 已放弃） | 不做 |

#### 已知边界（照抄 DSH 的诚实清单，写进 UI 与本文档）

- **只约束写，不约束读**：受限令牌挡不住"读工作区外文件"。这天然解决了守卫"按路径不分读写"的历史问题——沙箱模式下**读放行由 OS 兜底写**，守卫的读拦截可退役（见 4.4）。
- NTFS **硬链接**可跨路径别名同一文件，放行路径外的硬链接是漏洞。
- `NUL` 设备因 DACL 设计仍可写。
- **网络拒绝是 best-effort**（Job Object 不天然禁网）；需要断网请用容器/虚拟机。
- 未经安全审计；**不得作为对抗恶意代码的边界**，只防误操作（SAFETY 式声明，UI 关于页放同款文案）。

### 4.4 集成与守卫降级

pwsh.ts execute 的新流程：

```
command → [守卫 checkCommandAgainstWorkspace：产出 reasons（提示层，永远跑）]
        → 沙箱可用？
           ├─ 可用：confine 后执行；被拒 → 回传 "[sandbox: 工作区外写入被拒绝（workspace-write 模式）]" + 原样 stderr
           │        + 提示模型可带 justification 升级重试一次（走 2.4 审批）
           └─ 不可用：按 4.2 Phase A 的 SANDBOX_UNAVAILABLE 文案拒绝（除非 danger-full-access）
        → danger-full-access：直接执行（守卫 reasons 仅在 alwaysConfirm 时展示）
```

- 守卫降级为**审批理由生成器**：不再承担放行/拦截裁决（那归沙箱与模式），它的 reasons 继续喂给审批卡。Phase B 稳定前不删代码。
- MCP 工具仍不走沙箱（配置即信任，现状约定不变，文档明示）。

### 4.5 验收

- 单测：模式状态机与 SessionData 往返；SANDBOX_UNAVAILABLE 文案与触发条件；守卫降级后 reasons 仍产出。
- Phase B 真实执行测试（对齐 pwsh.test.ts 风格，跑真进程）：受限进程写工作区内成功 / 写 `%TEMP%` 外失败（Access is denied）/ 读工作区外成功 / 超时 kill 后无孙进程残留（Job Object 生效）。
- 手动：read-only 模式下让模型建文件 → 被拒 → 带 justification 升级 → 审批卡显示理由 → 批准后执行成功。

2. **压缩摘要质量**：摘要丢了关键路径/决定，模型后续会跑偏——提示词强调保留清单（§3.4），并依赖 precompact 备份兜底。
3. **spill 文件增长**：只增不删（除 purge）。开放问题：是否给 spill 目录加"30 天自动清理"？先不做，观察到问题再说。
4. **read-only 模式的真实需求度**：等 M4 落地后观察使用频率，再决定 Phase B 优先级（若 workspace-write 够用，M5 可延后）。
5. **reasoning_content 风险项**：见 §3.4 联动说明；压缩功能上线后该风险的表现面会变化。
6. **README 过时**：本次一并把 README.md 改写为 Web UI 现状 + 指向本文档（或单独任务）。
