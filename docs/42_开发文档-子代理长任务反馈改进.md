## 1. 各项设计要点

### 1.1 run_pwsh 超时（A1/A5）

**根因（实测）**：无约束路径用 `child.kill()`，在 Windows 上只 `TerminateProcess` 直接子进程（pwsh）。它启动的脚本成为孤儿，还攥着继承的 stdout 管道——Node 的 `close` 要等它退出才触发。对照实验（`docs/42` 实施时跑）：4 s 超时 + 睡 20 s 的孙进程，旧实现 **21.2 s** 才返回且 `exit code: unknown`，新实现 **4.3 s** 返回。这正是反馈里「300 s 超时后 exit code: unknown」的完整机制。

- `killTree`：`taskkill /PID <pid> /T /F`（SystemRoot 绝对路径，不依赖 PATH、不给工作区同名程序可乘之机），失败回落 `child.kill()`。沙箱路径本就有 Job Object 杀树，不改。
- 回执：超时行说明「进程树 PID 已一并终止 / 以上是超时前已捕获的输出 / 可能留有半成品 / 拆小步或调大 pwshMaxTimeoutMs」。
- `PYTHONUNBUFFERED=1`：Python 接管道/文件时块缓冲（实测 `line_buffering=False`），被杀时缓冲区里的进度全丢。两条执行路径都设（沙箱路径与 TMP/TEMP 同款「改→创建→还原」同步窗口）；宿主已显式设置则尊重。
- `stripAnsi`：只作用于入模型文本。

### 1.2 图像块常驻与图片预算（A2；用户评审后的修订）

**评审结论（用户）**：图片应保留在上下文——初版的「看过即退役」撤销。理由两条：

1. **缓存**：每次退役都让前缀缓存从那张图所在消息起失效。范围只是其后一两轮（不大），但读图密集时几乎每轮都触发。常驻时图像块落在缓存前缀里，按缓存命中价重放，不产生失效。
2. **回看**：退役后模型没法再看（改完图想对照前一张时已经不在了）。

**终版口径（参照 DSH）——只有三种情况图片不进请求：**

| 情况 | 行为 | 性质 |
|---|---|---|
| 自动压缩 | 被摘要替换区间里的图随消息移除，保留尾部的图照常携带。`COMPACTION_PROMPT` 补「含查看过的图片文件路径」——read_image 的结果文本带路径，摘要保住路径，模型可按路径重读 | 既有行为；补提示词与回归用例 |
| 图片预算超限 | 同时留在上下文里的图片超过 `imageContextMaxCount`（缺省 40 张）或 `imageContextMaxBytes`（缺省 16 MiB），任一超限 → 把**最早的图永久换成占位文本**，之后不再发送 | 新增 |
| 纯文本模型 | 请求里带图消息只发文本 + 省略说明（`imageOmittedNote`）；历史不动，换回视觉模型即恢复（被预算移出的除外） | 新增（此前会把图原样发给纯文本模型） |

工具结果剪枝只剪文本、图像块保留——既有行为，补了回归用例。

**预算的实现要点**（`Agent.enforceImageBudget`，每次请求前调用）：

- 一张图 = 一个移出单位，同一条消息里的图可以只移一部分（用户一次贴 4 张、预算 2 张 → 只移最早的 2 张）。
- 移出顺序：① 已看过的工具读图（可按原路径重读）→ ② 未看过的工具读图 → ③ 用户贴图（不能按路径重读，排最后）。用户贴图占满预算时，新读的工具图会被移出——占位说明里写明「预算仍被占满时重读还会被移出」，免得模型反复重读。
- **成批移出**：① 档一次移到预算的 75%（`IMAGE_BUDGET_TARGET`）。缺省 40 张时，读到第 41 张移出 11 张回到 30 张，之后每再读 11 张才触发一次。② ③ 档只移到硬预算。
- 只在视觉会话执行（`deps.vision`）：纯文本会话不发图，没有超预算可言，也不该因为换了模型永久丢图。
- 「已看过」= 消息下标小于 `seenLen`（最近一次成功请求时的历史长度）；restore / compact 之后重置为当时的历史长度。

**权衡（如实）**：图片常驻后，读图多的任务上下文涨得比退役版快，压缩会来得早一些——这是用户的明确取舍（要回看能力与缓存稳定）。代价的另一面是：预算移出的是最早的图，一次就让前缀缓存从那条起**整段失效**，比退役的一次失效大得多——所以宁可成批、低频触发。请求载荷由字节预算兜住（16 MiB 解码后 base64 约 21 MiB）。

**被移出的用户贴图**：界面按历史重渲染（重开会话/刷新），移出后那几张图不再显示，原消息下方留有移出说明。工具读图本来就不在界面渲染图片，无界面变化。

### 1.3 进展快照与预警线提示（B1/B3）

- `core/progress.ts`（纯函数，无 IO）：`toolEventsOf`（调用与结果按 id 配对）/ `toolOk`（run_pwsh 只认 `exit code: 0`）/ `progressFactsOf`（写入/读取/已看图路径、最后成功的命令、最近 3 个动作带成败、最后留言）/ `progressDigestOf` / `providerLimitOf`。
- B3 根因：旧 `toolCallDigest` 在没有 path 时回退取「第一个字符串参数」，把 `new_string` 源码当路径。新实现**拿不到 path 就只报工具名**。
- 快照随存档 meta 落盘（`subagent.progress`），旧档缺省 = 无。
- `AgentDeps.contextWarn`：占用越过 `subagentWarnContextPct` 时向历史注入一次系统提示（与轮次上限收尾提示同形），每个 Agent 生命周期至多一次；worker 装配时注入。

### 1.4 唤醒简报与台账回填（A3/B2）

- A3 根因：`readerLedger` 的 per-reader 快照随旧实例消亡，复活的新实例「本 reader 上次所见」为空。
- `rehydrateLedger`：历史里成功读过/写过的路径中，**mtime ≤ 上次活动时刻**的按当前指纹回填；**变过的绝不回填**（可能是别的实例改的）。写入时的 hash 乐观锁照旧兜底。
- `wakeBriefOf`：塞在任务书前。在线待命实例追加任务也走（只报变动、不回填——它的台账完好）。
- `filesChangedSince`：有界扫描（2 万条目 / 12 层，跳过 node_modules、.git 等），按 scope 过滤。
- 简报不往工作区写任何文件。

### 1.5 派发回执附注（C5/B4）

- `dispatchNoteOf`：①同范围已有待命/归档且留有存档的实例 → 「优先 agent_followup 唤醒而非新派」；②当前并发 N/上限；③近期限流。**只提醒不拦截**。
- `scopesOverlap`：目录级前缀比对；**任一方未给 scope 不提示**——旧记录不带 scope，按「整个工作区」比会让每次派发都撞上历史记录。

### 1.6 限流可见性（B4）

- `providerLimitOf` 从错误文案归类：速率限制（rate）/ 用量上限（cap）；认不出不臆测。
- 失败报告按类给建议；`rt.subagentLimits` 瞬态记录（不入档）；`subagent_status` 表尾与派发附注可查。

### 1.7 read_archive 摘要版（B7）

`summary=true`：任务书（截 300）/ 助手说明（截 400）/ 操作索引（每个调用一行 + 成败）/ 进展速览。完整版不变。

### 1.8 只读子代理（A6）

`readOnly: true` → `mountWorkerAgent` 不装 `write_file`/`edit_file` 与 MCP 工具（MCP 不走沙箱，装了就无法保证只读）；`run_pwsh` 的 `modeOf()` 钉死 `read-only` 且不走升级链路；系统提示加 `READONLY_ROLE_SECTION`；文件工具对 `ctx.readOnly` 仍硬拒（纵深）；标记随记录与存档 meta 保存，复活时还原。

### 1.9 提示词（C1–C4、B5、D2、E）

- 协调者 base：任务书自检四条（依赖已就绪 / 并发与调用预算 / 命名与临时目录 / 关键语义）；冲突预防补「接手同一写入范围前先确认原实例已归档或停止，用户要求保留原实例时不要另派新实例」；工具参考同步 readOnly、唤醒简报、`read_archive summary=true`、状态表限流行。
- worker 职责段：长任务留痕 / 读图节制 / 调用预算 / pandas 取列。
- golden 快照逐字节同步（`contract.test.ts`）。

## 3. 不变量与注意

1. **家族哨兵升为八文件**：`subagents.ts` / `subagent-worker.ts` / `subagent-report.ts` / `subagent-archive.ts` / `subagent-records.ts` / `subagent-status.ts` / `subagent-brief.ts` / `subagent-mcp.ts` 各 ≤400 行。两次纯移动就是为了守住它——往这几个文件加东西前先看余量（当前最大 352）。
2. **预算移出必须新建消息对象**，不得原地删字段（缓存与锚点都按对象身份）；移出后 `usageAnchor` 置空。
3. **台账回填的判据是 mtime ≤ 基准时刻**：外部进程改回同 mtime 会漏判，所以它只用于「免重读」，写入时的 hash 乐观锁不因此放松。
4. **基准时刻取在文件写入之后的下一个事件循环之后**（收尾时 `Date.now()`）：文件 mtime 是操作系统实时钟，同一 tick 内 `Date.now()` 可能仍是 tick 开头的缓存值（测试里踩过）。单测要显式把 mtime 压到过去。
5. **简报的 root 为空必须直接返回**：空串会被 `resolve("")` 解析到进程 cwd 去扫盘。
6. **沙箱路径还原 `PYTHONUNBUFFERED` 必须 `delete`**：`process.env.X = undefined` 会写成字符串 `"undefined"`（源码哨兵锁定）。
7. **提示词改文案 = golden 显式同步**：`sections.ts` 与 `contract.test.ts` 两处逐字节镜像。本轮用「同一份 JSON 喂两个文件」的方式保证一致。
8. **上下文占比带状测试对固定部分敏感**：worker 提示词每多一行都会让它们漂移（本轮窗口 2000 → 3000、任务书长度重标定）。再改 worker 提示词时预期要重标。
9. **预算移出的缓存代价远大于退役**：移的是最早的图，前缀缓存从它所在那条起整段失效——① 档成批移到 75% 就是为此，不要改成「刚好回到预算」（每读一张移一张 = 每轮整段失效）。
10. **`seenLen` 必须随 restore / compact 重置**：否则恢复档与保留尾部里的图全被当成「未看过」，① 档永不触发，预算形同虚设。
11. **tokens 的逐对象缓存不区分注入的计数函数**：同一条消息对象不要先按注入计数器数、再按真实分词器数——省略口径的用例要另建新对象（测试里踩过）。
12. **受限进程不能用管道抓子进程的输出**（2026-11-24 真机实测；受限令牌下建管道被拒，机制未细究）：R 的 `system2(stdout=TRUE)` 报 `CreatePipe failed`、Python 的 `subprocess` 管道（`capture_output=True` / `stdout=PIPE`）报 `PermissionError [WinError 5]`、Node 的 `spawn` 管道报 `EPERM`。替代写法都正常：让子进程把输出写文件再读、或不抓输出（继承 stdio）；R 的 `parallel::makeCluster`（走 socket）正常。`run_pwsh` 按 stderr 特征把这类失败单列成「管道限制」回执（`PIPE_REFUSED`）——不走升级链路、不攒升级额度（Python 那条的「拒绝访问」此前会被判成区外写入被拒，把模型引向申请解除沙箱）。

## 4. 顺带修掉的两个旧缺陷

1. **`VISION_LINE_WORKER` 第三句从未进入提示词**：第二行行尾缺 ` +`，被 ASI 截成 `const X = "a" + "b"; "c";`——「view_image 是给无视觉模型的借视觉通道…」一直是死代码。测试快照有同样的写法所以从未暴露。已补 ` +` 并修正快照。**视觉会话的 worker 系统提示因此多了一句话**（docs/34 的原意）。
