## 1. P1（P0 bug）：停止无法中断运行轮——审批卡挂起死锁

### 1.1 现象

协调者会话 busy（worker 运行中）按「⏹ 停止」后：轮次不结束、按钮一直是停止、busy 状态不变；期间该会话的设置修改/压缩/发消息全部 409（「无法进行其他操作」的主体）。切到别的会话不受影响（多会话并行语义正常）。

### 1.2 根因（已定位，代码证据）

**stop → 审批卡的链路缺一环：`doAsk` 的 promise 只能被 `/api/approval` 决议或轮结束清理收尾，而轮结束清理又依赖工具返回——工具正在等这张卡 → 循环等待。**

完整链条（符号名定位）：

1. `startTurn`（`src/web/session-lifecycle.ts`）：`rt.abortCtl = new AbortController()` → `rt.agent.run(text, rt.abortCtl!.signal)`；**finally 里才有** `if (rt.pendingApproval) rt.pendingApproval("cancelled")`——即「取消挂起的卡」只发生在轮结束之后。
2. `/api/stop`（`src/modules/web-sessions/index.ts`）：只做 `rt.abortCtl?.abort()`，**不触碰 rt.pendingApproval**。
3. abort 信号的可达范围：`Agent.run`（`src/agent.ts`）把 signal 传给 provider.chat 与工具 `ctx.signal`（正常）→ agent_task/agent_tasks 透传给 worker（`src/modules/tools/agent-task/agent-task.ts` 的 `svc.run(parsed, ctx.signal)`）→ worker 的 pwsh/LLM 调用都能被中止（`runPwsh` 有 `opts.signal` → Job Object kill；`src/web/subagents.ts` 的 sig 合并）。**这条链本身是通的**（SA3 冒烟第 6 项验证过 abort 级联）。
4. **断点在审批**：`requestApprovalFor`（`src/web/session-runtime.ts`）的 `opts.signal?.aborted` 检查只在**排队项发起前**做一次（「队列快速排空」语义）；`doAsk`（同文件）设置 `rt.pendingApproval` 后返回的 promise **没有任何 abort 监听**——正在等的卡对 abort 完全无感。
5. 于是：worker 的工具 await 审批 promise → agent_tasks await 全部 worker → agent.run await 工具 → startTurn await agent.run → finally（取消卡）永远到不了。**只有用户手动点掉卡片（/api/approval）才能解锁。**

**注意：这是普通会话同病的既有缺陷**（普通会话按停止时若有卡在等，同样挂住，只是普通轮次短、用户顺手就把卡点了，不易察觉）；协调者场景 worker 长任务 + 卡片不显眼，把缺陷放大成「完全卡死」。**同修，不是只修协调者路径。**

### 1.3 修复方案（推荐）

在 `doAsk` 上挂 abort 监听（`requestApprovalFor` 已持有 `opts.signal`，把它传给 `doAsk` 或在 `askOnce` 包装层监听）：

```ts
// session-runtime.ts · doAsk(sh, rt, req, signal?) 内部：
function doAsk(sh, rt, req, signal?: AbortSignal): Promise<ApprovalDecision> {
  return new Promise((resolveP) => {
    rt.pendingApproval = (decision) => { /* 现有逻辑：清槽+审计+resolveP */ };
    rt.auditEvents.push(auditAsked(rt.auditEvents, req));
    sh.broadcast(SSE_EVENTS.approval, { sessionId: rt.id, ...req });
    // 新增：等待中的卡随中止信号立即取消（决议走既有 cancelled 路径，审计自然记录）
    signal?.addEventListener("abort", () => rt.pendingApproval?.("cancelled"), { once: true });
  });
}
```

要点：

- **决议语义零新增**：abort 时走的就是现有 `pendingApproval("cancelled")` 通道（审计记 decided/cancelled，worker 收到 cancelled 后按现有「被取消」文案自寻出路，fail-closed 不破）；
- 监听器 `{ once: true }`；卡片被正常决议后 `rt.pendingApproval` 已清为 null，迟到的 abort 触发是空操作（`?.` 保护）；
- 前端不用改：cancelled 决议后轮次随即收尾，`turnEnd` 既有逻辑隐藏卡片（`$("#approval").classList.add("hidden")`）；若想更跟手可在 approval 事件或 state 里带「已取消」提示，非必需；
- 排队中的卡已被现有 `signal.aborted` 前置检查覆盖，无需重复处理。

**次要（可选，不建议本次做）**：busy 期设置/压缩 409 是 docs/4 既有语义（防轮中变更撕裂状态），修好 P1 + P3 的可见性后体验问题基本消解；如确要放宽（如允许 busy 中切 effort），单独立项评估。

## 2. P2：worker 调用 MCP 弹权限确认（普通模式正常）

### 2.1 结构事实（先读这个，再核实）

**worker 目前根本没有 mcp__ 工具——这是 D3 定案（docs/5 偏差 19，SA4 审计后显式决定「不带」）。**证据链：

- worker 的 ToolRegistry 在 `runWorker`（`src/web/subagents.ts`）里从 `sh.ctx.tools.all()` 装配（过滤 coordinator 受众）——这是**系统工具注册表**（6 个 worker 工具）；
- MCP 工具的注册路径完全不同：`McpManager.apply(cfg, cfg, registry)`（`src/mcp/manager.ts`）把 `mcp__<server>__<tool>` 注册进**传入的那个 registry**——即各会话自己的 `rt.registry`；协调者会话的 createRuntime/bindWorkspace 两处都跳过 mcp.apply（偏差 6），所以协调者会话生命周期内不存在任何已连接的 MCP；
- worker 系统 prompt 的 `mcpInstructions: null`（runWorker 装配 Agent 时显式置空），mcp 段不渲染——worker 连「有 MCP 可用」的提示都没有；
- 因此 worker 若幻觉调用 `mcp__xxx`，得到的是「未知工具」错误（`registry.executeWithMeta` 的报错文案），**不会弹审批卡**。

**推论**：用户看到的「子代理调用 mcp 弹权限确认」必然是 worker 用 `run_pwsh`/文件工具**绕行**模拟 MCP 查询（比如 npx 启动 MCP 服务器 CLI、curl 端点、直接读文献库文件），命中了 pwsh 守卫（工作区外路径/scope 越界——`pathHintsOutsideScope` 命中即强制弹卡，danger 模式也弹）或写入裁决（区外/scope 外写入）。审批卡带着 `[子代理 name]` 前缀 + 命令原文，用户把命令内容读成了「调 mcp」。**普通会话没这问题是因为普通会话直接调 mcp__ 工具（信任模型，不走审批）。**

### 2.2 核实步骤（动手前先做，5 分钟）

用户的会话存档里有全部证据——审批审计事件带命令原文与 reasons：

```bash

    try: d = json.load(open(f, encoding="utf8"))
```

### 2.3 修复方向

**路线 A（推荐）：给 worker 接真 MCP——会话级「worker 专用 McpManager」**（相当于把 D3 从「不带」改为「worker 带、协调者仍不带」；transport 层并发安全已在 SA4 审计通过——docs/5 偏差 19，按 id 配对派发，多路并发安全）：

- 挂载点：`SessionRuntime` 加可选字段（如 `workerMcp?: McpManager`），**懒加载**——首个 runWorker 启动时 `new McpManager(ctx.mcpTransports)` + `apply(loadMcpConfig([sh.globalMcpFile]), loadMcpConfig([join(w.root,"mcp.json")]), workerRegistry)`；连接与工具清单为会话内全部 worker 共享（每 server 一个进程，不是每 worker 一个）；
- worker 装配（`runWorker`）：`workerMcp.apply(...)` 的目标 registry 就是该 worker 新建的 registry（McpManager.apply 自己管理 registered 清单与 stopAll——注意它是「一次性 apply 到一个 registry」的形态：要么每个 worker apply 到自己 registry 但**共享连接**（需要小改 manager 支持多 registry 或抽 connect 层），要么 worker 共享一个已 apply 的「模板 registry」再复制工具定义。**实现时先审 `McpManager.apply/stopAll/toTool` 的形状再定**，别硬塞；
- worker 系统 prompt：`mcpInstructions` 从该 manager 的 `instructionsText()` 取（worker 是 sessionKind=normal，mcp 段照常渲染——worker 有权知道 MCP 用法）；
- **红线**：coordinator 自己的 `rt.registry` 仍然只有 agent_task/agent_tasks、系统提示仍无 mcp 段（偏差 6 的语义是「协调者不装配」，不禁止 worker；三条冒烟脚本的「registry 仅两件」断言别破）；
- 生命周期：会话运行态存续期间保持连接（与普通会话 rt.mcp 同等待遇）；worker 的 `reloadMcp` 降级文案可顺带升级为重载这个 manager（可选）；
- 审批语义：MCP 工具信任模型与普通会话一致（不走审批）→ 用户报告的弹卡自然消失（前提是 2.2 核实结论确为 pwsh 绕行）；
- README/docs 口径更新：已知限制「子代理不带 MCP」条目改为新语义；docs/5 偏差 19 追加修订记录。

**路线 B（若核实发现根因不是绕行）**：按核实到的真实根因修（例如确实是 scope 守卫误伤合法路径 → 调 `pathHintsOutsideScope` 启发式；例如是文献库路径在工作区外本就该弹 → 属预期，改文案/文档）。

### 2.4 测试与验收

- 单测：worker registry 含 `mcp__` 工具（桩 transport）；coordinator registry 仍仅两件（现有断言保持）；懒加载只建一次 manager；worker prompt 的 mcp 段渲染；

- 真机：文献库 MCP 工作区，协调者派「查文献 X」worker → 直接调 mcp__ 工具、**不弹卡**、报告返回。

## 3. P3：无法查看子代理的内容（worker 过程可见性）

### 3.1 现状（设计如此，属增强而非 bug）

- worker 的 AgentUi 是 no-op（`runWorker` 装配），中间过程（思考流/工具调用/中间文字）**有意不穿透前台历史**（docs/5 D8：前台上下文最小化是两层架构的意义）；
- 目前可见面只有：①agent_task(s) 工具块的**时间线一行/worker**（SA4：spawned→done/error，`.subs-line`）；②工具块展开后的**合并最终报告**（`formatWorkerResult`，`[i/N] name\n[子代理 x 完成] …\n---\n报告全文`）；③`/status` 的审计计数；④超长报告的 spill 全文在 `~/.ZQQ-harness/spill/<sessionId>/sub-<seq>-<name>/`（无 UI，只能手工开文件）。
- 用户要的是「看 worker 在干什么/干了什么」——过程级可见性。

**快速缓解（先告知用户，零代码）**：工具块头部点开即可看合并报告全文；spill 文件路径在报告尾部标注。

### 3.2 方案选项

**方案 A（推荐先做）：worker 全程 transcript 落盘 + 前端查看入口**

- 落盘：`runWorker` 收尾时（`finishSubagent` 附近）把 `worker.agent.messages`（标准 ChatMessage[]，含思考块与工具调用/结果）best-effort 写 `spill/<sessionId>/<dirTag>/transcript.json`（失败不影响结果返回；目录已存在，零新机制）。可与 SubagentRecord 联动：记录里加 `transcript?: string`（相对路径），currentState/存档自然携带；
- 读取 API：web-sessions 模块加只读路由（如 `GET /api/subagent-transcript?sessionId=&subId=`，校验 sessionId 为 UUID + subId 为数字 + 路径拼接待过 `sh.sessions.spillDir` 收口，防穿越）；返回 `{ messages }`；
- 前端：时间线行（`.subs-line`）done/error 状态追加「📄 过程」链接 → fetch 上述 API → 弹模态（复用现有 `.modal` 样式）渲染。渲染可先做朴素版（按消息角色列出：思考折叠块复用 `addHistoryThink` 思路、工具调用复用 `addTool/addToolRes` 思路、正文 `mdLite`）；刷新后仍可看（文件在盘上），**满足「事后查看」**；
- 不变量：worker 过程仍不进前台历史/上下文（transcript 只在用户主动点开时进 UI，不进模型）。

**方案 B（后续增强，可与 A 共存）：实时过程流**

- 扩展 SSE `subagent` 事件：`phase: "tool" | "toolResult"`（带 subId/name + 截断版文本，如各 500 字符），worker 的 no-op UI 里 `printToolCall/printToolResult` 改为向父会话广播这些事件（注意 makeUi 的 ml 锚点不适用于 worker——不带 ml，走缓冲重放即可）；
- 前端：时间线行下挂按 subId 分组的可折叠过程区（复用 `.think` 折叠样式）；
- 契约三端同步自动由 contract.test 把关（事件名不变，只是 phase 扩值——`core/events.ts` 注释同步更新）；
- 事件量控制：文本截断 + 只发 tool 级不发 delta 级；
- A 的 transcript 落盘同时是 B 切换会话/刷新后的重放数据源。

**不推荐的路线**：worker messages 进前台历史（违背两层架构初衷）或全量进 SessionData（存档膨胀）。

### 3.3 测试与验收

- A：单测——transcript 落盘（成功/写失败不影响结果）；API 路径校验（非法 id 拒绝）；SubagentRecord.transcript 字段往返；冒烟/浏览器端到端——跑完 worker 后时间线行有「📄 过程」，点开可见其工具调用与报告，刷新后仍在；
- B（若做）：契约注释更新 + 前端分组渲染 + 缓冲重放不串块（subId 配对，参照 toolBlocks 的 callId 模式）。
