## §1 问题①：新建/切换对话卡顿——现状链路与根因

### 1.1 用户可感知路径与代码链路

**点击工作区行**（`sidebar.js wsHeadNode` click → `POST /api/workspace`）→ `modules/web-workspaces/index.ts:45`：

```
host.persistSession(cur)            // 归档当前对话（无消息时空转，不落盘）
await host.newSessionForView(p)     // ← 阻塞点 D（MCP 连接）+ 触发下列全量读盘
  └ session-lifecycle.ts newSessionForView
     ├ await createRuntime(...)     // 重量级装配（见 1.3 根因 D）
     ├ sessions.prependOrder        // 写 order.json（小文件，可忽略）
     ├ sessions.save(空占位)         // 写盘一次（可忽略）
     └ sweepEmptySessions(sh)       // ← 阻塞点 A（全量 list()）
broadcast sessions → sessionsPayload // ← 阻塞点 A ×2（listAllGrouped + listRecycled 各一次 list()）
broadcast state → currentState      // contextEstimate 有逐消息缓存，可忽略
```

**点击会话条目**（`switchSession` → `POST /api/sessions/load`）→ `switchView`：目标不在内存时 `createRuntime`（根因 D）+ `broadcast sessions`（根因 A）。

**＋新对话**（`POST /api/sessions/new`）→ `newSessionForView`：同上。

### 1.2 根因 A（主因）：`SessionStore.list()` 每次全量读盘 + 全量 JSON.parse，且是**同步 I/O**

`web/sessions.ts list()`（:155）遍历 sessions/ 目录，对每个 `.json` 文件 `readFileSync` + `JSON.parse` **完整 SessionData**——含全部 messages（工具结果全文、base64 图片）。会话文件单份数百 KB～数 MB、几十个会话时，一次 list() 即几十～几百 MB 的解析量。而一次「点击工作区」触发 **4 次 list()**：

| 调用点 | 次数 |
|---|---|
| `sweepEmptySessions`（newSessionForView 内） | 1 |
| `sessionsPayload → listAllGrouped` | 1 |
| `sessionsPayload → listRecycled` | 1 |
| web-workspaces handler 里 `broadcast("sessions", sessionsPayload())` | 2（又一轮 listAllGrouped+listRecycled） |

readFileSync/JSON.parse 全部在**事件循环上同步执行**——期间 SSE 推流（正在跑的会话的 delta）、其他 HTTP 请求全部停摆。**这就是"有会话在跑时（此时会话文件大、且用户能感知到流卡住）切换特别卡"的构成**。会话少/小时不卡，符合"有工作的对话时才卡"的反馈。

### 1.3 根因 D（次因）：`createRuntime` 串行 await MCP 连接

`session-runtime.ts createRuntime`（:439）对普通会话 `await rt.mcp.apply(...)`——每个 MCP 服务器 stdio spawn + initialize 握手（超时 20s，正常也要几百 ms～数秒）。它被 `newSessionForView`/`switchView`/`bindWorkspace` await，导致 `POST /api/workspace` 的**响应延迟 = 全部 MCP 服务器连完**——前端点击后要等广播+响应才见到新会话。且**每个新会话各自新建 McpManager 重连全部服务器**（无跨会话复用），频繁新建对话时反复握手。

### 1.4 次要因素

- **空占位堆积与清扫**：每次点工作区都新建空会话并存档（"创建即存档"设计），被切走的空档靠 `sweepEmptySessions` 全量 list() 清扫——反馈里"之前的空白对话消失"正是它。行为本身合理，但每次点击都付出 1.4 的装配 + 清扫成本。
- `switchView` 装载磁盘会话返回**全量 messages**（含图片 base64），前端 `renderHistory` 全量重建——切换大历史会话的固定成本（低频、一次性，本路线不动；docs/26 §8 已豁免 renderHistory 的 keyed 化）。

### 1.5 修复方案（P1）

| 编号 | 改动 | 收益 |
|---|---|---|
| **P1-1** | `SessionStore` 会话元数据**内存缓存**（`Map<id, SessionMeta>`，构造时全量建一次；save/delete/purge/restore/recycle 写路径增量维护） | list() 从 O(全盘读+全量 parse) 变 O(内存遍历)；一次点击 4 次 list() 全部命中缓存 |
| **P1-3** | MCP 连接**异步化**：`createRuntime`/`bindWorkspace` 不再 await `mcp.apply`（fire-and-forget + per-session ready promise）；连接完成后 `agent.setMcpInstructions` + 广播 state；`startTurn` 开跑前 `await rt.mcpReady`（防首轮缺 mcp__ 工具/说明） | 新建/切换会话的 POST 立即返回；MCP 握手并行进行，首轮消息最多等握手完成（与现状相同的工具可见性保证） |
| **P1-4** | **空占位换绑**：`POST /api/workspace` 时当前查看会话尚无任何用户消息 → `bindWorkspace` 就地换绑（不新建、不触发清扫）；配套 `removeFromOrder([id])` 清掉旧工作区 order 键 | 反复点工作区不再反复 createRuntime+存档+清扫；"空白对话消失"语义不变（就地覆写） |

**明确不做**（记录取舍）：
- 跨会话 MCP 连接池——生命周期管理复杂（会话删除时不能误停别人在用的连接），握手本身已被 P1-3 移出关键路径，收益/风险比不划算。
- `renderHistory` 增量化——无稳定消息级 id（docs/26 F3 豁免先例），且是低频一次性成本。
- 缓存与磁盘外部修改的一致性：用户手改 sessions/*.json 文件在缓存下要到重启才可见（旧行为每次读盘自愈）。正常使用全部经 API（写路径同步维护缓存），可接受；文档化。

## §2 问题②：子代理界面与主对话的体验差距——现状与根因

### 2.1 用户诉求清单

1. 子代理**思考实时展示**（主对话有思考流，子代理没有）；
2. 子代理**文字实时增量展示**（目前运行中详情页靠 1.5s 轮询全量重拉）;
3. 读写编辑工具**展示文件名**；
4. `write_file` 展示**写入的内容**（而不是参数 JSON）；
5. `edit_file` 展示**删除行/新增行的红绿 diff**；
6. （补充反馈）工具块**折叠态一行摘要**：`run_pwsh` 只显示 description、读/写/编辑显示「读/写/编辑某文件」——展开才见具体内容。**该条同时适用于主对话与子代理时间线**（统一体验）。

### 2.2 现状与根因

| 诉求 | 现状 | 根因位置 |
|---|---|---|
| 思考/文字实时 | **完全没有**：worker 的 `printReasoningDelta`/`printTextDelta` 是空函数（`subagent-worker.ts makeWorkerUi:194-195`），当初是"方案 B 事件量控制——只发 tool 级不发 delta 级"的取舍 | 后端 UI 缝 |
| 运行中详情页 | 每 1.5s 轮询 `/api/subagent-transcript` 拉全量 messages + `JSON.stringify` 比对 + 整体重建（`drawer.js pollLiveDetail`）——能看，但 granularity 是 1.5s 且闪烁感来自全量重建 | 前端 |
| 工具块摘要 | 主对话与抽屉时间线的块头都是 `⚙ 工具名 + firstLine(参数JSON)`（`chat.js addTool:130`、`drawer.js appendToolCall:694`）——pwsh 显示一长串 JSON，读写编辑看不出针对哪个文件 | 前端渲染 |
| write/edit 展开体 | 统一是 `prettyArgs(参数JSON)` 代码块（`targs` pre）——write 的内容埋在 JSON 转义里，edit 看不出删了什么加了什么 | 前端渲染 |
| 实时路径缺完整参数 | 实时 `tool` 事件只带 `preview`（`previewArgs` 截 160 字符，`agent.ts:91`）——前端即使想渲染 diff/全文也没有完整 old_string/new_string/content。历史渲染路径有完整 `tc.arguments` | **协议缺口** |

### 2.3 方案（P2）

**协议层**（后端）：
- **P2-1 worker delta 节流广播**：`makeWorkerUi` 实现思考/文字增量缓冲，每 ~120ms 合并 flush 为 `subagent` 事件新 phase `"delta"`（`{ sessionId, subId, name, phase:"delta", kind:"reasoning"|"content", text, ml }`）。`ml` = flush 时 worker agent 历史长度——**与主对话 delta 同款锚点**，切回重放经既有 `filterByMl` 自动去重。工具调用/结果事件前**同步强制 flush**（保证思考先于工具块的显示顺序）。120ms 合并把事件量降 1~2 个数量级，视觉上仍是逐字流。
- **P2-2 tool 事件携带完整参数**：`AgentUi.printToolCall` 增加可选第 4 参 `args`（完整参数 JSON 串）；`agent.ts` 调用点透传 `call.arguments`；`makeUi`（主对话）与 `makeWorkerUi`（子代理）广播时截断到 `TOOL_EVENT_ARGS_MAX_CHARS`（新前端显示协议常量，config.ts 导出，默认 20k，与前端 `CFG.TRUNC_TOOL_FULL` 对齐）。历史渲染路径不变（消息里本就有全量）。

**前端渲染层**：
- **P2-3 新纯逻辑模块 `app/toolinfo.js`**（入 F1 纯逻辑集合，可单测）：
  - `toolHeadline(name, argsRaw, fallbackPreview)` → 折叠行摘要：
    - `run_pwsh` → `description`（缺省退回 command 首行）
    - `read_file` → `读取 <path>`（带 offset/limit 时附 `· 行 N-M`）
    - `write_file` → `写入 <path>`
    - `edit_file` → `编辑 <path>`
    - 其他工具 → `firstLine(fallbackPreview)`（现状不变）
  - `toolBodyBlocks(name, argsRaw)` → 展开体片段序列：
    - `write_file` → `[{ type:"content", text }]`（只显示写入内容；附 description 注记行）
    - `edit_file` → `[{ type:"diff", oldText, newText, note? }]`（occurrence/replace_all 注记）+ 通用参数块（无 diff 可解析时退回）
    - `read_file`/其他 → `[{ type:"args", text: prettyArgs }]`（现状）
    - argsRaw 解析失败（截断/非法 JSON）→ 全部退回现状展示（args 块 + preview 头）
  - DOM 渲染器 `renderToolBody(container, name, argsRaw)` 放 `dom.js`（视图底层，chat/drawer 共用，遵守 drawer 不 import chat 的分层）
- **P2-4 消费点接线**：
  - `chat.js addTool`：块头 `tprev` 用 `toolHeadline`；`tblock-b` 首段由 `renderToolBody` 生成（替换原 `targs` 直填）。`main.js` SSE tool 处理器传 `d.args ?? d.preview`。
  - `drawer.js makeTimeline.appendToolCall`：同款（历史路径 `tc.arguments` 全量；保底视图 `s.args ?? s.preview`）。
  - `drawer.js onSubagent` 新增 `phase:"delta"` 处理：详情页正看该 subId 且 run 态 → 时间线尾部增量渲染（think live 块 / answer 块，同主对话打字机语义；tool 事件到达即折叠思考=「完成即收起」）；详情页没开则丢弃（切回时由 transcript 全量补齐，无重复）。
  - 运行详情页轮询从 1.5s 降频到 4s（**兜底校正**：事件丢失/渲染漂移时自愈；事件流为主路径）。
- **P2-6 CSS**：`.tdiff` 红绿行（`-` 红 `+` 绿，半透明底色适配暗色主题）、`.wbody` 写入内容块（复用 tres 滚动样式）。

**数据流自洽性说明**（防重复渲染的锚点设计）：运行详情页有两个数据源——事件流（增量、实时）与 transcript 轮询（全量、权威）。轮询返回 `JSON.stringify(messages)` 与上次相同→不重建→增量元素留存；不同→全量重建覆盖增量元素（内容一致，无重复）。worker delta 带 `ml` 后，切走再切回的缓冲重放经 `filterByMl` 过滤掉已落入快照的部分（与主对话同机制），重放进详情页的增量只补「快照之后」的尾部。

## §4 风险与不变量

- **不变量（沿用 docs/21 §5）**：SSE 事件名表不增删（delta 复用 `subagent` 事件名，只是新 phase 值；契约测试不受影响）；两层架构不破（worker 过程仍不进前台历史/协调者上下文，delta 只进抽屉）；`spawned ⟹ 终态事件`守恒不受 flush 影响（flush 只管 delta 文本，不产生生命周期事件）。
- **缓存失效风险**：SessionStore 新增写路径（未来）忘记维护缓存 → 列表陈旧。对策：写路径集中（save/delete/purge/restore/recycleWorkspace 五处）+ 注释警示 + 测试覆盖。
- **MCP 异步化窗口**：会话创建到 MCP 就绪之间系统提示缺 MCP 段/工具——与 coordinator `workerMcpToolsOf` 预热同款窗口（已有先例）；`startTurn` 的 `await rt.mcpReady` 收口（首条消息发出时工具必已注册，语义与现状等价，只是等待点后移）。
- **前端事件量**：120ms 合并下单个 worker 每秒 ≤8 条 delta 事件，3 并发 worker ≤24 条/秒——SSE 本地回环无压力；文本量由 flush 合并自然控制。
